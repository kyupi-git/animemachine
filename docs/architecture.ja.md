# AnimeMachine アーキテクチャ

AnimeMachine は、証拠と書き込み権限の境界を明確に分けます。Torrent Collector は新しい `.torrent` メタデータを発見して書き込み、AnimeMachine は Torrent Pool を読み取り専用で走査します。AnimeMachine はダウンロード計画を生成し、実際のメディア取得は qBittorrent または Ani-RSS が担当します。外部メディアライブラリは識別や再生に利用でき、既定では読み取り専用です。階層化された状態により、一つの曖昧な一致が自動化経路で拡大され、誤ったディレクトリや誤ダウンロードになることを防ぎます。

Collector の完全性フィルタは `src/animemachine/torrents/collector_filter.py`、ネットワーク探索とサービスループは `collector.py`、移行、再試行、原子保存、Pool 監査は `collector_state.py` にあります。Collector はローカル Catalog を読み取り専用で参照します。SEARCH、FILTER、metainfo classifier のバージョンは独立管理され、FILTER の変更では既発見結果を先に再評価し、SEARCH が変わった場合だけ新しい履歴探索世代を作ります。Torrent v1、v2、hybrid の identity は `metainfo.py` が一元的に計算・保存し、入口ごとに別々の hash 規則を作りません。

## 0.2.1 のアーキテクチャ

0.2.1 でも従来の「証拠境界 + 書き込み権限境界」を維持し、Catalog、Torrent Pool、qBittorrent、Ani-RSS 間の責務は変更していません。主な変更は、従来分散していたネットワーク耐障害性とバックグラウンド保守を共有基盤へ昇格したことです。`network/connectivity.py` が障害疑い、確定オフライン、環境変更、復旧許可の状態を一元管理し、`network/diagnostics.py` が実際の接続先プローブを本番要求と同じ健全性学習へ接続します。`application_update.py` は共通のネットワークソース、ダウンロード、完全性検証を再利用して Release の検出と更新を行います。Docker イメージでは安定した `packaging/docker/entrypoint.py` が検証済みアプリ層を選択し、再起動を監督し、新しい層がヘルスチェックに失敗した場合はロールバックします。Docker のアプリ層が置き換えるのは AnimeMachine の Python パッケージだけで、ベースイメージ、supervisor、Python/OS コンポーネント、実行時依存関係は対象外です。これらの境界が変わる場合は完全な新イメージを公開・取得します。アプリ層の有効化では、まず `pending.json` に対象とロールバック情報を永続化し、その後 `current` ポインタを原子的に切り替えるため、二つの書き込み間で中断しても初回ヘルスチェックを受けていない新層だけが活動状態になることはありません。ポータブル版更新 worker と Docker supervisor の初回ヘルスプローブは実際の Web 待受アドレスから導出し、LAN/IPv6 への明示バインドはそのアドレスを直接探査し、IPv4/IPv6 のワイルドカード待受だけをローカルループバックへ変換するため、正常な置換先を更新失敗と誤判定しません。

画像側では、バックグラウンド先読み、失敗再試行、定期更新を別々の優先段階とし、前景昇格、適応型リソース予算、永続化進捗を同じスケジューリング境界で扱います。サービスのライフサイクルも `Starting → Ready → Warming → Warm` と明示し、「Catalog は利用可能」と「画像/履歴のバックグラウンド準備中」を分離しました。リモート Ani-RSS 再生は AnimeMachine HTTP 中継を使うため、Ani-RSS メディアディレクトリをマウントしない構成も同一再生経路に入り、限定的な Range、再開、スループット診断を記録します。

Ani-RSS リソース探索は画像事前取得と作品優先順を共有しつつ、独立したネットワークキューで動作します。正常な優先/フォールバックモードでは現在のホームページ群と直近 6 か月を先に処理し、その後 7～24 か月前を月単位で遡り、運用中の再確認はリソースプール走査間隔で起動します。起動時の事前取得と周期再確認は非ブロッキング走査リースを共有し、前回がまだ実行中なら新たに期限到達した回は待機させず並列実行もせず、そのままスキップして完了時刻も進めません。実行時 Ani-RSS 監視も同じリソース再確認を独立してスケジュールし、初回導入で画像事前読み込みが API の初回正常同期より先に開始しても、そのプロセス内で `ready` になった後の監視回から再起動なしで探索を補完します。`ani_rss_search_state` は作品ごとの最終試行、成功時刻、結果数、失敗証拠を保存して重複要求を抑えます。接続／転送失敗は正常な走査完了として扱わず、スケジューラは最大 5 分の短い再試行へ切り替えます。時計の巻き戻しで作品単位の最終試行時刻が現在より明確に未来へずれた場合は直ちに期限到達として扱い、未来時刻によって探索が長期間抑制されることを防ぎます。24 か月境界は自動探索だけを制限し、ユーザーの明示選択は古い作品もオンデマンド検索できます。地域方針は Torrent と Ani-RSS の適格性判定前に共通適用し、共同制作は少なくとも一地域が許可されていれば残します。 リソース検索は現在のタイトル候補で結果がない場合、利用可能な中国語・日本語・英語の後続候補を結果取得または候補枯渇まで順に試します。リソースオーバーレイは現在の Ani-RSS の「エンドポイント + 資格情報フィンガープリント」世代にも結び付けます。同期でエンドポイントまたは API Key の変更を検出すると、同一トランザクションで旧 `ani_rss_resource` / `ani_rss_search_state` を消去して探索を再び期限到達にし、旧世代で実行中の検索はコミット前に世代を再確認して不一致なら遅着結果を破棄します。リモートのリソース検索は開始時の実効プロキシルート世代も固定してコミット前に再確認し、検索中にプロキシまたは `NO_PROXY` が世代交代した場合は、その結果を破棄してネットワーク世代をまたぐ書き戻しを防ぎます。


実行中の Ani-RSS 同期は `ani_rss_state`、`ani_rss_subscription`、`ani_rss_media` からなる一つの整合スナップショットとして扱い、自動の購読／メディア更新を Web サービスの単一監視入口へ集約します。CLI の明示同期は引き続き利用できますが、別の自動周期 worker と競合しません。正常な `listAni` で作品対応を先に確定し、その後 URL を保持するすべての対応済み購読を制限付き並列 `playList` で取得します。リモートで無効化されていてもダウンロード済みファイルを保持する可能性がある購読も対象です。`last_success_at` はメディア段階まで完全に終了した場合だけ進み、個別 `playList` が失敗した場合や明示的ユーザー操作へ処理を譲った場合はその購読の直前正常スナップショットを保持し、次の完全間隔を待たず最大 5 分で補償同期の対象になります。時計補正によって保存済みの試行／成功時刻が現在時刻より明確に未来側へずれた場合も、直ちに期限到達として扱い、未来時刻によって更新が長期間抑制されることを防ぎます。要求とメディア段階には上限時間を設け、バックグラウンド同期は明示的なユーザー Ani-RSS 操作が待機していない場合だけ非ブロッキングで操作ロックを取得するため、停止または部分障害中の Ani-RSS がユーザー検索、Torrent、画像フォールバック、Web 要求を長時間占有しません。作品詳細の再生可能件数は購読進捗ではなく `ani_rss_media` の実スナップショットから算出します。Ani-RSS メディアディレクトリを設定している場合、その読み取り専用走査は同じ間隔設定を使いながら HTTP API の健全性とは分離し、独立バックグラウンドスレッドで動作します。API 未設定/利用不能でも走査でき、ソース単位の非ブロッキング走査ロックにより同じソースの前回が未完了なら新しい回だけをスキップし、他の外部ライブラリは妨げません。カバーは正常なローカルキャッシュがない場合、またはユーザーが明示的に再読み込みした場合だけ、現在の API Key が直近同期で検証済みの資格情報世代と一致し、接続先と同期状態も正常確認済みの場合だけ、同期済み購読の `cover` と Ani-RSS `/api/file` から取得します。要求は早期失敗させ、返却内容は画像として検証し、その検証に成功した後だけ `/api/file` を正常と記録します。検証できなければ直ちに ImageFetcher の従来経路へ戻します。転送障害またはサーバー障害が起きた `/api/file` エンドポイントは現在の資格情報世代との組み合わせごとに 30 秒間の早期フォールバック状態に入り、後続カバーが作品ごとに同じ待ち時間を繰り返しません。この抑制は対象 Ani-RSS エンドポイントが実際に使うルート世代へ結び付け、リモートの実効ルートが本当に変わった場合だけ早期無効化するため、localhost/LAN の直結先は無関係なプロキシ切替の影響を受けません。API Key を交換して正常な再同期が完了した場合も旧資格情報の抑制を引き継ぎません。リモート Ani-RSS の統合同期は各回の開始時点で実際に使うルート世代を固定して保存します。要求途中でプロキシが切り替わっても新ルートを検証済みと誤認せず、世代差から直ちに補償同期を起動できます。環境プロキシ、Windows システムプロキシ、`NO_PROXY` 規則によって新しいルートが成立した場合は、通常の同期間隔が未到来でも直ちに同期対象になります。新ルートの同期検証が完了するまでは、以前のリモート `ready` スナップショットを論理的に `unknown/manual` として扱い、現在のリソース、外部読み取り専用メディア、リモート再生元には使いません。ただし基礎スナップショット自体は保持し、再同期成功後の迅速な復旧に利用します。localhost、ループバック、プライベートネットワークの Ani-RSS は直結を維持し、このプロキシ世代トリガーから除外するため、ローカルサービスを誤ってプロキシへ送ったり無意味に再同期したりしません。 同じリモート ID について一回の `listAni` 応答だけ URL、有効状態、現在/総話数、ダウンロード先などの任意証拠が欠けた場合は、直前に検証済みの値を継承し、不完全な一回の応答でメディア更新経路を切断したり既知状態をゼロへ戻したりしません。ダウンロード先は現行 Ani-RSS の `customDownloadPathTemplate` と旧レスポンスの `downloadPath` の両方を認識し、バージョン差でパス証拠を失いません。実際に完全なリモート一覧から消え、削除猶予条件も満たした購読だけを削除へ進めます。`listAni` の申告総数より実際に返る一意のリモート ID 数が少ない世代は不完全な購読スナップショットとして扱い、未返却購読の削除猶予を進めず、完全成功時刻も更新せず、短い周期の補償再試行を維持します。旧版 Ani-RSS との互換のため `listAni` に `total` がない応答でも既存行は更新できますが、「その世代で欠落した」ことだけを削除証拠にはせず、有効な `total` が返却された一意のリモート ID 数と一致した場合だけ削除猶予を進めます。リモートメディア token は上流へ接続する前に現在の資格情報と `ani_rss_state` を再確認し、Ani-RSS が正常でなくなった場合は古いプレイヤー要求をローカルで即時失敗させます。正常な `listAni` が対応済み作品へ明示的な `cover` パスを返した場合、有効な画像バイトを持たない、その作品の従来画像経路由来 `no_cover` 負キャッシュも同期時に解除します。そのため Ani-RSS が復旧して再検証された後は、24/72 時間の保守周期や期間外の自動更新停止に妨げられず、次の通常画像要求から Ani-RSS カバーを利用できます。 プロトコル境界は 0.2.1 の完全 Compose が固定する Ani-RSS `v3.2.28` で検証しています。`listAni` / `playList` / `mikan` / `mikanGroup` はトップレベル型だけでなく `weekList` / `weeks` / `items` などの入れ子オブジェクト配列も厳密に検証し、子構造が壊れている場合はプロトコルエラーとして失敗閉鎖します。異常応答を完全な空スナップショットと誤解して購読の削除猶予を進めたり、メディアやリソースキャッシュを消したりしません。

「利用可能なソース」と「ライブラリ状態」は直交した証拠軸です。Torrent と Ani-RSS は同時に成立でき、両方がない場合だけ「利用可能なソースなし」となります。Ani-RSS が現在の利用可能ソース証拠になるのは、資格情報が設定済みで接続状態が `ready` と確認されている間だけです。資格情報の削除・変更や接続先変更後に古い ready 状態を使い続けません。公開する「ライブラリ状態」は細粒度の内部証拠から排他的な 4 分類へ正規化し、ローカル入庫 > 外部読み取り専用 > ダウンロード送信済み > 未入庫の優先順で決定します。`runtime_work` の `existing` と完了済み qBittorrent 結果はローカル入庫、検証済み外部媒体は外部読み取り専用です。有効な購読へ対応する `ani_rss_media` の HTTP 再生可能媒体は、現在の資格情報が存在し接続状態が `ready` と確認されている間だけ外部読み取り専用となり、その場合だけカード単位の `has_external_media` 証拠にも反映します。API 切断、資格情報の削除・変更、または接続先変更後の再検証待ちでは、SQLite の過去メディアスナップショットは復旧用に保持しますが、カード、詳細、再生入口から現在再生可能な外部媒体としては公開しません。独立してマウントされた読み取り専用媒体はこの API 健全性ゲートの影響を受けません。未完了 qBittorrent の `queued` / `downloading` 系だけがダウンロード送信済み、それ以外は未入庫です。`occupied_review`、`placeholder`、`absent` などはディレクトリ検証、完全性、書き込み安全判定のため内部に残りますが公開分類にはせず、Ani-RSS 購読もダウンロード送信済みには数えません。地域ポリシーはまず Catalog SQL の表示可否へ適用するため、無効化した地域の作品が「利用可能なソースなし」として再表示されることはありません。同じ規則をカード情報と Torrent/Ani-RSS 適格性にも適用し、既存 Ani-RSS 購読が無効化した地域を迂回しないようにします。日本以外の作品は引き続き Archive の国・地域証拠と文字体系から `original_language` を推定し、アニメ原題、原作名、制作会社集約は独立フィールドのまま同期ソースによって上書きされません。 カード上の Ani-RSS 管理フラグとリソース件数もフィルター、詳細、再生と同じ健全性ゲートを使い、資格情報の削除・変更、接続先変更後の再検証待ち、接続失敗時には直ちに無効化します。過去の SQLite スナップショットだけで「現在利用可能」に見える状態を作りません。

## 実行境界

AnimeMachine の主要実装は `src/animemachine` にあります。Web、Catalog、Torrent 索引、ライブラリ検証、qBittorrent、Ani-RSS、再生、字幕の各モジュールは SQLite 証拠を共有しますが、「得られた結果はどこへでも書き込める」という権限は共有しません。ある結果がディレクトリ変更、ダウンロード投入、置換へ進むには、次の段階が要求する証拠強度を満たす必要があります。

AnimeMachine が直接扱う入力は二種類です。(1)ユーザーまたは任意の Torrent Collector が共有ディレクトリへ置いたローカル Torrent メタデータ、(2)ユーザーが接続した外部コンポーネントから返された記録です。Archive、カバー、補助メタデータは共通ネットワーク層を通り、プロキシ/直結の選択、ミラー切替、失敗時バックオフ、レスポンスサイズ制限、完全性検証を行います。サイズとダイジェストが既知の Archive/アプリ更新資産では、ダウンロード層が再開可能な Range 分割を優先し、分割転送が失敗して確認済みの非 Range 代替ソースがある場合は全体ファイル転送へ降格します。原子的な公開前にサイズと SHA-256 を検証し、完全取得済みでもダイジェスト不一致の一時ファイルは次回再試行へ持ち越しません。プロキシ設定は要求ごとに再取得し、実効経路を直結、環境プロキシ、Windows システムプロキシとして分類します。プロキシ URL の破損、無効なポート、または現在の実行環境で必要なプロキシ転送を生成できない場合は、クライアント生成段階でその候補だけを隔離して後続経路へ進み、診断の経路識別子にも脱機密化した scheme/host/port だけを残します。実際のプロキシ設定が変わると接続世代は更新されますが、ネットワーク健全性の学習はこの安定した経路分類ごとに蓄積します。そのため、以前使ったプロキシ環境へ切り替えればその環境で学習した最適ソースを再利用でき、直結へ戻っても直結時の履歴は失われません。localhost、ループバック、プライベートネットワークは直結を維持します。デプロイ側の資格情報は環境変数またはシークレットファイルを優先します。管理者が Web 設定で入力した qBittorrent、Ani-RSS、字幕サービスの資格情報は状態ディレクトリ配下の制限付き資格情報ファイルへ保存され、再起動後も有効です。公開設定、ドキュメント、ブラウザストレージ、Web API 応答には書き出しません。POSIX ではサービスアカウントだけが読み書きできる権限にし、Windows では可能な限り現在のサービスアカウントと SYSTEM だけへ ACL を絞ります。これは権限で隔離したローカル保存であり暗号化 Vault ではないため、サービスアカウントまたはホスト管理者はファイルを読めます。デプロイ側の環境変数/Secret は Web 保存値より常に優先します。接続テストでは、ブラウザに現在入力されている qBittorrent/Ani-RSS Key をその要求だけの一時資格情報としてサーバー側プローブへ渡せますが、プロセス環境や状態ファイルには書き込みません。永続化は設定保存経路でのみ行います。サーバーは完全な設定と今回入力した資格情報を一つの設定トランザクションとして扱い、永続設定と実行時オーバーレイ後の設定を先に完全検証してから、設定とロールバック可能な資格情報バッチをコミットします。永続化に失敗した場合は保存前の状態へ戻します。設定と資格情報の変更は同じ書き込みゲートを共有するため、並行する管理者要求がトランザクションやロールバックの途中へ割り込むこともありません。明示的な接続テストは `recovery_probe` 内で実行するため、完全オフライン確定後でも管理者のプローブをローカルモードが遮断せず、localhost、ループバック、プライベートネットワークは引き続き直結します。ネットワーク健全性層は各接続先の直近成功率、EWMA 遅延、スループット、冷却状態、直近失敗理由をネットワーク環境別に永続化し、時間バケットで画像ソースの短期健全性推移も保持します。直近の証拠は時間減衰した有効サンプル数として扱い、サンプルが少ない結果は信頼度で中立値へ収縮させるため、一度だけの成功・失敗で順位が大きく変わりません。接続先選択は複合品質に加えて現在ソースの保持時間と最小切替利益を持ち、候補が十分に優れる場合、または現在ソースがクールダウンへ入った場合だけ切り替えます。診断プローブと実際の要求は同じ健全性証拠を共有し、現在の選択、サンプル信頼度、保持・切替理由も表示します。完全オフラインは、AnimeMachine の常用サービスと独立したインターネットプローブの双方が、長い観測空白なしに少なくとも 30 分連続して失敗した場合だけ確定します。全体障害を最初に疑った時点から失敗サンプルの学習だけを停止し、通常要求の試行は継続し、リモートのバックグラウンド処理を停止するのはオフライン確定後だけです。復旧プローブは常にローカルモードを迂回でき、通常要求または手動ネットワーク再検査が一度でも接続成功を証明すればオフライン状態を解除してバックグラウンド処理を再開するため、プロキシ切替、短時間の切断、単一上流障害、スリープ復帰でローカルモードに固定されません。画像プリロードは別プロセスで実行し、バックグラウンドの並行数・帯域制限はバックグラウンドタスクだけに作用します。前景で表示された作品を常に優先し、すでにバックグラウンド待ちの同一作品も前景要求で即座に昇格できます。バックグラウンド予算は前景操作、前景画像の応答時間、CPU 負荷、直近の画像 I/O 時間、ネットワーク失敗信号に応じて保守的に縮小します。ブラウザ側ではスクロール方向に沿って厳密に制限した次画面付近だけを先読みします。起動後のバックグラウンド事前取得は、現在のランダムシードで有界の先頭ページ群をページ順に完了し、次に直近 6 か月の全作品を補完し、その後 7 か月前から月単位で厳密に古い作品へ遡ります。定期画像更新は独立した最低優先度キューを使います。正常な既存キャッシュは、放送 6〜2 か月前、2 か月前〜放送 1 か月後、放送 1〜2 か月後の各期間だけ自動確認し、間隔はそれぞれ 72、24、72 時間です。低優先度スキャンは 12 時間ごとに期限到達作品を選び、期間外では自動更新を停止しますが、手動の「再読み込み」は常に強制更新できます。

任意の Torrent Collector は独立した Compose サービスとして動作し、共有 Torrent Pool には書き込みできますが、AnimeMachine は同じ Pool を読み取り専用で扱います。この境界は意図的です。Collector が判断するのは「このメタデータを候補プールへ入れてよいか」であり、AnimeMachine が判断するのは「実際にどの作品へ対応し、必要範囲を覆い、ダウンロードすべきか」です。前者は後者の代わりになりません。

初回導入の挙動もセキュリティ境界の一部です。CLI、ローカル起動、4種類の Compose は既定で `0.0.0.0:8787` に統一して待受するため、同一 LAN の端末から `IP:8787` で利用できます。回環以外を待受する場合、対応する高度な方針で明示上書きしない限り Web 認証を自動的に有効化します。アカウント DB の初回作成時は、管理者パスワードが自動生成、デプロイ変数、秘密ファイルのいずれから来た場合でも、初期管理者名とパスワードをコンソールへ表示します。ゼロ設定で自動生成され、権限制限された bootstrap 資格情報ファイルへ保存された初期管理者については、そのアカウントが有効な管理者である間、後続の起動でも同じ資格情報を再表示するため、初回ログを見逃しても復旧できます。明示的なデプロイ資格情報は、再表示だけを目的として追加保存しません。管理対象 qBittorrent/Ani-RSS のサービス秘密値が未指定なら、各 bootstrap がコンポーネント設定ディレクトリの `.animemachine/` 配下へ一度生成して永続再利用し、AnimeMachine はそのファイルを読み取り専用でマウントします。明示的な環境変数や Secret は引き続き優先されます。管理構成 3/4 では、アプリ起動を一回限りの bootstrap の正常完了と対応サービスコンテナの起動へ明示的に依存させるため、初回の空設定ディレクトリで API Key ファイル生成より先に AnimeMachine が起動することもありません。Compose は必須の `.env` に依存せず、ローカルディレクトリにも相対パスの既定値を持つため、テンプレートをそのまま起動でき、`.env` は既定値を上書きするときだけ使用します。`04-full-stack/compose.yaml` は Torrent Collector サービスと名前付きボリューム定義も内包しており、空ディレクトリへこの YAML だけをコピーしても完全な構成を保ちます。完全構成のパス契約も一貫しており、Ani-RSS の最終ダウンロードテンプレートは共有 `/Media`、qBittorrent は `/downloads/incomplete` を未完了データ用に使い、AnimeMachine は完了メディアを読み取り専用 `/Media` から利用するため、「購読 → ダウンロード → 検出/再生」がゼロ設定のまま閉じます。Docker supervisor は root を必要な書き込み可能マウントポイントの非再帰的な所有権準備だけに使い、その後 AnimeMachine の各コマンドを起動する前に `PUID/PGID` へ恒久的に降格します。これにより Docker が初回作成した空の bind ディレクトリでもゼロ設定起動を妨げず、アプリ本体は非 root のまま動作します。

## Web 認証と権限境界

Web 層はローカル SQLite アカウントストアと短期セッション Cookie を使用します。認証有効時のロールは `admin` と `user` の 2 種類だけです。サーバー側の `requires_admin()` は設定書き込み、Archive/メタデータ保守、Library Audit、履歴復元、ユーザー管理、ネットワーク再検査、画像事前読み込み制御、ログ/履歴/診断の参照、アプリ更新などの管理 API を一括して管理者権限で保護します。一般ユーザーには Catalog 検索、作品単位操作、ダウンロード計画、許可された再生/購読機能が残ります。状態変更要求には有効な CSRF token も必要です。設定/API 出力では認証情報などの機密値をマスクします。

フロントエンドの表示制御は操作性の補助にすぎず、安全境界は常にサーバー側で再検証します。たとえば全体の「再シャッフル」はインスタンスのランダムシードを変更するため管理者だけに表示し、一般ユーザーが手動で要求を組み立ててもサーバーが拒否します。認証無効時はローカル単一ユーザーセッションを管理者相当として扱いますが、Host/Origin と書き込み要求の制約は維持されるため、「ログイン不要」は「要求境界なし」を意味しません。

## データフロー

```text
Bangumi Archive ──> アニメ Catalog ──> タイトル、関係、ディレクトリ計画
Torrent Collector ─> 共有 Torrent Pool（一括リリースのメタデータ）
Torrent Pool ──────> 増分インデックス ──> 候補方針とファイル一覧
ローカルライブラリ ─> 検証/履歴 ──────> 差分補完と状態
Ani-RSS ──────────> 購読と読み取り専用メディアマッピング
候補計画 ─────────> qBittorrent / Ani-RSS ──> ダウンロード状態の反映
```

Archive はバックグラウンドで段階的に構築し、完全性検査に合格してから原子的に公開します。大規模 Torrent Pool と外部メディアライブラリは増分・短バッチで処理し、一回の全量走査が長いデータベーストランザクションを保持しないようにします。Web 読み取りは独立接続と短いトランザクションを使うため、カタログ構築、走査、対話的な閲覧を並行できます。起動状態 API はライフサイクルを `Starting → Ready → Warming → Warm` と明示します。`Ready` は Catalog と Web が利用可能であることを意味し、`Warming` はバックグラウンドの Catalog/画像準備が続いているだけで、サービス利用不可として扱いません。ホームの第 2 状態行は、バックグラウンド画像状態、`YYYY-MM` までの履歴方向進捗、使用中の Bangumi Archive 版、Catalog 作品総数を簡潔にまとめ、残り件数、ETA、現在の処理対象は表示しません。完全な進捗、残り見込み、実スループット由来の ETA、現在の対象、適応型バックグラウンド並行数は診断画面に残します。年/季フィルタは引き続き明示的な `start_from` / `start_to` 月境界へ投影します。冬は 1 月を含む年を基準に前年 12 月まで跨ぎ、春・夏・秋はそれぞれ 3～5、6～8、9～11 月へ写像するため、サーバー側に別の季節クエリ意味論は追加しません。ブラウザから旧フィルタ状態を復元するときは、現在の季節定義で正規化してから年/季を逆同期します。年を明示せず跨年冬季の月範囲だけを保存した旧状態は 1 月を含む年を基準にし、復元時の 1 年ずれを防ぎます。プリロード段階と制御状態は別途永続化され、再起動後は画像キャッシュを事実上の基準として処理を継続します。

日本以外の作品でも Archive の主タイトルは互換性のため `anime_work.title_ja` に保存しますが、この物理列名は歴史的な互換名であり、意味は「Archive の主タイトル／原題」です。実際の言語は `original_language` を正とします。`anime_title` は言語タグ付きの多言語タイトルと別名を保存するため、韓国語の主タイトルと中国語訳、日本語版名、英語版名を同時に保持できます。国・地域の証拠はタグ、Infobox、主タイトルの文字種、制作会社から統合します。日本以外の制作会社集約は `ブランド〖法人一覧〗`、`法人名（ブランド）` のような Archive 上で検証可能な構造だけを利用し、日本作品は従来の改名ファミリー規則を維持します。原作タイトルは関係データとしてアニメの主タイトルと分離し、アニメ原題を上書きしません。詳細画面の関連作品名、シリーズ関係図、後続リリース監視、画像プリロード診断の現在作品名も現在の UI 言語と同じ選択規則を使い、`anime_work` / `anime_title` に検証済みの中国語・英語・日本語タイトルがあればそれを優先します。0.2.1 の機能移行では保存済み英語別名を再走査し、CJK・キリル・ギリシャ・アラビア文字などラテン文字以外のアルファベット文字を含むのに `en` と誤分類された候補を拒否し、旧 Catalog の `anime_work.title_en` を補正またはクリアして新しいタイトル方針世代を記録します。上流に英語名が存在しない場合、英語表示層は作品の原題へ一時的にフォールバックしますが、その値を `title_en` へ書き込んだり英語名として分類したりしません。検証済み英語名を後から取得すれば自然にそちらが優先され、Catalog の再構築も不要です。簡体字中国語 UI では原言語が粗い `zh` 表記でも、明示的な `zh-Hans` タイトルを優先します。タイトル正規化では韓国文字とキリル文字も保持し、原作照合、字幕検索、メディア完全性比較に利用します。

カバーはアプリ全体を遅くしやすい外部依存なので、画像のネットワーク取得を独立 `ImageFetcher` プロセスへ移しています。Bangumi の約 400 px のサーバー側縮小画像を優先し、公式ソースと利用可能なミラーへ短い遅延差を付けた並列フォールバックを行い、原寸画像は最後の代替に残します。一時的な失敗は短期間だけ負キャッシュし、サービス再起動時にその状態を消去します。キャッシュ未命中時は Web API がすぐプレースホルダーを返し、バックグラウンド取得成功後にフロントエンドが置き換えます。同じ作品を取得中に「再読み込み」を押した場合も、一回の強制更新を保持し、進行中要求に吸収されて消えないようにします。既に有効なキャッシュの更新に失敗した場合は旧画像をそのまま提供し、最後に成功した取得時刻と失敗証拠を保持します。これにより、失敗した確認を成功更新として 24/72 時間先へ送ることなく、後続の 12 時間保守パスで元の更新規則に従って再試行できます。一括画像保守は終了状態を基準に進捗を集計し、完全オフラインまたは画像ワーカー利用不能によりキューへ入れなかった項目は失敗として数えるため、待機項目がないだけで成功扱いにはなりません。 Web に永続化した資格情報は独立画像プロセス生成前に親プロセスへ読み込み、さらに各タスクが現在の実効 Ani-RSS 資格情報スナップショットを持ちます。そのため `spawn` 子プロセスが起動時の古い API Key を後続要求へ固定することはなく、実行中の Key 変更・削除も再起動なしで Ani-RSS カバーのショートカットの有効化・切替・停止へ反映されます。

## 作品識別とディレクトリ

ディレクトリ処理には固定の順序があります。**作品を識別し、既存パスを識別し、その後にだけ新規作成を検討する。** 作品 identity はタイトル、別名、初回放送月、シリーズ関係、既存ファイルから証拠を得ます。既存ライブラリに一意で信頼できる近似ターゲットがあれば再利用し、誤ったディレクトリを見つけた場合も「より標準的な二つ目」を作る前に元位置で修正します。公式英語副題は原題と意味が異なり、十分な証拠がある場合だけディレクトリ名へ追加します。

理由は、Bangumi の論理エントリが一つの物理ディレクトリと同義ではないからです。分割放送、付属短編、元から分割されていない映画/OVA の一括リリース、非常に長い連続作品では、複数の論理メンバーが同じ物理ターゲットを共有する場合があります。逆に物理ターゲットを統合しても、Catalog 内の論理メンバーは分けて保持します。したがって、すべてのダウンロード計画はまず正規ターゲットへ解決してからローカルファイルと差分比較し、Torrent タイトルだけから identity 層を飛ばしてディレクトリを作ることはありません。

## リソース戦略

ユーザー提供 Torrent と Collector 収集 Torrent は最終的に同じ増分インデックスへ入ります。Collector の事前フィルタは、自動収集境界から明確に外れるメタデータを止めるだけで、AnimeMachine の作品識別、適格性判断、順位計算を代替しません。リソース種別はユーザーが明示的に無効化した場合だけ除外し、認識できない値は「その他」へまとめます。古いリリースの命名は必ずしも標準化されていないため、長期アーカイブでは未知値を即エラー扱いするより安全です。

許可するリソース種別には地域方針も含まれます。中国は中国本土・香港・マカオ・台湾、欧州は英国・ロシアを含む全欧州国、空欄または証拠不足は「その他」へ対応します。この方針は新規候補の適格性だけを制限し、既存メディア、購読、履歴証拠は破壊しません。

順位は、一作品または一シリーズを満たす完全な案を単位とします。最初に必要話数/巻数を覆えるかを判断し、その後で一括性、リリースグループ、ソース、解像度、字幕、改訂日などを比較します。品質条件はカバー範囲が成立した後に評価され、高解像度でも欠話を相殺できません。

同一 infohash に AnimeMachine 管理タスクは一つだけです。一つの一括リリースから異なるファイル index を複数の子作品へ割り当てられ、後から追加ファイルが必要になった場合は既存タスクを再利用して、以前未選択だった index だけを追加します。正式投入の前には必ず不変計画を生成します。ターゲットディレクトリ衝突や置換対象ファイルがあれば、既存内容を直接上書きせず、一時保管、検証、レビューへ進みます。

## 作品関係グラフのアルゴリズム

作品関係図は、多対多の証拠から関係構造を復元し、その後で描画方法を決めます。第一段階ではグラフ自体を処理します。(1)Bangumi の元関係を方向付き edge へ正規化、(2)確定できる逆関係を追加、(3)確認済みの重複 edge と証明可能な推移冗長 edge を削除、(4)厳密関係からシリーズ連結成分を作成、という順序です。明らかな誤接続修正、孤立サブシリーズへの入口追加、サブシリーズ先頭への関係再アンカーは、強い証拠がある場合だけ行います。元の関係証拠は常に残し、修正後の解釈で取得元の事実を上書きしません。

第二段階でレイアウトします。ノードは年月、媒体、タイトル順に並べ、同じ媒体または明確な数値順序を持つ作品は同じ行を優先します。主系列続編は可能なら中央の直線トラック、番外、派生、総集編、別演出・翻案、シリーズ横断関係は別トラックとポートを使います。ルーターはノード境界、使用済みトラック、ラベル矩形、曲がりコストを同時評価し、直線、直交折れ線、必要時の縦迂回を選べます。同じ起点を持つ長距離 edge は時刻と目的位置でさらに階層化し、読み取りにくい交差を減らします。複雑な図では指定関係種別の非表示、全画面表示、SVG/PNG 書き出しに対応します。

実行データベース、Archive、カバーキャッシュ、ログ、資格情報、非公開パス、ビルド成果物は実行時/ローカル成果物であり、ソースツリーには含まれません。この区別から、ソースは再取得できますが状態ディレクトリはバックアップ対象になり、逆にビルドキャッシュのクリーンアップでユーザー Catalog や所蔵履歴を触ってはいけないことも分かります。

## データベース規約

AnimeMachine は二つの SQLite を使い、「大規模走査の書き込み」と「安定したフロントエンド照会」を分離します。(1)アニメ Catalog は既定で `$ANM_STATE_DIR/catalog/anime-catalog.sqlite3` にあり、Bangumi Archive 由来のアニメメタデータ、作品関係、カバー、外部メディアマッピング、Web 照会と計画生成に使う runtime 状態投影を保存します。(2)実行ライブラリは既定で `$ANM_STATE_DIR/catalog/runtime.sqlite3` にあり、Torrent Pool の生の増分索引、検証済み identity、ファイル分割、投入証拠、ローカル検証結果を保存します。短バッチ完了後に検証済み結果だけを Catalog の `runtime_*` テーブルへ同期するため、フロントエンドが走査 DB と直接競合しません。

両 DB のパスは環境変数で上書きできますが、二つの AnimeMachine インスタンスが同じ状態ディレクトリへ同時書き込みしてはいけません。アニメ Catalog の基礎構造は `src/animemachine/catalog/service.py`、実行ライブラリのマイグレーションは `src/animemachine/catalog/migrations.py`、照会投影は `src/animemachine/torrents/runtime.py` が管理します。マイグレーションは前方互換かつ反復実行可能である必要があります。資格情報、非公開パス一覧、手動エクスポートを公開ドキュメントやテスト fixture へ書き込んではいけません。

### アニメ Catalog

- `anime_work`：論理アニメ作品。Bangumi ID、Archive 主タイトル（物理列 `title_ja` は互換名）、`original_language`、初回放送月、媒体、話数、概要、物理統合ロールを保存します。
- `anime_title`：言語タグ付きの多言語タイトルと別名。日本以外の原語主タイトルや明示的な地域／言語版名も保存し、ディレクトリ命名には検証済み原題と本当に必要な副題だけを使用します。
- `anime_staff`、`anime_cast`、`anime_studio`、`anime_studio_cluster`：スタッフ、キャスト、制作会社の正規化データ。
- `anime_tag`、`anime_theme`、`anime_theme_evidence`、`anime_country`：フィルタ項目とそのルール証拠。
- `anime_relation`：Archive の元関係。`anime_relation_edge` と `anime_series_component` は正規化関係と厳密なシリーズ連結成分を保存します。
- `anime_image`：検証済みカバー MIME、bytes、取得元、キャッシュ状態。完全取得と形式検証後にだけ原子書き込みします。
- `external_library_source`、`external_media_file`：外部読み取り専用メディアライブラリの取得元、ディレクトリ、ファイル単位証拠。
- `ani_rss_state`、`ani_rss_subscription`、`ani_rss_media`、`ani_rss_resource`、`ani_rss_search_state`、`ani_rss_action`：Ani-RSS 同期状態、再生可能メディアのスナップショット、バックグラウンド検索の抑制状態、冪等操作記録。
- `metadata_snapshot`、`metadata_evidence`、`metadata_repair_queue`：底包 provenance、補助メタデータ、遅延修復タスク。

### 実行ライブラリと照会投影

- `torrent_source`、`torrent`、`torrent_manifest_file`：Torrent Pool のファイル指紋、infohash、タイトル、ソース、リリースグループ、manifest、解析エラー。取得元指紋が変化した場合だけ再読み込みします。取得元パスの identity はホストファイルシステムの正規化規則に従い、Windows では大文字小文字を同一視し、大小文字を区別するファイルシステムでは差異を保持することで、消失した取得元を正確に照合します。同一 info-hash に複数の `.torrent` コピーがある場合、現在の主取得元が消失しても完全走査時に残存コピーへ `torrent_path` を再選択し、利用可能なメタデータが失効パスを指し続けないようにします。
- `anime_work`、`anime_work_member`、`torrent_work`：物理ターゲット、論理メンバー、Torrent と作品の検証済み多対多マッピング。`torrent_work` は identity と最終パスの権威ある証拠です。
- `file_map`：一括リリース内の各ファイル index について正規ターゲットと選択証拠を保存します。
- `submission`、`submission_revision`、`submission_file_revision`：AnimeMachine 管理 qBittorrent タスクと追加選択履歴。一つの infohash は一つのタスクに対応します。
- `asset_provenance`、`release_baseline`、`upgrade_candidate`：ローカルファイル provenance、比較基準、検証可能な更新候補。
- `torrent_resolution`、`torrent_target_path`、`title_review`、`scope_exclusion`：自動解決できない範囲、タイトル、ターゲット、処理理由。
- `runtime_work`、`runtime_torrent`、`runtime_torrent_work`、`runtime_torrent_file`、`runtime_file_map`、`runtime_submission`：アニメ Catalog 内のフロントエンド照会投影で、実行ライブラリの権威ある記録を置き換えません。
- `download_plan`、`runtime_watch`、`runtime_watch_match`、`runtime_asset`、`runtime_completeness`、`runtime_review`：アニメ Catalog に保存する不変計画、追跡、ローカル完全性、フロントエンドレビュー状態。

### 状態原則

AnimeMachine の状態処理は六つに整理できます。(1)論理作品と物理ディレクトリは同じではなく、分割放送、付属短編、元から未分割の一括リリースは同じ物理ターゲットを共有できます。(2)未検証マッピング、一時提案、曖昧一致はディレクトリ変更やダウンロード投入を許可しません。(3)ローカル差分比較は同一正規ターゲット内だけで行い、高速モードは正規ターゲットと正確なバイト数でスキップし、精密モードは比較基準がある場合だけ hash を計算します。(4)置換には改訂証拠、完全な一時保管、検証のすべてが必要で、失敗時は旧ファイルを保持します。(5)magnet タスクは完全な manifest を得るまでは登録だけ行い、ファイルを自動マッピングせず、ダウンロードも投入しません。(6)設定変更で無効になるのは派生順位と未実行計画だけで、検証済み作品 identity や取得元証拠は削除しません。

六つの共通目的は、状態変更を説明可能にすることです。新しい証拠で結論を変えることはできますが、一回の設定変更や曖昧一致で、すでに検証済みの事実まで消してはいけません。

### 並行処理

長時間の取り込みと走査は短いバッチコミットを使い、長いトランザクションを保持しません。Web 読み取りは独立接続で WAL を有効にします。カバーのネットワークアクセスは完全に別プロセスで動作し、Web 要求スレッドもメインプロセスの HTTP 接続プールも使いません。フロントエンド進捗は原子状態ファイルまたはバックグラウンドタスク表から取得します。時間のかかる処理を分離し、その遅延を通常の閲覧や照会へ広げない構成です。
