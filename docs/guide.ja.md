# AnimeMachine 導入ガイド

AnimeMachine の導入では、最初に二つの項目を決めます。(1)AnimeMachine が管理するメディアの保存先、(2)既存の qBittorrent、Ani-RSS、Torrent プール、旧メディアライブラリを外部で使用するか、Compose にまとめて管理するかです。その他の設定は、ほぼこの二つから決まります。

初回起動前に最低限必要なのはアニメコレクション用ライブラリだけです。Torrent プールと外部読み取り専用ライブラリは空でもよく、qBittorrent と Ani-RSS も AnimeMachine 起動の前提ではありません。後から接続しても Catalog を作り直す必要はありません。

## パスの意味

| 名称 | 権限 | 用途 | 推奨設定 |
|---|---|---|---|
| アニメライブラリ | 読み書き | AnimeMachine が管理するメディア、プレースホルダー、字幕、ディレクトリ構造を保存 | ローカルディスク、NAS 共有、またはコンテナ `/Library` |
| Torrent プール | AnimeMachine は読み取り専用 | ユーザーまたは任意の Torrent Collector が `.torrent` を置くディレクトリ。サブディレクトリや無関係なファイルも許可 | 独立ディレクトリまたはコンテナ `/Torrents` |
| 外部読み取り専用メディアライブラリ | 読み取り専用 | 既存メディアを移動・改名・削除せずマッピング | ani-rss または別のメディアディレクトリ；コンテナ `/External` |
| Ani-RSS メディアディレクトリ | 読み取り専用 | Ani-RSS がダウンロード済みの内容を作品ページとプレイリストへマッピング | コンテナ `/Media` |
| 状態ディレクトリ | 読み書き | SQLite、Archive、カバー、字幕、計画、操作履歴を保存 | ローカル SSD；コンテナ `/Data` |
| 設定ディレクトリ | 読み書き | `config.json`、証明書、コンポーネント設定を保存 | コンテナ `/Config` |

混同しやすいのは「ホストのパス」「AnimeMachine から見えるパス」「qBittorrent から見えるパス」の違いです。ローカル実行では同じことが多い一方、Docker や別ホスト構成では完全に異なる場合があります。AnimeMachine が必要とするのは最終的なマッピングが実在してアクセスできることだけで、各プロセスが同じ文字列のパスを使う必要はありません。

Windows のローカル実行では `D:\Anime` や `\\nas\anime` のようなドライブパス/UNC を直接指定できます。UNC へアクセスするのは AnimeMachine を実行する Windows アカウントなので、そのアカウントに共有先の読み書き権限が必要です。マップドドライブは現在のログオンセッションに属するため、常駐サービスの唯一の前提には向きません。同じアカウントでテストファイルを作成・改名・削除し、権限を確認してください。

Docker 内の `/Library`、`/Torrents` などは固定されたコンテナ内パスで、ユーザーはホストの実ディレクトリをそこへ割り当てます。外部 qBittorrent には別途「qBittorrent 自身から見えるライブラリパス」が必要で、`/Anime`、`/downloads/anime`、UNC などになり、AnimeMachine の `/Library` と同じである必要はありません。Windows Docker Desktop で UNC を bind source に直接使うより、ホスト OS が先に SMB/NFS をマウントし、そのローカルマウントポイントを Docker へ渡す方が安定します。Linux、macOS、fnOS でも同じ方式を推奨します。

![接続とパス設定](images/settings-connections.png)

*「設定 → 接続」：ライブラリ、Torrent Pool、外部メディア、qBittorrent、Ani-RSS のパスと接続状態をまとめて確認します。*

Ani-RSS 接続に必要な API key は、Ani-RSS の「ログイン設定」画面で確認できます。

## ローカル導入

### Windows 10/11

Windows のローカル実行は次の順序が分かりやすいです。(1)ソースモードは Python 3.11 以降を先にインストールします。公式 Windows Release は固定の Python 3.14 ランタイムを同梱するため別途 Python は不要で、ルートの `BUILD-INFO.json` からバージョン、コミット、ビルド環境を確認できます。(2)ソースモードは `scripts\windows\AnimeMachine.cmd`、Release は展開後にルートの `AnimeMachine.cmd` を実行します。(3)初回起動時にローカル環境ファイルと初期管理者資格情報を作成し、コンソールに初期ログイン情報と保存場所を表示します。資格情報ファイルは残りますが、以後の起動で新しいパスワードを毎回生成することはありません。(4)`http://127.0.0.1:8877` を開き、「設定 → 接続」でアニメライブラリ、Torrent プール、必要な外部コンポーネントを設定します。(5)ソースモードの状態は既定で `.local/state`、Release は `data/state` に保存され、再起動後も既存の Catalog、キャッシュ、履歴を使用します。

初回起動前にパスを準備する場合は、`deploy/local/.env.local.example` を `.local/.env.local` にコピーし、必要な項目だけコメント解除します。Release ではルートの `.env.local` を使用します。NAS のユーザー名やパスワードを AnimeMachine に長期保存して一手順減らすより、Windows の実行アカウント自体に共有権限を与える方を推奨します。

### Linux/macOS

ソースモードでは Linux が `scripts/unix/AnimeMachine-Linux.sh`、macOS が `scripts/unix/AnimeMachine-macOS.command` を実行します。初回起動時に `.local/venv` へ隔離環境を作成し、Python 3.11 以降が必要です。Release は展開後にルートの対応スクリプトを使用します。各 Release は Windows、Linux、macOS の入口を保持しますが、ビルド元と異なる OS で実行する場合はシステム側に Python 3.11+ が必要で、初回起動時にその環境向けの依存関係を取得する場合があります。

展開ツールが Unix の実行権限を保持しなかった場合は、先に `chmod +x AnimeMachine.sh AnimeMachine-Linux.sh AnimeMachine-macOS.command` を実行します。macOS から NAS を使う場合は Finder で SMB をマウントして `/Volumes/共有名/...` を指定し、Linux では OS 側で `/mnt` または `/srv` に SMB/NFS をマウントするのが適切です。AnimeMachine は通常のファイルパスだけを扱い、認証、切断後の再接続、ネットワークファイルシステムの挙動は OS に任せられます。

## Docker Compose

Docker 導入には Docker Engine 24+ と Docker Compose 2.20.3+ が必要です。AnimeMachine が qBittorrent を直接管理する場合、対象 qBittorrent は 5.2.0 以降が必要です。利用する構成ディレクトリで `.env.example` を `.env` にコピーし、少なくともパス、AnimeMachine 管理者パスワード、外部サービスのシークレットを確認します。内蔵 qBittorrent または Ani-RSS を使う場合は、リポジトリの `Initialize-AnimeMachine` スクリプトで AnimeMachine、qBittorrent、Ani-RSS の資格情報を生成し、一度だけまとめて表示できます。

設定後は次を実行します。

```bash
docker compose up -d
docker compose logs -f animemachine
```

通常は `.env` を `compose.yaml` と同じディレクトリへ置くのが最も安全です。自動化環境の都合で別の場所に環境ファイルを置き、`--env-file` で Compose を起動する場合は、`ANM_ENV_FILE` も同じファイルの絶対パスへ設定してください。Compose とサービスコンテナが異なる設定を読むと、変数値とサービス動作にずれが生じます。

fnOS を例にすると、Compose の初回起動時に Bangumi Archive の基礎パッケージをダウンロードします。`[sync] Complete` が表示されると Catalog を利用でき、カバー画像の事前取得は引き続きバックグラウンドで進みます。`[images] preload complete` は直近 6 か月分のカバー事前取得が完了した状態です。

### 四つの構成

| ディレクトリ | コンポーネント | Torrent Pool の供給元 | 推奨用途 |
|---|---|---|---|
| `01-animemachine-standalone` | AnimeMachine、外部 Ani-RSS は任意 | ユーザー管理または空 | Catalog、ディレクトリ、外部メディア、Torrent Pool を単独で管理し、Ani-RSS 未設定でも利用可能 |
| `02-animemachine-external-qbt` | AnimeMachine + 外部 qBittorrent、外部 Ani-RSS は任意 | ユーザー管理ディレクトリ | 手動コレクション。Torrent Pool のリソースを照合して外部 qBittorrent へ送る |
| `03-animemachine-managed-qbt` | AnimeMachine + Torrent Collector + 内蔵 qBittorrent、外部 Ani-RSS は任意 | Collector がリソースを収集 | 自動コレクション。Collector がリソースを収集し、内蔵 qBittorrent がコレクションを維持 |
| `04-full-stack` | AnimeMachine + Torrent Collector + 内蔵 qBittorrent + 内蔵 Ani-RSS | Collector が一括リリースを収集 | 全自動コレクション/購読。すべてのコンポーネントを一つの Compose プロジェクトで管理 |

四つの構成は独立して利用でき、最初の三構成では Ani-RSS が任意です。すでに安定した qBittorrent がある環境なら 02 が合いやすく、AnimeMachine とダウンロード経路をまとめて NAS へ移す場合は 03 または 04 を検討します。

03、04 は `deploy/compose/torrent-collector.yaml` の共有サービス定義を読み込み、Release ではこのファイルを構成の `compose.yaml` と一緒に提供します。Torrent Collector は AnimeMachine イメージ内の `torrent-collector` コマンドで動作し、ホストの Torrent Pool には書き込みできますが、AnimeMachine の `/Torrents` は引き続き読み取り専用です。Collector はタイトル、Torrent manifest、ローカル Catalog の証拠から `accept / reject / defer` を判定し、Torrent Pool に入るのは `accept` だけです。証拠不足のものは固定話数で完全と推測せず、未確定のまま保持します。既存 Pool の監査は既定でレポートのみです。明確に拒否されたファイルを隔離する場合は明示的に有効化し、隔離先は Torrent Pool の外に置きます。単話・単巻の継続追従は Ani-RSS に任せる方が適しています。

通常の `.env` には日常的に変更する項目だけを残しています。プロキシ、ポーリング間隔、履歴バックフィルのバッチ、最大再試行回数、監査モード、Collector 独立状態ディレクトリなどは `deploy/compose/torrent-collector.advanced.env.example` にまとめています。必要な項目だけ `.env` へ追加し、プロキシは既定で無効です。

### fnOS / NAS

fnOS などの NAS では、Docker プロジェクト内に `config`、`data`、`imports`、`torrents`、`library`、`external` の六種類を用意し、I/O 特性で配置を分けると扱いやすくなります。(1)`config` と `data` は SSD、(2)`library` は大容量メディアプール、(3)`torrents` は既存 Torrent Pool に割り当て、AnimeMachine 側は読み取り専用、(4)`external` は ani-rss や旧メディアへ割り当てて同じく読み取り専用、(5)`.env` には `/vol1/1000/docker/animemachine/data` のような NAS 上の実際の絶対パスを指定、(6)コンテナの `PUID/PGID` に `config`、`data`、`library` の書き込み権限を与えます。

導入後に「Web は開くがファイルを走査できない」「読み取りはできるがディレクトリを作れない」といった症状が出たら、AnimeMachine の内部パスを変える前にホストのマウントと `PUID/PGID` を確認してください。コンテナ内パスはマッピング結果にすぎず、ホスト側権限の方が典型的な原因です。

### 実行環境とストレージの分離

AnimeMachine を小型ホストや仮想マシンで動かし、メディアだけ別 NAS に置くこともできます。推奨経路は、NAS が SMB/NFS を提供 → AnimeMachine のホスト OS がマウント → Compose にはローカルマウントポイントだけを渡す、という形です。AnimeMachine は NAS の資格情報を長期保持する必要がなく、ネットワークファイルシステムの再接続も OS に任せられます。

データベース、Archive、カバーキャッシュは可能なら実行ホストの SSD に残し、大容量メディアと Torrent Pool だけをネットワークストレージに置きます。建庫、フィルタ、関係図は多数の小さなレコードを頻繁に読む一方、容量を消費するのは動画ファイルです。この二つの I/O を分ける方が、状態ディレクトリ全体を NAS に置くより安定しやすくなります。

## ネットワークと基礎データ

AnimeMachine のネットワーク層は公式ソース、ユーザー設定ミラー、直結から利用可能な経路を選び、Archive のサイズと SHA-256 を検証します。プロキシ設定は各要求ごとに動的に読み取るため、サービス稼働中にシステム/環境プロキシを切り替えても、以後の要求は再起動なしで新しい経路を利用できます。ループバックとプライベートネットワークは直結を維持し、ローカル qBittorrent、Ani-RSS、NAS へのアクセスを不要にプロキシへ回しません。

底包を手動で用意する場合は、公式 `dump-*.zip` を `/Imports`、ローカル Release では `imports` ディレクトリへ置いてから起動・取り込みします。企業 HTTPS ゲートウェイが独自 CA を使う場合は PEM CA を設定ディレクトリへ置き、`ANM_CA_BUNDLE` を指定します。証明書検証の失敗は信頼チェーンが不足しているという意味なので、TLS 検証を無効にするのではなく CA を追加するのが正しい対応です。

## 更新とバックアップ

更新とバックアップは四点で整理できます。(1)ソース更新後は起動スクリプトを再実行し、隔離環境を現在のプロジェクトに合わせて再インストールする、(2)Docker は `docker compose pull && docker compose up -d` で更新する、(3)状態ディレクトリと設定ディレクトリをバックアップすればデータベース、カバー、字幕、計画、設定を保存でき、メディアは従来のストレージ方針で別途バックアップする、(4)二つの AnimeMachine インスタンスから同じ状態ディレクトリへ同時書き込みしない、です。

別マシンへ移行する場合は、まず状態ディレクトリと設定ディレクトリを丸ごとコピーし、元のメディアパスまたは等価なマッピングを復元します。SQLite だけをコピーしても起動できる場合はありますが、キャッシュ、計画、履歴の一部を失うため推奨しません。

## 利用ガイド

### 初回カタログ構築

初回利用時にすべての自動化を同時に有効化する必要はありません。安定した順序は、(1)ログイン後に「設定 → 接続」でアニメライブラリ、Torrent Pool、任意の外部ライブラリへのアクセス状態を確認、(2)「一般」でアニメ底包を確認・更新し、Archive をバックグラウンドで段階的に取り込み、右上の状態表示で実際の段階と進捗を確認、完全な Catalog が検証後に公開されるまで待つ、(3)Torrent Pool は設定周期で増分走査し、完了済みバッチからすぐ検索でき、候補が見つからない作品は詳細ページから個別検索、(4)大量の旧メディアがある場合は自動ダウンロード前にローカルリソース検証を実行、です。

ローカル検証には二段階あります。高速モードは主に正規ターゲット、ファイル分布、正確なバイト数を比較し、日常走査向けです。ハッシュ検証は比較基準が存在し、ユーザーが精密検証を明示的に有効化した場合に使います。必要な場所だけ証拠強度を高め、全動画に対する SHA-256 の反復計算を避けます。

### 選択とダウンロード

初回利用時、ホームの月フィルタは現在月とその前五か月を対象にします。たとえば 2026 年 8 月なら 2026-03～2026-08 です。その後のフィルタ変更はブラウザのローカル状態に保存されます。既定では 1 ページ 12 作品です。テーマは OS 設定に追従し、言語切替の横から暗色/明色を手動選択することもできます。

リソース選択は自動と手動を併用できます。(1)作品を選択すると、現在の方針に従って完全性と優先度の適切な案を探します。(2)手動介入が必要なら、作品詳細から特定の一括リリース、巻まとめ、複数話、単話プランを選べます。自動選択は即時ダウンロードではなく、現在の証拠から候補を作る処理です。

「ダウンロード開始」を押すと、まず不変のダウンロード計画を生成します。計画にはターゲットディレクトリ、推定容量、追加/スキップ/一時保管して置換するファイル、qBittorrent と Ani-RSS のどちらへ渡すかが表示されます。qBittorrent への投入は既定で停止状態のままで、ユーザーが自動開始を明示した場合だけ直ちに開始します。

リソース方針は完全な一括リリースを優先し、その後に単話/単巻の組み合わせを検討します。組み合わせ案は実際のカバー範囲で判断し、長期間更新が止まっているリリースグループは優先度を下げます。既存ローカルファイルは差分計画で扱い、正規ターゲットとバイト数が完全一致すれば既定でスキップ、不足分だけ補完、信頼できる改訂証拠がある旧ファイルは先に一時保管し、重複でない既存ファイルは残します。

### Ani-RSS

Ani-RSS 接続後は三つのモードがあります。(1)優先：ローカルに完全な合集がない場合は Ani-RSS を優先、(2)フォールバック：ローカルに利用可能な案がまったくない場合のみ Ani-RSS を利用、(3)手動：ユーザーが「Ani-RSS リソース検索」を押した場合だけアクセス、です。遠端が一時的に利用不能でもユーザーが選んだ長期モード自体は変更せず、復旧後も元の設定で動作します。

Ani-RSS 管理メディアは AnimeMachine では常に外部読み取り専用ソースとして扱い、直接移動や改名をしません。既定では 30 分ごとに Ani-RSS の購読状態を同期し、設定された Ani-RSS メディアディレクトリを走査します。放送中作品で後からダウンロード完了した話数も、次の同期で再生可能範囲へ入ります。同一作品に複数の Ani-RSS 購読がある場合は遠端 ID ごとに独立保持し、互いに上書きしません。

作品詳細からダウンロード済み内容を持つ Ani-RSS 購読を削除できますが、これは明示的な遠端書き込み操作です。UI が再確認した後、Ani-RSS HTTP API で購読とファイルの削除を要求し、遠端一覧を再同期して結果を確認します。「外部読み取り専用」とは AnimeMachine がマッピングされたメディアディレクトリを直接変更しないという意味で、ユーザーが明示的に確認した Ani-RSS API 削除まで禁止する意味ではありません。

### 再生

ライブラリ一覧で具体的なメディアを選んでから、「コピー」「プレイリストをダウンロード」「VLC で開く」「PotPlayer で開く」を使用します。生成する M3U は本編だけを含み、話数順に並びます。同じ話数に複数のメディアがある場合、標準プレイリストでは一つだけを選び、バイト数まで同じ複製は除外します。特典や残りの複製はライブラリ記録に残ります。第 N 話から再生しても前の項目はプレイリストに残り、プレイヤーの開始位置だけを選択した項目へ移します。

ローカル実行なら通常はファイルパスをそのままプレイヤーへ渡せますが、Docker や遠隔導入ではそうとは限りません。コンテナ内 `/Library` はユーザー PC から見えないため、「設定 → 外部プレイヤー引き渡し」でクライアントから到達できる HTTP アドレス、またはサーバーパスからクライアントパスへの変換を設定します。たとえばサーバー `/Library` を Windows の `\\nas\anime`、macOS の `/Volumes/anime` へ割り当てられます。再生端末から実際にアクセスできるパスでなければ、ローカルプレイヤー直接起動に意味はありません。

### 字幕

放送中リリースでは候補選択時にユーザー言語の字幕を優先します。アーカイブ向けは (1)内蔵字幕、(2)同名外部字幕、(3)ローカル字幕アーカイブ、(4)ユーザー設定字幕サービス、の順で確認します。新しい字幕を選ぶ場合、旧字幕はまず状態ディレクトリへバックアップします。外部読み取り専用ライブラリのメディアであれば、新字幕も AnimeMachine の状態ディレクトリへ保存し、元メディアのパスへ書き戻しません。

つまり字幕処理とメディア所有権は別です。AnimeMachine は読み取り専用動画に再生用字幕を関連付けられますが、そのことによって外部メディアライブラリを変更する権限を得るわけではありません。

### ディレクトリと履歴

単独作品ディレクトリは既定で `『YYYY_MM』『作品原名』`、シリーズディレクトリは `『開始－終了』『「シリーズ根名」シリーズ』` を使い、シリーズ内の子作品は各自の初回放送月で命名します。同一公式クールの分割放送は最初のクールへ統合し、明確な本編所属があるミニアニメ、Picture Drama などは付属物として扱い、別のプレースホルダーディレクトリを作りません。

ディレクトリ処理は、作品 identity と既存パスの確定から始めます。AnimeMachine がユーザー所有ファイルを移動・改名・置換する前に、「設定 → 履歴」へ変更を記録します。AnimeMachine 自身が作る通常ディレクトリは重複記録しません。ディレクトリ占有、合集境界、作品 identity に自動確定できない衝突が残る場合、ダウンロード計画は十分な証拠が得られるまでレビュー状態で停止します。
