# AnimeMachine 導入ガイド

AnimeMachine の導入では、最初に二つの項目を決めます。(1)AnimeMachine が管理するメディアの保存先、(2)既存の qBittorrent、Ani-RSS、Torrent プール、旧メディアライブラリを外部で使用するか、Compose にまとめて管理するかです。その他の設定は、ほぼこの二つから決まります。

初回起動前に最低限必要なのはアニメコレクション用ライブラリだけです。Torrent プールと外部読み取り専用ライブラリは空でもよく、qBittorrent と Ani-RSS も AnimeMachine 起動の前提ではありません。後から接続しても Catalog を作り直す必要はありません。

## パスの意味

| 名称 | 権限 | 用途 | 推奨設定 |
|---|---|---|---|
| アニメライブラリ | 読み書き | AnimeMachine が管理するメディア、プレースホルダー、字幕、ディレクトリ構造を保存 | ローカルディスク、NAS 共有、またはコンテナ `/Library` |
| Torrent プール | AnimeMachine は読み取り専用 | ユーザーまたは任意の Torrent Collector が `.torrent` を置くディレクトリ。サブディレクトリや無関係なファイルも許可 | 独立ディレクトリまたはコンテナ `/Torrents` |
| 外部読み取り専用メディアライブラリ | 読み取り専用 | 既存メディアを移動・改名・削除せずマッピング | ani-rss または別のメディアディレクトリ；コンテナ `/External` |
| Ani-RSS メディアディレクトリ | 読み取り専用 | Ani-RSS がダウンロード済みの内容を作品ページとプレイリストへマッピング | コンテナ `/Media` |
| 状態ディレクトリ | 読み書き | SQLite、Archive、カバー、字幕、計画、操作履歴を保存 | ローカル SSD；コンテナ `/Data` |
| 設定ディレクトリ | 読み書き | `config.json`、証明書、コンポーネント設定を保存 | コンテナ `/Config` |

混同しやすいのは「ホストのパス」「AnimeMachine から見えるパス」「qBittorrent から見えるパス」の違いです。ローカル実行では同じことが多い一方、Docker や別ホスト構成では完全に異なる場合があります。AnimeMachine が必要とするのは最終的なマッピングが実在してアクセスできることだけで、各プロセスが同じ文字列のパスを使う必要はありません。

Windows のローカル実行では `D:\Anime` や `\\nas\anime` のようなドライブパス/UNC を直接指定できます。UNC へアクセスするのは AnimeMachine を実行する Windows アカウントなので、そのアカウントに共有先の読み書き権限が必要です。マップドドライブは現在のログオンセッションに属するため、常駐サービスの唯一の前提には向きません。同じアカウントでテストファイルを作成・改名・削除し、権限を確認してください。

Docker 内の `/Library`、`/Torrents` などは固定されたコンテナ内パスで、ユーザーはホストの実ディレクトリをそこへ割り当てます。外部 qBittorrent には別途「qBittorrent 自身から見えるライブラリパス」が必要で、`/Anime`、`/downloads/anime`、UNC などになり、AnimeMachine の `/Library` と同じである必要はありません。Windows Docker Desktop で UNC を bind source に直接使うより、ホスト OS が先に SMB/NFS をマウントし、そのローカルマウントポイントを Docker へ渡す方が安定します。Linux、macOS、fnOS でも同じ方式を推奨します。

![接続とパス設定](images/settings-connections.png)

*「設定 → 接続」：ライブラリ、Torrent Pool、外部メディア、qBittorrent、Ani-RSS のパスと接続状態をまとめて確認します。*

Ani-RSS 接続に必要な API key は、Ani-RSS の「ログイン設定」画面で確認できます。0.2.0 以降、「設定 → 接続」で保存した qBittorrent、Ani-RSS、ASSRT、OpenSubtitles の API 資格情報は、状態ディレクトリ配下のアクセス制限付き `credentials/` ファイルへ保存され、再起動後も有効です。値は `config.json`、ブラウザのローカル保存領域、ログ、API 応答へ書き出しません。同じ資格情報がデプロイ環境変数または Docker Secret で提供されている場合はデプロイ値を優先し、Web 保存値で実行中のデプロイ資格情報を上書きしません。「接続テスト」は入力欄にある qBittorrent/Ani-RSS API Key をそのテストだけで一時使用し、保存も消去もしません。新しい資格情報を制限付きストレージへ書き込むのは「設定を保存」を実行したときだけです。保存時は、完全な設定と今回入力した複数資格情報をサーバー側で一つのトランザクションとして扱い、すべての設定検証を先に完了してからコミットします。永続化のどこかで失敗した場合はその保存をロールバックします。完全オフラインが既に確定していても、管理者が実行した「接続テスト」は明示的な復旧プローブとして対象へ接続を試み、ローカル/LAN として認識された対象は引き続き直結します。

## ローカル導入

### Windows 10/11

Windows のローカル実行は次の順序が分かりやすいです。(1)ソースモードは Python 3.11 以降を先にインストールします。公式 Windows Release は固定の Python 3.14 ランタイムを同梱するため別途 Python は不要で、ルートの `BUILD-INFO.json` からバージョン、コミット、ビルド環境を確認できます。(2)ソースモードは `scripts\windows\AnimeMachine.cmd`、Release は展開後にルートの `AnimeMachine.cmd` を実行します。(3)`.env.local` を作成しなくても直接起動でき、既定では `0.0.0.0:8787` を待ち受けます。そのため同じ PC は `http://127.0.0.1:8787`、LAN 内の別端末は `http://<AnimeMachineホストIP>:8787` を利用できます。外部から到達可能なバインドでは認証が自動的に有効になり、管理者パスワード未指定なら初回起動時にランダム生成して権限制限された資格情報ファイルへ保存し、ユーザー名、パスワード、保存場所をコンソールへ表示します。自動生成された初期管理者が有効な間は、後続の起動でも同じログイン情報を再表示します。(4)ログイン後に「設定 → 接続」でライブラリ、Torrent プール、必要な外部コンポーネントを追加します。(5)ソースモードの状態は既定で `.local/state`、Release は `data/state` に保存され、再起動後も既存の Catalog、キャッシュ、履歴を使用します。

初回起動前にパスを準備する場合は、`deploy/local/.env.local.example` を `.local/.env.local` にコピーし、必要な項目だけコメント解除します。Release ではルートの `.env.local` を使用します。NAS のユーザー名やパスワードを AnimeMachine に長期保存して一手順減らすより、Windows の実行アカウント自体に共有権限を与える方を推奨します。

### Linux/macOS

ソースモードでは Linux が `scripts/unix/AnimeMachine-Linux.sh`、macOS が `scripts/unix/AnimeMachine-macOS.command` を実行します。初回起動時に `.local/venv` へ隔離環境を作成し、Python 3.11 以降が必要です。Release は展開後にルートの対応スクリプトを使用します。各 Release は Windows、Linux、macOS の入口を保持しますが、ビルド元と異なる OS で実行する場合はシステム側に Python 3.11+ が必要で、初回起動時にその環境向けの依存関係を取得する場合があります。

展開ツールが Unix の実行権限を保持しなかった場合は、先に `chmod +x AnimeMachine.sh AnimeMachine-Linux.sh AnimeMachine-macOS.command` を実行します。macOS から NAS を使う場合は Finder で SMB をマウントして `/Volumes/共有名/...` を指定し、Linux では OS 側で `/mnt` または `/srv` に SMB/NFS をマウントするのが適切です。AnimeMachine は通常のファイルパスだけを扱い、認証、切断後の再接続、ネットワークファイルシステムの挙動は OS に任せられます。

## Docker Compose

Docker 導入には Docker Engine 24+ と Docker Compose 2.20.3+ が必要です。AnimeMachine が qBittorrent を直接管理する場合、対象 qBittorrent は 5.2.0 以降が必要です。0.2.1 の完全 Compose 構成は Ani-RSS `v3.2.28` と qBittorrent `5.2.3` を固定し、現在のアダプターはこの二つのインターフェースで検証済みです。四つの構成はいずれも `.env` を作成せず `docker compose up -d` だけで起動できます。既定では `0.0.0.0:8787` を公開し、相対ディレクトリを使い、AnimeMachine の管理者パスワードを自動生成します。`04-full-stack/compose.yaml` は自己完結した一ファイル定義で、この YAML だけを空ディレクトリへコピーしても親ディレクトリのファイルに依存しません。構成 3/4 では内蔵 qBittorrent/Ani-RSS のランダム API 資格情報も各コンポーネントの設定ディレクトリへ生成して永続再利用します。AnimeMachine は対応する bootstrap の正常完了と管理対象サービスコンテナの起動を待ってから初回アプリプロセスを開始するため、空の設定ディレクトリで資格情報生成とアプリ起動が競合しません。構成 4 の初回起動では Ani-RSS のダウンロード先テンプレートを共有 `/Media`（ホスト既定 `./external/ani-rss`）へ向け、qBittorrent の `/downloads/incomplete` は未完了データだけに使うため、完了した Ani-RSS メディアはコンテナパスを手動調整せず AnimeMachine から直ちに検出・再生できます。Docker が初回に `root:root` で作成する空の bind ディレクトリにも対応できるよう、AnimeMachine のコンテナ入口は起動初期に必要な書き込み先だけを準備し、アプリ起動前に直ちに `PUID/PGID` へ降格します。既存メディアの内容を再帰的に所有者変更することはありません。ホストパス、固定資格情報、PUID/PGID、プロキシ、ポートを変更するときだけ `.env.example` を `.env` にコピーして編集してください。明示設定は自動生成値より優先されます。

設定後は次を実行します。

```bash
docker compose up -d
docker compose logs -f animemachine
```

カスタム設定では `.env` を `compose.yaml` と同じディレクトリへ置けば、Compose の標準補間規則で自動的に読み込まれます。自動化環境では `docker compose --env-file /path/to/custom.env up -d` を直接使え、別のサービス用 env-file 設定は不要です。Compose の `ANM_BIND_ADDRESS` はホスト側の公開アドレスだけを制御し、コンテナ内の AnimeMachine は常に `0.0.0.0:8787` を待ち受けます。既定では LAN から `http://<DockerホストIP>:8787` でアクセスでき、認証も自動的に要求されます。Web をホストのループバックだけへ公開したい場合に限り `ANM_BIND_ADDRESS=127.0.0.1` を設定してください。`ANM_WEB_PORT` はホスト側の公開ポートを指定し、コンテナ内ポートは 8787 のままです。

fnOS を例にすると、Compose の初回起動時に Bangumi Archive の基礎パッケージをダウンロードして解析します。利用開始の基準は、まとめて表示される `========== AnimeMachine access ==========` です。この時点でコア初期化と Catalog は完了し、Web サービスへ接続でき、カバー画像のバックグラウンド事前取得も開始済みです。同じブロックに、実際のネットワーク経路、Ani-RSS、qBittorrent、ストレージパス、主要画像ソースの状態を簡潔に表示します。インスタンスのランダムシードは最初の有効な Catalog 作成時に生成して永続化し、通常の再起動や Catalog 再構築では変わりません。新しいシードになるのは、ユーザーが「再ランダム」を実行した場合、またはインスタンスを再デプロイした場合だけです。カバーは現在のランダムシードで有界の先頭ページ群をページ順に完了し、次に直近 6 か月の全作品を補完し、その後は 7 か月前から月単位で古い作品へ遡ります。一枚の一時的な失敗で後続バッチを止めず、バックグラウンドで再試行します。正常な既存キャッシュは、放送 6〜2 か月前、2 か月前〜放送 1 か月後、放送 1〜2 か月後の期間だけ自動確認し、間隔はそれぞれ 72、24、72 時間です。12 時間ごとに最低優先度のスキャンが期限到達作品を選び、期間外では自動更新を停止しますが、手動の「再読み込み」は常に実行できます。`[images] preload complete` は履歴全体の走査と有限回の再試行が完了したことを示し、実際にカバーが存在しない項目や継続して到達不能な少数項目は残る場合があります。

### 四つの構成

| ディレクトリ | コンポーネント | Torrent Pool の供給元 | 推奨用途 |
|---|---|---|---|
| `01-animemachine-standalone` | AnimeMachine、外部 Ani-RSS は任意 | ユーザー管理または空 | Catalog、ディレクトリ、外部メディア、Torrent Pool を単独で管理し、Ani-RSS 未設定でも利用可能 |
| `02-animemachine-external-qbt` | AnimeMachine + 外部 qBittorrent、外部 Ani-RSS は任意 | ユーザー管理ディレクトリ | 手動コレクション。Torrent Pool のリソースを照合して外部 qBittorrent へ送る |
| `03-animemachine-managed-qbt` | AnimeMachine + Torrent Collector + 内蔵 qBittorrent、外部 Ani-RSS は任意 | Collector がリソースを収集 | 自動コレクション。Collector がリソースを収集し、内蔵 qBittorrent がコレクションを維持 |
| `04-full-stack` | AnimeMachine + Torrent Collector + 内蔵 qBittorrent + 内蔵 Ani-RSS | Collector が一括リリースを収集 | 全自動コレクション/購読。すべてのコンポーネントを一つの Compose プロジェクトで管理 |

四つの構成は独立して利用でき、最初の三構成では Ani-RSS が任意です。すでに安定した qBittorrent がある環境なら 02 が合いやすく、AnimeMachine とダウンロード経路をまとめて NAS へ移す場合は 03 または 04 を検討します。 `04-full-stack` の初回起動では、Ani-RSS のダウンロード先や自動起動など不足している既定値を補います。以後のコンテナ再作成では Compose 管理の API Key と qBittorrent 接続だけを更新し、Ani-RSS 側でユーザーが変更した自動起動やダウンロード先テンプレートなどの動作設定は上書きしません。

03 は `deploy/compose/torrent-collector.yaml` の共有サービス定義を読み込みます。04 は一ファイルのゼロ設定デプロイを成立させるため、同じ Torrent Collector サービスと名前付きボリュームを `04-full-stack/compose.yaml` へ直接内包しており、この YAML 単体でデプロイできます。Release では 03 と高度な再利用のため共有 Collector ファイルも引き続き提供します。Torrent Collector は AnimeMachine イメージ内の `torrent-collector` コマンドで動作し、ホストの Torrent Pool には書き込みできますが、AnimeMachine の `/Torrents` は引き続き読み取り専用です。Collector はタイトル、Torrent manifest、ローカル Catalog の証拠から `accept / reject / defer` を判定し、Torrent Pool に入るのは `accept` だけです。証拠不足のものは固定話数で完全と推測せず、未確定のまま保持します。既存 Pool の監査は既定でレポートのみです。明確に拒否されたファイルを隔離する場合は明示的に有効化し、隔離先は Torrent Pool の外に置きます。単話・単巻の継続追従は Ani-RSS に任せる方が適しています。

通常の `.env` には日常的に変更する項目だけを残しています。プロキシ、ポーリング間隔、履歴バックフィルのバッチ、最大再試行回数、監査モード、Collector 独立状態ディレクトリなどは `deploy/compose/torrent-collector.advanced.env.example` にまとめています。必要な項目だけ `.env` へ追加し、プロキシは既定で無効です。

### fnOS / NAS

fnOS などの NAS では、Docker プロジェクト内に `config`、`data`、`imports`、`torrents`、`library`、`external` の六種類を用意し、I/O 特性で配置を分けると扱いやすくなります。(1)`config` と `data` は SSD、(2)`library` は大容量メディアプール、(3)`torrents` は既存 Torrent Pool に割り当て、AnimeMachine 側は読み取り専用、(4)`external` は ani-rss や旧メディアへ割り当てて同じく読み取り専用、(5)`.env` には `/vol1/1000/docker/animemachine/data` のような NAS 上の実際の絶対パスを指定、(6)コンテナの `PUID/PGID` に `config`、`data`、`library` の書き込み権限を与えます。`04-full-stack` では、Ani-RSS のメディアディレクトリにも書き込み権限が必要です。

導入後に「Web は開くがファイルを走査できない」「読み取りはできるがディレクトリを作れない」といった症状が出たら、AnimeMachine の内部パスを変える前にホストのマウントと `PUID/PGID` を確認してください。コンテナ内パスはマッピング結果にすぎず、ホスト側権限の方が典型的な原因です。

### 実行環境とストレージの分離

AnimeMachine を小型ホストや仮想マシンで動かし、メディアだけ別 NAS に置くこともできます。推奨経路は、NAS が SMB/NFS を提供 → AnimeMachine のホスト OS がマウント → Compose にはローカルマウントポイントだけを渡す、という形です。AnimeMachine は NAS の資格情報を長期保持する必要がなく、ネットワークファイルシステムの再接続も OS に任せられます。

データベース、Archive、カバーキャッシュは可能なら実行ホストの SSD に残し、大容量メディアと Torrent Pool だけをネットワークストレージに置きます。建庫、フィルタ、関係図は多数の小さなレコードを頻繁に読む一方、容量を消費するのは動画ファイルです。この二つの I/O を分ける方が、状態ディレクトリ全体を NAS に置くより安定しやすくなります。

## ネットワークと基礎データ

AnimeMachine のネットワーク層は公式ソース、ユーザー設定ミラー、直結から利用可能な経路を選び、Archive のサイズと SHA-256 を検証します。Archive やアプリ更新のようにサイズとダイジェストが既知の大容量ファイルでは、再開可能な Range 分割を優先します。優先 Range 経路が実転送中に失敗し、別の確認済み経路が全体ファイル転送だけに対応している場合は自動的に全体取得へ降格し、同じ完全性検証を維持します。完全取得済みでも SHA-256 が一致しない一時ファイルは破棄し、次回再試行で破損内容を再利用しません。外部要求ごとに実際の経路を再判定し、直結、環境プロキシ、Windows システムプロキシを区別します。プロキシ構成が変わると以後の要求は新しい接続世代へ移り、以前のネットワーク経路で記録されたエンドポイント失敗状態も分離されるため、初回のプロキシなし起動からプロキシへ変更する場合、別プロキシへ切り替える場合、直結へ戻す場合のいずれも再起動は不要です。環境プロキシまたは Windows システムプロキシの URL が壊れている、ポート指定が無効、または現在の実行環境でそのプロキシ転送を生成できない場合は、その経路だけを飛ばして直結を含む後続経路を試し、遠隔要求全体を途中で中断しません。診断に表示するプロキシアドレスは脱機密化し、異常な文字列も資格情報を含む形では表示しません。ループバック、プライベートネットワークは直結を維持し、ローカル qBittorrent、Ani-RSS、NAS へのアクセスを不要にプロキシへ回しません。

ホームの第 2 状態行は、バックグラウンド画像準備、`YYYY-MM` までの履歴方向進捗、使用中の Bangumi Archive 版、Catalog 作品総数を簡潔に表示します。残り件数、ETA、現在の処理対象はホームには表示せず、詳細は「設定 → 診断」に残します。

「設定 → 一般」の先頭にある「システム状態」は、ネットワーク、Ani-RSS、qBittorrent、ストレージ、画像プリロード、再生経路を少数の「正常/警告」へ集約し、詳細は引き続き「設定 → 診断」に表示します。診断では現在の実効通信経路と、Bangumi Archive、Subject Cache、Bangumi API、各画像ソースの直近成功率、遅延、スループット、直近の失敗理由を読み取り専用で確認できます。画像ソースはさらに、直結、環境プロキシ、Windows システムプロキシごとに直近 12 時間の健全性推移を表示します。「再検出」は実際の要求と同じネットワーク層を使うため、その結果もミラーの健全性へ反映されます。ミラー順位は三種類のネットワーク環境ごとに学習し、直近の証拠を時間減衰させ、有効サンプル数から信頼度を求めます。このため、サンプルが少ないソースが一度の偶発結果だけで最上位へ移動することはありません。現在ソースには短い保持時間と最小切替利益もあり、診断画面には現在の選択、信頼度、「保持中」「候補が十分に優れる」「現在ソースがクールダウン中」などの理由を表示します。同じ画面では、直近 6 か月、履歴カタログ、失敗再試行の三段階プリロードに加え、残り見込み、直近の実処理スループットから算出した ETA、処理速度、現在の処理対象、適応型バックグラウンド並行数も確認できます。バックグラウンド処理は一時停止・再開、並行数・帯域制限が可能で、制御値と進捗は状態ディレクトリへ保存されます。実効バックグラウンド強度は、前景操作が増えた場合、画像応答が遅くなった場合、CPU 負荷が上がった場合、または直近の画像 I/O・ネットワーク信号が悪化した場合にも自動的に下がり、条件が戻れば再び上がります。前景で表示された作品を常に優先し、ブラウザはスクロール方向の次画面付近だけを限定的に先読みします。サーバー側では現在のランダムシードの先頭ページ群をページ順に処理し、次に直近 6 か月、その後は 7 か月前から月単位で履歴へ遡ります。定期画像更新は全カタログの事前取得と失敗再試行より後ろに置き、最低優先度のタスクを同時に 1 件だけ実行します。すでにバックグラウンド待ちの作品も前景で表示された時点で即座に昇格します。

底包を手動で用意する場合は、公式 `dump-*.zip` を `/Imports`、ローカル Release では `imports` ディレクトリへ置いてから起動・取り込みします。企業 HTTPS ゲートウェイが独自 CA を使う場合は PEM CA を設定ディレクトリへ置き、`ANM_CA_BUNDLE` を指定します。証明書検証の失敗は信頼チェーンが不足しているという意味なので、TLS 検証を無効にするのではなく CA を追加するのが正しい対応です。

## 0.2.1 へのアップグレード

以前のリリースから 0.2.1 へ更新するために Catalog を再構築したり、メディアディレクトリを移動したりする必要はなく、0.2.0 からの追加移行も不要です。既存のローカル/Compose 設定を引き続き基礎設定として使い、アプリ更新の定期確認は既定で無効のままです。明示的に有効化しない限り、新版が自動インストールされることはありません。0.2.1 用 Docker イメージは安定 supervisor のエントリポイントと、書き込み可能な状態ディレクトリ内のアプリ層更新領域を引き続き含みます。現在のコンテナが 0.2.0 より前で、この supervisor をまだ持たない旧イメージを使っている場合は、最初の一回だけ通常どおり 0.2.1 イメージを pull してコンテナを再作成してから、Web 経由の Docker 更新と起動失敗時ロールバックを利用してください。ポータブル版の更新 worker と Docker supervisor は再起動後、実際の待受アドレスに対してヘルスチェックを行います。LAN/IPv6 アドレスへ明示的にバインドした場合は固定の `127.0.0.1` を探査せず、`0.0.0.0`/`::` などのワイルドカード待受だけを対応するループバックへ変換します。

ネットワーク設定の移行も不要です。実行中に環境プロキシまたは Windows システムプロキシを有効化、無効化、変更すると、以後の要求で新しいネットワーク環境を再識別し、診断とソース健全性学習は経路環境ごとに分離されます。全上流が一時的に失敗しても直ちに完全オフラインにはならず、少なくとも 30 分の連続失敗観測後にリモートのバックグラウンド処理を停止し、復旧プローブと限定的な機会回復要求は維持します。更新後の環境確認は「設定 → 診断 → 再検出」を一度実行し、システム健全性サマリー、アプリ更新ソース、画像ソース状態を確認するのが最短です。

## 更新とバックアップ

更新とバックアップは四点で整理できます。(1)公式ポータブル版と新しい Docker イメージは「設定 → 更新を確認」で現在/最新バージョン、ダウンロード元、SHA-256 検証、更新結果を確認し、手動確認またはオンライン更新を実行できます。更新経路は GitHub、API、Release、内蔵プロキシを診断して健全な最速経路を永続学習し、失敗した経路はバックオフのクールダウンへ入ります。定期確認は既定で無効で、有効化すると通知のみまたは自動インストールを選択でき、既定の確認時刻は実行端末のローカル時刻 04:35 です。Docker のアプリ層更新は状態ディレクトリへ保存され、Docker Socket をマウントせず、コンテナ内の監督プロセスが再起動と失敗時のロールバックを行います。この層が置き換えるのは AnimeMachine の Python アプリケーションコードだけで、ベースイメージ、supervisor、Python/OS コンポーネント、変更された実行時依存関係は置き換えません。(2)ソース環境は従来どおりソース更新後に起動スクリプトを再実行し、これらのイメージレベル要素が変わった場合や Web 更新非対応の旧 Docker イメージから移行する場合は `docker compose pull && docker compose up -d` でイメージ全体を更新します。(3)状態ディレクトリと設定ディレクトリをバックアップすれば、データベース、カバー、字幕、計画、設定、Docker のオンライン更新層を保存でき、メディアは従来のストレージ方針で別途バックアップします。(4)二つの AnimeMachine インスタンスから同じ状態ディレクトリへ同時書き込みしないでください。

別マシンへ移行する場合は、まず状態ディレクトリと設定ディレクトリを丸ごとコピーし、元のメディアパスまたは等価なマッピングを復元します。SQLite だけをコピーしても起動できる場合はありますが、キャッシュ、計画、履歴の一部を失うため推奨しません。

## 利用ガイド

### 設定とアカウント権限

「設定」は管理者が管理し、一般、リソース優先度、リソースグループ、接続、診断、購読、ユーザー、ログ、履歴、更新確認、AnimeMachine について、の各画面を含みます。一般では Archive/メタデータ保守と UI 方針、リソース優先度とリソースグループでは候補順位とリリースグループ規則を調整します。接続では管理ライブラリ、Torrent Pool、qBittorrent、Ani-RSS、外部読み取り専用メディア、字幕サービス、外部プレイヤー連携、メタデータネットワークの接続先をまとめて設定し、外部プレイヤー連携はサーバーパスからクライアントパスまたは HTTP 再生 URL への対応を担当します。診断はネットワーク、ストレージ、画像事前読み込み、再生経路、システム健全性を集約し、ネットワーク再検査も実行できます。購読、ユーザー、ログ、履歴は後続リリース/Ani-RSS 購読、アカウント管理、障害調査、記録済みディレクトリ変更の確認/復元に使用し、更新確認ではアプリ更新、AnimeMachine についてではバージョンとプロジェクトリンクを確認できます。

「設定 → 一般 → 許可するリソース種別」には地域の複数選択もあり、中国、日本、韓国、米国、欧州、その他を既定ですべて有効にします。中国には中国本土、香港、マカオ、台湾、欧州には英国・ロシアを含むすべての欧州国を含め、地域が空欄または証拠不足の場合は「その他」です。共同制作は、少なくとも一つの地域が許可されていれば候補に残ります。中国語 UI は中・日・韓・米・欧・その他、英語 UI は米・欧・中・日・韓・その他、日本語 UI は日・韓・中・米・欧・その他の順です。この方針はまず Catalog の表示可否に適用し、同時に Torrent と Ani-RSS のソース可用性も制御します。地域を無効にすると、その地域の作品は Catalog のカード結果から除外され、対応する Torrent/Ani-RSS ソースでも絞り込み対象になりませんが、既存ローカルメディアや遠隔購読レコードは削除しません。

通常の設定は Web UI から変更することを推奨します。自動化された配備や UI に直接表示されない高度な項目を使う場合、`config/config.example.json` が永続設定の完全なテンプレート、`config/config.schema.json` が対応するフィールド、型、列挙値、境界の仕様です。実際の設定はソース/ポータブル版ではルートの `config.json`、Docker では `/Config/config.json` が既定で、`ANM_CONFIG_PATH` で変更できます。`config.json` を直接編集するときは Web 保存との競合を避けるため AnimeMachine を停止し、次回起動時の内蔵検証で不正値を検出してください。配備レベルの環境変数は `deploy/local/.env.local.example` と各 Compose ディレクトリの `.env.example` を基準とし、パスワード、Token、プロキシ資格情報を公開テンプレートへ書き戻さないでください。

認証を有効にした場合のロールは 2 種類です。管理者は設定変更、Archive/メタデータ保守、Library Audit とネットワーク再検査、画像事前読み込み制御、ユーザー管理、アプリ更新を実行でき、ランダム並び替え時には「再シャッフル」でインスタンス全体のランダムシードを再生成できます。一般ユーザーは Catalog の閲覧、作品/リソース確認、個別作品画像の更新、ダウンロード計画の生成・送信、許可された再生/購読操作を利用できますが、管理者設定や上記の全体保守 API は利用できません。初回ログイン後は新しい管理者を作成してから初期 `admin` を無効化することを推奨します。現在ログイン中の自分自身は無効化できません。認証を無効にした単一ユーザーのローカルモードは管理者相当で動作しますが、Host/同一オリジンおよび書き込み要求の保護は維持されます。

### 初回カタログ構築

初回利用時にすべての自動化を同時に有効化する必要はありません。安定した順序は、(1)ログイン後に「設定 → 接続」でアニメライブラリ、Torrent Pool、任意の外部ライブラリへのアクセス状態を確認、(2)「一般」でアニメ底包を確認・更新し、Archive をバックグラウンドで段階的に取り込み、上部の状態行で Catalog 状態、画像の履歴方向への進捗、底包情報を確認し、完全な Catalog が検証後に公開されるまで待つ、(3)Torrent Pool は設定周期で増分走査し、完了済みバッチからすぐ検索でき、候補が見つからない作品は詳細ページから個別検索、(4)大量の旧メディアがある場合は自動ダウンロード前にローカルリソース検証を実行、です。

ローカル検証には二段階あります。高速モードは主に正規ターゲット、ファイル分布、正確なバイト数を比較し、日常走査向けです。ハッシュ検証は比較基準が存在し、ユーザーが精密検証を明示的に有効化した場合に使います。必要な場所だけ証拠強度を高め、全動画に対する SHA-256 の反復計算を避けます。

### 選択とダウンロード

初回利用時、ホームの月フィルタは現在月とその前五か月を対象にします。たとえば 2026 年 8 月なら 2026-03～2026-08 です。その後のフィルタ変更はブラウザのローカル状態に保存されます。開始月と終了月が同一年の場合、「年」は表示同期としてその年を示して「季」を有効にします。明示的な月範囲があるとサーバーは重複する年条件を無視するため、検索結果は変わりません。年をまたぐ冬も認識し、「2026 年 + 冬（1月前後）」は 2025-12～2026-02 を表し、「年」は 1 月を含む 2026 年を基準にします。「季」の 5 項目は、すべて、冬（1月前後）、春（4月前後）、夏（7月前後）、秋（10月前後）で、四季はそれぞれ 12～2、3～5、6～8、9～11 月です。季を選択したまま「年」を変えると正しい季節範囲を再計算し、同一年のカスタム範囲で「年」だけを変える場合は月番号を維持します。旧版でブラウザに保存された季節フィルタも復元時に新定義へ正規化されます。明示的な年を持たず「前年 12 月～当年 2 月」だけを保存した旧冬季状態も、常に 1 月を含む年を基準に復元され、冬季全体が 1 年ずれることはありません。既定では 1 ページ 12 作品です。テーマは OS 設定に追従し、言語切替の横から暗色/明色を手動選択することもできます。

「未来／日付不明」は固定の開始月・終了月を持たない独立フィルタ状態なので、ブラウザ状態の復元時に空の月範囲から逆推定して選択を消しません。また、日本以外の作品で Archive の主タイトルを常に日本語とみなす前提を廃止し、主タイトルの文字種、国・地域、タグ、制作会社の証拠から原題言語を保持します。明示された日本語、英語などの別名は独立して保存し、対応する UI 言語で利用できます。原作関係のタイトルは「原作名」として別に表示し、特定作品だけを対象に原作名や日本語版タイトルをアニメ原題へ固定することはありません。

リソース選択は自動と手動を併用できます。(1)作品を選択すると、現在の方針に従って完全性と優先度の適切な案を探します。(2)手動介入が必要なら、作品詳細から特定の一括リリース、巻まとめ、複数話、単話プランを選べます。自動選択は即時ダウンロードではなく、現在の証拠から候補を作る処理です。

「ダウンロード開始」を押すと、まず不変のダウンロード計画を生成します。計画にはターゲットディレクトリ、推定容量、追加/スキップ/一時保管して置換するファイル、qBittorrent と Ani-RSS のどちらへ渡すかが表示されます。AnimeMachine は qBittorrent のタスクを常に停止状態で投入するため、計画確認が即時ダウンロードを意味することはありません。計画を確認した後、ユーザーが qBittorrent 側で開始します。

リソース方針は完全な一括リリースを優先し、その後に単話/単巻の組み合わせを検討します。組み合わせ案は実際のカバー範囲で判断し、長期間更新が止まっているリリースグループは優先度を下げます。既存ローカルファイルは差分計画で扱い、正規ターゲットとバイト数が完全一致すれば既定でスキップ、不足分だけ補完、信頼できる改訂証拠がある旧ファイルは先に一時保管し、重複でない既存ファイルは残します。

### 閲覧・フィルタ・作品関係図

ホーム画面ではカード/表形式、月と状態のフィルタ、検索、並び替え、1 ページ件数、ランダム順を利用でき、フィルタと表示設定はブラウザのローカル状態へ保存されます。「利用可能なソース」は Torrent ソース、Ani-RSS ソース、利用可能なソースなしに分かれ、前二者は同じ作品で同時に成立でき、両方が存在しない場合だけ「なし」に一致します。「ライブラリ状態」は独立かつ排他的な「ローカル入庫 / 外部読み取り専用 / ダウンロード送信済み / 未入庫」の 4 分類です。ローカル媒体または qBittorrent 完了後に管理対象へ入った媒体は「ローカル入庫」、マッピング済み読み取り専用媒体は「外部読み取り専用」です。Ani-RSS HTTP API で再生可能な媒体は、現在の資格情報が存在し接続正常と確認されている間だけ「外部読み取り専用」です。API 切断、資格情報の削除・変更、または接続先変更後の再検証待ちでは、過去の API メディアスナップショットは復旧用に保持しますが、現在再生可能な外部媒体としては表示せず、独立してマウントした読み取り専用ディレクトリは API 健全性の影響を受けません。qBittorrent へ送信済みで未完了の待機・ダウンロード中・停止/一時停止タスクは「ダウンロード送信済み」、それ以外は「未入庫」です。Ani-RSS 購読そのものは「ダウンロード送信済み」にはなりません。「フォルダー要確認」などの細粒度状態はディレクトリ検証、完全性、ダウンロード安全判定のため内部に残りますが、ライブラリ状態のフィルタ分類にはなりません。設定で地域を無効にすると、その地域の作品は「利用可能なソースなし」へ再分類されず Catalog カード結果から除外されます。共同制作は少なくとも一地域が許可されていれば表示を続けます。ランダム順はインスタンス全体で永続化されたシードを使うため、ページ再読み込みやサービス再起動では順序が変わらず、管理者が「再シャッフル」を実行した場合だけ新しいシードを生成します。作品詳細の関係図では前作、続編、総集編、番外、派生、別解釈/別映像化、シリーズ横断関係を確認でき、ノードから関連作品へ移動できます。複雑な図は全画面表示、関係種別の一部非表示、SVG/PNG 書き出しに対応します。カード、詳細、関係図のノード、後続リリース監視、画像プリロード診断の現在作品名は同じ現在の UI 言語規則でタイトルを選びます。0.2.1 へ更新すると既存 Catalog に保存済みの英語別名を自動再評価し、CJK・キリル・ギリシャ・アラビア文字など、ラテン文字以外のアルファベット文字を含む別名が英語として誤分類されていれば除外して、欠けている、または品質の低い検証可能な英語表示名を補正します。上流に英語名が存在しない場合、英語 UI は可読性のため作品の原題へ一時的にフォールバックしますが、その原題を英語名として保存・分類しません。検証済み英語名を後から取得すれば自動的に優先され、Catalog の再構築も不要です。関係図から作品を選択する場合も通常のリソース適格性と内部ライブラリ検証を通り、ダウンロード計画の検証を迂回しません。

### 後続リリース監視

AnimeMachine が管理する単話または単巻タスクが完了すると、そのタスクの正確なリリース指紋を使って後続リリース監視を作成します。後の Torrent Pool 走査で同じ指紋かつより大きい連番を検出した場合、「設定 → 購読」に確認待ちの一致を作るだけで、自動ダウンロードはしません。この監視は Ani-RSS の遠隔購読とは別機構です。監視を削除しても AnimeMachine の将来の一致検出を止めるだけで、既にダウンロードしたメディアや Ani-RSS 購読は削除しません。

### Ani-RSS

Ani-RSS 接続後は三つのリソース利用モードがあります。(1)優先：ローカルに完全な一括リリースがない場合は Ani-RSS を優先、(2)フォールバック：ローカルに利用可能な案がまったくない場合のみ Ani-RSS を利用、(3)手動：バックグラウンドでは Ani-RSS リソースを自動検索・計画せず、ユーザーが「Ani-RSS リソース検索」などを明示的に実行した場合だけリソースを検索します。これら三つのモードが制御するのはリソース探索と計画だけで、購読と API 再生可能メディアの状態は設定済み同期間隔どおり更新します。リモートが一時的に利用不能でもユーザーが選んだ長期モード自体は変更せず、復旧後も元の設定で動作します。

Ani-RSS API Key が正常で「優先」または「フォールバック」の場合、AnimeMachine は Ani-RSS リソース結果をバックグラウンドで事前取得します。順序は画像事前読み込みに追従し、現在のランダムシードのホーム順で直近 6 か月をページ単位に先行処理し、その残りを補完した後、7 か月前から直近 24 か月の放送済み自然月まで月単位で遡ります。画像バッチを先に投入し、Ani-RSS は小規模な上限制並行キューで後追いするため、通常は画像が少し先に完了します。運用中の再確認は「リソースプール走査間隔（分）」に従います。起動時の事前取得と周期再確認は一つの非ブロッキング走査リースを共有し、次の走査時刻に前回がまだ実行中なら、その回は待機キューへ入れず並列実行もせず、そのままスキップして完了時刻も進めません。実行中の処理が終了した後、次のスケジューラ確認で対象を再判定します。リソース検索が Ani-RSS の接続／転送障害で失敗した場合は失敗証拠を保存し、その回を正常完了として扱わず、リソースプール走査間隔全体を待つ代わりに最大 5 分の短い再試行へ切り替えます。時計の巻き戻しで作品単位の最終試行時刻が現在より明確に未来へずれた場合は、その作品を直ちに期限到達として再判定し、未来時刻まで探索が抑制されないようにします。実行時 Ani-RSS 監視も同じリソース再確認を独立して起動するため、初回導入で画像事前読み込み開始時にはまだ未検証でも、数秒後に `ready` になれば再起動なしで同じプロセス内から探索を開始します。24 か月を超えた作品は無人バックグラウンド検索から外れます。この 2 年制限は自動事前取得/再確認だけに適用し、ユーザーの明示選択は制限しません。Ani-RSS だけを正常に接続した環境でも作品カードと関係図ノードを選択でき、複数作品の計画では現在の優先順位に従って Ani-RSS と Torrent を混在させられます。 作品単位の検索では、先のタイトル候補で結果がない場合に利用可能な中国語・日本語・英語の後続候補も試すため、英語名だけで一致する作品が前二候補の失敗だけで打ち切られません。Ani-RSS の接続先または API Key を変更すると旧ソースのリソース検索キャッシュを即時に消去し、旧ソースで実行中だった検索結果は切替後に書き戻せません。新ソースの検証が成功すれば、旧ソースの走査期限を引き継がず直ちにリソース探索を再開できます。リモート Ani-RSS の各リソース検索は開始時の実効プロキシルート世代も記録し、実行中にプロキシまたは `NO_PROXY` が世代交代した場合は遅着結果をコミット前に破棄し、現在のネットワーク世代で通常の再確認を続けます。

Ani-RSS HTTP API から提供されるメディアは、現在の API 資格情報が存在し接続正常と確認されている間だけ外部読み取り専用ソースとして扱い、直接移動や改名をしません。独立してマウントした Ani-RSS メディアディレクトリは常に読み取り専用ディレクトリとして扱います。「同期間隔（分）」は既定 30 分で一つの統合更新を制御し、自動の購読／API メディア同期は一つのバックグラウンド監視入口だけが担当します。各回は購読と作品対応を先に同期し、続いてリモート URL を保持するすべての対応済み購読を API `playList` で更新します。Ani-RSS 側で無効化されていてもダウンロード済みファイルを保持する可能性がある購読は対象に残るため、Ani-RSS メディアディレクトリをマウントしていなくても、新しくダウンロードされた話数は通常、設定した同期間隔内に作品詳細と M3U へ現れます。作品詳細の再生可能件数は購読の `currentEpisodeNumber` ではなく、ローカル `ani_rss_media` スナップショットに実在するファイル／話数から算出するため、購読進捗と再生可能ファイル数を混同しません。完全成功時刻はメディア段階まで終了した場合だけ進みます。個別プレイリストの一時失敗や、明示的ユーザー操作へバックグラウンド処理が譲った場合は直前の正常結果を保持し、他作品を消去せず、次の完全間隔を待たず最大 5 分で補償同期の対象になります。時計補正によって保存済み同期時刻が現在より明確に未来側へずれた場合も直ちに期限到達として扱い、更新が長期間抑制されることを防ぎます。Ani-RSS メディアディレクトリを設定している場合、その読み取り専用走査は同じ同期間隔設定を使いますが HTTP API の健全性とは分離され、API 未設定または一時利用不能でも継続します。ディレクトリ走査は API スナップショットを遅らせない独立バックグラウンドスレッドで動作し、同じ外部メディアソースの走査は同時に一回だけ許可され、前回が実行中ならそのソースの新たに期限到達した回だけを待機させずスキップし、他のソースには影響しません。ローカルカバーキャッシュは、現在の API Key が直近同期で検証した資格情報世代と一致し、接続先と同期状態も正常確認済みで、AnimeMachine 側に正常カバーがない場合だけ `/api/file` で早期取得を試みます。転送障害またはサーバー障害が起きたエンドポイントは、現在の資格情報世代との組み合わせごとに 30 秒間の早期フォールバック状態に入り、後続の画像キューは直ちに従来画像ソースへ戻ります。この Ani-RSS エンドポイントが実際に使うリモートルート世代が変わった場合だけ抑制を早期解除するため、localhost/LAN の直結先は無関係なプロキシ切替で再試行を繰り返しません。API Key を交換して正常な再同期が完了した場合も旧資格情報の抑制を引き継がず、HTTP 成功でも返却内容を画像として検証できなければ採用せず、`/api/file` も正常とは記録しません。既存の正常キャッシュはバックグラウンドで置換しません。明示的な「再読み込み」だけ Ani-RSS を再試行します。同一作品の複数購読はリモート ID ごとに独立保持します。Ani-RSS 未設定、資格情報なし、接続先変更後で未再検証、到達不能の場合は、HTTP 自動同期、現在の Ani-RSS 利用可能ソース判定、API の外部読み取り専用状態、API 購読／リソース表示、リモート再生入口、カバーのショートカットを自動的にスキップし、直前の正常 API メディアスナップショットは SQLite に復旧用キャッシュとしてのみ保持します。Torrent、Bangumi 画像、ローカルライブラリ処理、設定済み Ani-RSS メディアディレクトリの読み取り専用走査は独立して継続します。localhost、ループバック、プライベートネットワークは環境プロキシ変更後も直結します。リモート Ani-RSS は実効的なプロキシ／直結ルートの世代を追跡します。各同期は開始時点で実際に使用するルート世代を固定して記録するため、要求の途中でプロキシが切り替わっても新しいルートを検証済みと誤認せず、世代差を検出して直ちに補償同期を期限到達として扱います。したがって環境プロキシ、Windows システムプロキシ、`NO_PROXY` 規則が実際に変化した場合も通常の同期間隔を待ちません。新しいルートが同期で検証されるまでは、以前のリモート `ready` スナップショットを再検証待ちとして扱い、現在の Ani-RSS リソース、API の外部読み取り専用メディア、リモート再生元としては公開しません。保存済みスナップショットは復旧用にだけ保持します。ローカル／LAN の接続先は直結のままなので影響を受けません。 既存のリモート ID に対する一回の `listAni` 応答で URL、有効状態、現在/総話数、ダウンロード先などの任意項目が一時的に欠けても、直前に検証済みの値を保持するため、既知状態をゼロへ戻さず、その後の `playList` 更新で新しい話数を引き続き検出できます。`listAni` が申告する購読総数より実際に返った一意のリモート ID 数が少ない世代は不完全な購読スナップショットとして扱い、未返却購読の削除猶予を進めず、完全成功時刻も更新せず、完全な一覧が確認できるまで短い周期の補償再試行を維持します。旧版 Ani-RSS との互換のため `listAni` に `total` がない応答でも既存行の更新は行いますが、「今回現れなかった」ことだけを削除証拠にはしません。欠落購読の削除猶予を進めるのは、有効な `total` が返された一意のリモート ID 数と一致する完全一覧だけです。完全なリモート一覧から明示的に消えた購読だけを削除処理へ進めます。Web UI で保存した Ani-RSS API Key は画像 worker 起動前に読み込み、画像タスクへ現在の実効値を渡すため、実行中の資格情報変更・削除がカバーのショートカットへ直ちに反映されます。既に発行済みのリモート再生 URL も、資格情報が削除・変更された場合または同期済み接続状態が `ready` でなくなった場合は AnimeMachine 側で即座に無効化し、利用不能な Ani-RSS へ追加のメディア要求を送りません。正常な同期で対応済み作品に明示的な Ani-RSS カバーパスが確認された場合、有効な画像バイトを持たない、その作品の従来画像経路由来 `no_cover` 負キャッシュを解除します。そのため復旧後は 24/72 時間のカバー保守周期を待たず、次の通常画像要求から Ani-RSS を再試行できます。

作品詳細からダウンロード済み内容を持つ Ani-RSS 購読を削除できますが、これは明示的なリモート書き込み操作です。UI が再確認した後、Ani-RSS HTTP API で購読とファイルの削除を要求し、リモート一覧を再同期して結果を確認します。「外部読み取り専用」とは AnimeMachine がマッピングされたメディアディレクトリを直接変更しないという意味で、ユーザーが明示的に確認した Ani-RSS API 削除まで禁止する意味ではありません。

### 再生

ライブラリ一覧で具体的なメディアを選んでから、「コピー」「プレイリストをダウンロード」「VLC で開く」「PotPlayer で開く」を使用します。生成する M3U は本編だけを含み、話数順に並びます。同じ話数に複数のメディアがある場合、標準プレイリストでは取得元の優先度とファイルサイズから一つを選びます。異なる話数は独立して選択するため、二つのファイルのバイト数が偶然同じでも相互に重複扱いしません。特典や残りの複製はライブラリ記録に残ります。第 N 話から再生しても前の項目はプレイリストに残り、プレイヤーの開始位置だけを選択した項目へ移します。

ローカル実行なら通常はファイルパスをそのままプレイヤーへ渡せますが、Docker や遠隔導入ではそうとは限りません。コンテナ内 `/Library` はユーザー PC から見えないため、「設定 → 接続 → 外部プレイヤー連携」でクライアントから到達できる HTTP アドレス、またはサーバーパスからクライアントパスへの変換を設定します。たとえばサーバー `/Library` を Windows の `\\nas\anime`、macOS の `/Volumes/anime` へ割り当てられます。Ani-RSS メディアディレクトリをマウントしていない場合でも、AnimeMachine は Ani-RSS HTTP API を通じて完全な M3U を生成・中継できます。VLC/PotPlayer は AnimeMachine の一時 HTTP メディア URL を読み込み、バイト Range、シーク、プレイリスト連続再生を利用でき、上流が短時間切断した場合は転送済み位置から再開を試みます。そのため、遠隔 Ani-RSS 再生はローカルメディアパスを前提としません。

PotPlayer/VLC のシーク失敗、途中停止、遠隔転送速度の異常を調べる場合は、「設定 → 診断 → リモート再生セッション」を確認します。直近セッションについて、クライアント Range、自動再開回数、Ani-RSS 上流 HTTP 状態、現在の転送速度だけを簡潔に保持し、メディア内容、完全なローカルパス、資格情報は保存しません。

### 字幕

放送中リリースでは候補選択時にユーザー言語の字幕を優先します。アーカイブ向けは (1)内蔵字幕、(2)同名外部字幕、(3)ローカル字幕アーカイブ、(4)ユーザー設定字幕サービス、の順で確認します。新しい字幕を選ぶ場合、旧字幕はまず状態ディレクトリへバックアップします。外部読み取り専用ライブラリのメディアであれば、新字幕も AnimeMachine の状態ディレクトリへ保存し、元メディアのパスへ書き戻しません。

つまり字幕処理とメディア所有権は別です。AnimeMachine は読み取り専用動画に再生用字幕を関連付けられますが、そのことによって外部メディアライブラリを変更する権限を得るわけではありません。

### ディレクトリと履歴

単独作品ディレクトリは既定で `『YYYY_MM』『作品原名』`、シリーズディレクトリは `『開始－終了』『「シリーズ根名」シリーズ』` を使い、シリーズ内の子作品は各自の初回放送月で命名します。同一公式クールの分割放送は最初のクールへ統合し、明確な本編所属があるミニアニメ、Picture Drama などは付属物として扱い、別のプレースホルダーディレクトリを作りません。

ディレクトリ処理は、作品 identity と既存パスの確定から始めます。AnimeMachine がユーザー所有ファイルを移動・改名・置換する前に、「設定 → 履歴」へ変更を記録します。AnimeMachine 自身が作る通常ディレクトリは重複記録しません。ディレクトリ占有、一括リリース境界、作品 identity に自動確定できない衝突が残る場合、ダウンロード計画は十分な証拠が得られるまでレビュー状態で停止します。
