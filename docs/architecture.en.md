# AnimeMachine Architecture

AnimeMachine is organized around explicit evidence and write boundaries. Torrent Collector may discover and write new `.torrent` metadata, while AnimeMachine scans the Torrent Pool read-only; AnimeMachine produces download plans, while qBittorrent or Ani-RSS performs the actual media download; external media libraries may participate in identification and playback and remain read-only by default. This layered state prevents an ambiguous match from being amplified through the automation chain into an incorrect directory or download.

Collector completeness filtering lives in `src/animemachine/torrents/collector_filter.py`, network discovery and the service loop in `collector.py`, and migration, retry, atomic persistence, and Pool auditing in `collector_state.py`. Collector reads the local Catalog without modifying it. SEARCH, FILTER, and metainfo-classifier versions are maintained separately: a FILTER change reevaluates already discovered results first, while only a SEARCH change creates a new historical-discovery generation. Torrent v1, v2, and hybrid identity is computed and stored centrally by `metainfo.py`, so separate entry points do not derive competing hash rules.

## Architecture changes in 0.2.0

Version 0.2.0 keeps the existing evidence and write-permission boundaries intact; responsibilities among the Catalog, Torrent Pool, qBittorrent, and Ani-RSS do not change. The main architectural change is that previously scattered network resilience and background maintenance are promoted into shared infrastructure. `network/connectivity.py` owns suspected-outage, confirmed-offline, environment-change, and recovery-permission state; `network/diagnostics.py` connects real endpoint probes to the same health-learning model used by production requests; and `application_update.py` reuses shared network-source, download, and integrity-verification primitives for release discovery and updating. In Docker images, the stable `packaging/docker/entrypoint.py` selects verified application layers, supervises restarts, and rolls back when the new layer fails its health check. A Docker app layer replaces the AnimeMachine Python package only, not the base image, supervisor, Python/system components, or runtime dependencies; changes across those boundaries require a new full image. Activation persists target/rollback metadata in `pending.json` before atomically switching the `current` pointer, so an interruption between the two writes cannot make an unvalidated layer the sole active pointer without its first-start health check. The first health probe used by portable update workers and the Docker supervisor is derived from the effective Web listen address: explicit LAN/IPv6 binds are probed directly, while only IPv4/IPv6 wildcard binds are converted to local loopback addresses, preventing a healthy replacement from being mistaken for a failed upgrade.

On the image side, background prefetch, failed-item retry, and scheduled refresh are separate priority stages, with foreground promotion, adaptive resource budgets, and persisted progress governed by the same scheduling boundary. Service lifecycle is also explicit as `Starting → Ready → Warming → Warm`, separating “Catalog is usable” from “background image/history preparation is still running.” Remote Ani-RSS playback now uses the AnimeMachine HTTP relay so deployments without a mounted Ani-RSS media directory still follow one playback path, with bounded Range, resume, and throughput diagnostics.

Ani-RSS resource discovery shares the work-priority order with cover warming while retaining its own network queue: healthy Prefer/Fallback mode handles current landing pages and the most recent six months first, then months 7–24 month by month; runtime rechecks are triggered by the Resource-pool scan interval. Startup warming and periodic rechecks share a non-blocking scan lease, so a due tick is skipped rather than queued or run concurrently when the previous pass is still active, without advancing completion timing. The runtime Ani-RSS monitor independently schedules the same resource recheck, preventing a first-start race in which image warming begins before the initial API health synchronization; once the integration becomes `ready` in that process, a later monitor tick can start discovery without a restart. `ani_rss_search_state` stores per-work attempt/success timestamps and result counts to suppress redundant requests. The 24-month boundary limits automatic discovery only; explicit user selection can still query older works on demand. Region policy is applied consistently before Torrent and Ani-RSS eligibility, and a co-production remains eligible when any of its regions is allowed.


Runtime Ani-RSS synchronization is one coherent snapshot across `ani_rss_state`, `ani_rss_subscription`, and `ani_rss_media`, with automatic subscription/media refresh consolidated into one Web-service monitor. Explicit CLI synchronization remains available but no longer competes with a second automatic cadence worker. A successful `listAni` first reconciles work mappings, then bounded concurrent `playList` calls cover every mapped subscription that still has a URL, including remotely disabled subscriptions that may still contain downloaded files, and materialize playable media into SQLite. `last_success_at` advances only after the media phase completes; if one `playList` fails or the media phase yields to an explicit user action, only that subscription's last good media snapshot is preserved and the snapshot becomes eligible for a compensating retry within at most five minutes rather than another full interval. If a wall-clock correction leaves persisted attempt/success timestamps materially in the future, synchronization is immediately treated as due so a future timestamp cannot suppress refresh indefinitely. Requests and the media phase are time-bounded, and background sync acquires the Ani-RSS operation lock only when no explicit user Ani-RSS action is pending, so a dead or partially degraded Ani-RSS cannot indefinitely hold up user search, Torrent handling, image fallback, or Web requests. The work-detail playable count comes from the actual `ani_rss_media` snapshot rather than the subscription-progress field. When an Ani-RSS media directory is configured, its read-only scan uses the same interval setting but is decoupled from HTTP API health and runs in a separate background thread; it can continue when the API is unconfigured/unavailable, while per-source non-blocking scan locks skip a new pass only when that same source is still being scanned, without blocking unrelated external libraries. Covers are fetched through the mapped subscription `cover` path and Ani-RSS `/api/file` only when no valid local cover exists or the user explicitly reloads it, and only when the current API key matches the credential generation validated by the latest synchronization and the endpoint and synchronized state are confirmed healthy; the shortcut fails fast and validates returned image bytes before handing any failure immediately back to ImageFetcher. A transport or server-side failure places the current `/api/file` endpoint in a 30-second fail-fast cooldown, so later covers do not repeat the same wait for every work; a proxy-generation change invalidates that cooldown immediately. Localhost, loopback, and private-network targets remain direct, so environment-proxy changes cannot accidentally route a local Ani-RSS through a proxy. For a stable remote ID, if one `listAni` generation temporarily lacks the URL, enabled state, current/total episode values, download path, or another optional evidence field, the last verified value is inherited instead of breaking media refresh or zeroing known state on one incomplete response; only a subscription that is actually absent from a complete remote list and satisfies deletion-grace handling proceeds toward removal. If `listAni` advertises more subscriptions than the unique remote IDs returned in that generation, it is treated as an incomplete subscription snapshot: unseen subscriptions do not age toward deletion, the full-success timestamp does not advance, and a short compensating retry remains due. A remote media token also rechecks current credentials and `ani_rss_state` before touching the upstream, so a stale player request fails locally when Ani-RSS is no longer healthy instead of waiting on an unavailable integration.

Available source and Library status are orthogonal evidence dimensions. Torrent and Ani-RSS sources may both be true, while No available source is true only when neither exists. Ani-RSS contributes current Available-source evidence only while credentials are configured and connection state is confirmed `ready`; removing or changing credentials, or changing the endpoint, cannot keep a stale ready state active. The public Library status is normalized from finer evidence into four mutually exclusive categories, with priority Local library > External read-only > Submitted download > Not yet in library: `runtime_work` state `existing` and completed qBittorrent results are Local library; verified external media is External read-only; HTTP-playable `ani_rss_media` that still maps to a live subscription is External read-only only while current credentials exist and connection state is confirmed `ready`, and then also sets card-level `has_external_media` evidence. If the API disconnects, credentials are removed or changed, or an endpoint change is awaiting revalidation, the historical SQLite media snapshot is retained for recovery but is not exposed as currently playable external media through cards, detail data, or playback entry points; independently mounted read-only media remains unaffected by this API-health gate. Only incomplete qBittorrent `queued`/`downloading`-class work is Submitted download; everything else is Not yet in library. Internal states such as `occupied_review`, `placeholder`, and `absent` remain available for directory verification, completeness, and write-safety decisions but are not public Library-status categories, and an Ani-RSS subscription is never treated as Submitted download. Region policy first participates in Catalog SQL visibility, so works from a disabled region cannot reappear merely as No available source. The same policy also applies during card enrichment and Torrent/Ani-RSS eligibility so an existing Ani-RSS subscription cannot bypass a disabled region. Non-Japanese works continue to infer `original_language` from Archive country/region evidence and script, while animation titles, source-work names, and studio aggregation remain separate fields and are not rewritten by the synchronization source. Card-level Ani-RSS managed flags and resource counts use the same health gate as filters, details, and playback; credential removal or change, an endpoint awaiting revalidation, or a failed connection clears them immediately instead of letting a historical SQLite snapshot look currently available.

## Runtime boundaries

The main AnimeMachine implementation is under `src/animemachine`. Web, Catalog, Torrent indexing, library verification, qBittorrent, Ani-RSS, playback, and subtitle modules share SQLite evidence, but they do not share an assumption that every result is allowed to write everywhere. A result advances into directory mutation, download submission, or replacement only after it reaches the evidence strength required by the next stage.

AnimeMachine directly handles two classes of input: (1) local Torrent metadata placed in the shared directory by the user or optional Torrent Collector; and (2) records returned by external components connected by the user. Archive data, covers, and supplementary metadata pass through the shared network layer, which handles proxy/direct routing, mirror failover, retry backoff, response-size limits, and integrity validation. For Archive/application-update assets with known size and digest, the download layer prefers resumable Range segments; when segmented transfer fails and a probed non-Range fallback is available, it downgrades to whole-file transfer, still verifies size and SHA-256 before atomic publication, and never carries a complete digest-mismatched temporary file into the next retry. Proxy settings are reread per request and the effective route is classified as direct, environment proxy, or Windows system proxy. If a proxy URL is malformed, its port is invalid, or the current runtime cannot instantiate the required proxy transport, that candidate is isolated during client creation and routing continues with later candidates; diagnostic route identifiers retain only sanitized scheme/host/port information. Actual proxy changes still create a new connection generation, but network-health learning is accumulated under these stable route classes, so switching to a proxy can reuse what that environment learned earlier and returning to direct access does not discard direct-route history. Localhost, loopback, and private networks stay direct. Deployment credentials prefer environment variables or secret files. qBittorrent, Ani-RSS, and subtitle credentials entered by an administrator in Web settings are instead persisted in restricted credential files under the state directory and survive restart. They are never written to public configuration, documentation, browser storage, or Web API responses; POSIX permissions restrict them to the service account, and Windows ACLs are tightened to the current service account and SYSTEM where possible. This is permission-isolated local secret storage, not an encrypted vault, so the service account or a host administrator can still read the files; deployment environment/Secret credentials always take precedence over Web-saved values. A connection test may pass the qBittorrent/Ani-RSS key currently typed in the browser as a request-scoped probe credential; it is not copied into the process environment or state files, and persistence occurs only through the settings-save path. The server treats the complete configuration plus newly entered credentials as one settings transaction: persistent configuration and the runtime-overlaid view are fully validated first, then configuration and a rollback-safe credential batch are committed; a persistence failure restores the pre-save state. Configuration and credential mutations share the same write gate, so concurrent administrator requests cannot interleave with a transaction or its rollback. Explicit connection tests run under `recovery_probe`, so confirmed offline mode cannot block an administrator-triggered probe, while localhost, loopback, and private-network targets remain direct. The network-health layer persistently records each endpoint's recent success rate, EWMA latency, throughput, cooldown, and latest failure reason independently for each network environment, while time buckets retain short-term image-source health trends. Recent evidence decays into an effective sample count, and low-sample observations are confidence-shrunk so one-off successes or failures cannot dominate. Endpoint selection adds an incumbent hold window and a minimum switching advantage on top of composite quality, switching only when another source is meaningfully better or the incumbent enters cooldown. Diagnostic probes share the same evidence as production requests and expose the current selection, sample confidence, and the reason for holding or switching. Complete offline mode is confirmed only after both AnimeMachine service probes and independent Internet canaries fail continuously for at least 30 minutes without a long observation gap. Failure learning is suspended from the first whole-network suspicion while ordinary requests may still try; remote background work is paused only after offline state is confirmed. Recovery probes always bypass local mode, and any successful ordinary request or manual network recheck exits offline state and resumes background work, so proxy changes, brief outages, single-upstream failures, or sleep/resume cannot permanently trap the process in local mode. Image preload runs in a separate process, and background concurrency/bandwidth limits apply only to background tasks. Foreground-visible works always have priority and can promote an item already waiting in the background queue. The background budget is conservatively scaled by foreground activity, foreground image latency, CPU pressure, recent image-I/O duration, and network-failure signals. In the browser, scroll direction drives a strictly bounded next-screen prefetch window. Startup preload first completes the bounded landing-page window page by page under the current random seed, then fills every work from the most recent six months, and finally walks backward strictly month by month from month seven; periodic image maintenance uses a separate lowest-priority queue. A healthy cached cover is checked automatically only from six to two months before airing, from two months before through one month after airing, and from one to two months after airing, at 72-, 24-, and 72-hour intervals respectively. A low-priority scan selects due works every 12 hours; outside those windows automatic refresh stops, while manual Reload always forces a refresh.

Optional Torrent Collector runs as an independent Compose service. It has write access to the shared Torrent Pool, while AnimeMachine keeps the same Pool read-only. This boundary is intentional: Collector decides whether metadata may enter the candidate pool; AnimeMachine decides which work the candidate actually belongs to, whether it covers the target, and whether it should be downloaded. The former does not replace the latter.

## Web authentication and permission boundary

The Web layer uses a local SQLite account store and short-lived session cookies. With authentication enabled there are only two roles, `admin` and `user`. Server-side `requires_admin()` checks consistently protect configuration writes, Archive/metadata maintenance, Library Audit, history restoration, user management, network rechecks, image-preload control, log/history/diagnostic reads, and application updates. Normal users retain Catalog queries, per-work actions, download plans, and permitted playback/subscription capabilities. State-changing requests additionally require a valid CSRF token. Configuration/API output redacts credential-like sensitive values.

Frontend visibility is only a usability hint; the server repeats every authorization check. For example, global “Reshuffle” changes the instance-wide random seed, so it is displayed only to administrators and remains server-protected even if a normal user manually constructs the request. With authentication disabled, the local single-user session maps to administrator capabilities, but Host/Origin and write-request constraints remain active; “no login” does not mean “no request boundary.”

## Data flow

```text
Bangumi Archive ──> Anime Catalog ──> titles, relationships, directory planning
Torrent Collector ─> shared Torrent Pool (collection metadata)
Torrent Pool ──────> incremental index ──> candidate policy and file manifests
Local library ─────> verification/history ──> differential completion and state
Ani-RSS ───────────> subscriptions and read-only media mapping
Candidate plan ────> qBittorrent / Ani-RSS ──> download-state feedback
```

Archive is built in background stages and published atomically only after integrity checks succeed. Large Torrent Pools and external media libraries are processed incrementally in short batches so one full scan does not hold a long database transaction. Web reads use independent connections and short transactions, allowing catalog construction, scanning, and interactive browsing to proceed concurrently. The startup-state API makes the lifecycle explicit as `Starting → Ready → Warming → Warm`: `Ready` means the Catalog and Web are usable, while `Warming` means only that background Catalog/image preparation is still running and must not be treated as service unavailability. The second home status row is deliberately compact and combines background-image state, the `YYYY-MM` backward frontier, the active Bangumi Archive version, and Catalog work count. Remaining work, ETA, and the current item are omitted from the home row; full progress, remaining work, throughput-derived ETA, current item, and adaptive background concurrency remain available in Diagnostics. Year/Season remains a front-end projection onto explicit `start_from` / `start_to` month bounds: Winter is anchored to the year containing January and crosses back to the previous December, while Spring, Summer, and Autumn map to Mar–May, Jun–Aug, and Sep–Nov. The server therefore needs no second season-query semantics. Browser-restored filter state is normalized through the current season definitions before reverse synchronization. A legacy state containing only a cross-year Winter month range is anchored to the year containing January, avoiding a one-year shift during restoration. Preload stages and controls are persisted separately and resume after restart using the image cache as the authoritative baseline.

For non-Japanese works, the Archive primary title is still stored in the compatibility column `anime_work.title_ja`, but that physical column name is now historical: semantically it is the Archive primary/original title, and `original_language` is authoritative for its language. `anime_title` stores language-tagged multilingual titles and aliases, so a Korean primary title can coexist with Chinese, Japanese-edition, and English-edition names. Country evidence combines tags, Infobox fields, title script, and studio evidence. Studio clustering for non-Japanese works uses only verifiable Archive structures such as `brand〖legal entities〗` and `legal entity (brand)`, while Japanese works keep the established rename-family rules. Source-work titles remain separate relation evidence and are never written back over the animation primary title. Title normalization also preserves Hangul and Cyrillic for source matching, subtitle search, and media-completeness comparison.

Covers are another external dependency that can easily slow an entire application, so image network access is moved into the independent `ImageFetcher` process. AnimeMachine prefers Bangumi's roughly 400 px server-side scaled image, uses short-delay parallel fallback across the official source and available mirrors, and keeps the original-size image as the last fallback. Transient failures receive only short negative caching and that transient state is cleared on service restart. On a cache miss, the Web API returns a placeholder immediately and the front end replaces it after the background fetch succeeds. If “Reload” is pressed while the same work is already being fetched, one forced refresh is preserved instead of being silently swallowed by the in-flight request. Bulk image maintenance counts terminal outcomes: items that cannot enter the queue because the system is fully offline or the image worker is unavailable are counted as failures rather than being reported successful merely because no work remains pending. Web-persisted credentials are loaded into the parent before the isolated image process is created, and each task carries the current effective Ani-RSS credential snapshot. A spawned child therefore cannot freeze an old API key for later requests, and changing or removing the key at runtime enables, switches, or disables the Ani-RSS cover shortcut without a restart.

## Identity and directories

Directory handling follows one fixed order: **identify the work, identify the existing path, and only then consider creating a new path.** Identity is supported by titles, aliases, first-air month, series relationships, and existing files. If the existing library contains one uniquely credible nearby target, that path is reused. An incorrect directory is corrected in place before creating a second, “more standardized” directory. An official English subtitle is appended to a directory name only when it is semantically distinct from the original title and sufficiently supported by evidence.

The reason is that a logical Bangumi entry is not inherently equivalent to one physical directory. Split broadcasts, attached shorts, originally unsplit movie/OVA collections, and very long continuous works may require multiple logical members to share one physical target. Conversely, after physical targets are merged, Catalog logical members remain distinct. Every download plan therefore resolves to a canonical target before differential comparison with local files; it cannot skip the identity layer and build directories directly from a Torrent title.

## Resource policy

Torrents supplied by the user and Torrents gathered by Collector ultimately enter the same incremental index. Collector prefiltering only blocks metadata that clearly falls outside the automated-collection boundary; it does not replace AnimeMachine work identification, eligibility decisions, or ranking. A resource class is excluded only when the user explicitly disables it, and unrecognized values are grouped under “Other.” For a long-term archive this is safer than treating unknown values as errors, because older release naming is not always standardized.

Allowed resource categories also include Region policy. China maps mainland China/Hong Kong/Macao/Taiwan, Europe maps all European countries including the UK and Russia, and blank or insufficiently evidenced regions map to Other. This policy limits eligibility for new candidates without destroying existing media, subscriptions, or historical evidence.

Ranking uses a complete plan for one work or one series as its unit. AnimeMachine first determines whether the plan covers the expected episodes/volumes and then compares collection form, release group, source, resolution, subtitles, revision date, and related preferences. Resource quality therefore participates after coverage has been established; a higher resolution cannot compensate for missing episodes.

Only one AnimeMachine-managed task may exist for one infohash. A single collection can map different file indexes to multiple child works; when additional files are needed later, the existing task is reused and only previously unselected indexes are added. Every formal submission is preceded by an immutable plan. If the plan detects a target-directory conflict or a file scheduled for replacement, execution moves into staging, validation, or review rather than overwriting existing content directly.

## Work relationship graph algorithm

The work relationship graph first reconstructs relationship structure from many-to-many evidence and then determines how to draw it. The first stage processes the graph itself: (1) normalize Bangumi source relationships into directed edges; (2) add reverse relationships that can be established; (3) remove confirmed duplicate edges and provably transitive redundant edges; and (4) build strict series connected components. Only strong evidence permits AnimeMachine to repair an obvious mislink, add an entry into an isolated subseries, or re-anchor a relationship to the head of a subseries. Original source evidence is always retained; a corrected interpretation does not overwrite the source fact.

Layout happens in the second stage. Nodes are ordered by month, medium, and title sequence; works with the same medium or a clear numeric sequence are preferentially placed on the same row. Mainline sequels use the central straight track when possible, while side stories, derivatives, recaps, alternate adaptations, and cross-series relationships receive separate tracks and ports. The router evaluates node boundaries, occupied tracks, label rectangles, and bend cost together and can choose a straight segment, orthogonal polyline, or vertical detour when necessary. Long-span edges sharing one source are then layered by time and target position to reduce unreadable crossings. Complex graphs can hide selected relationship types, open full-screen, and export SVG/PNG.

## Repository structure

```text
src/                 runtime source and built-in static resources
config/              public configuration examples and JSON Schema
deploy/              local deployment, four Compose layouts, and shared Torrent Collector definition
packaging/            image-build definitions
scripts/              Windows, Linux, and macOS build/start/cleanup entry points

```

Runtime databases, Archive data, cover caches, logs, credentials, private paths, and build artifacts are runtime/local outputs and are not part of the source tree. This distinction also means source can be reacquired, while the state directory should be backed up; conversely, cleaning build caches must not touch the user Catalog or collection history.

## Database conventions

AnimeMachine uses two SQLite files to separate “large scanning writes” from “stable front-end queries.” (1) The Anime Catalog defaults to `$ANM_STATE_DIR/catalog/anime-catalog.sqlite3` and stores anime metadata derived from Bangumi Archive, work relationships, covers, external-media mappings, and runtime-state projections used by Web queries and plan generation. (2) The runtime database defaults to `$ANM_STATE_DIR/catalog/runtime.sqlite3` and stores the raw incremental Torrent-Pool index, verified identities, file partitions, submission evidence, and local-verification results. After a short runtime batch completes, only verified results are synchronized into the Catalog's `runtime_*` tables, so the front end does not compete directly with the scanning database.

Both database paths can be overridden through environment variables, but two AnimeMachine instances must not write to the same state directory concurrently. The Anime Catalog base structure is created by `src/animemachine/catalog/service.py`, runtime migrations are managed by `src/animemachine/catalog/migrations.py`, and query projections by `src/animemachine/torrents/runtime.py`. Migrations must be forward-compatible and repeatable. Credentials, private-path listings, and manual exports must not be written into public documentation or test fixtures.

### Anime Catalog

- `anime_work`: logical anime works, including Bangumi ID, the Archive primary title (the physical `title_ja` column name is retained for compatibility), `original_language`, first-air month, medium, episode count, summary, and physical-merge role.
- `anime_title`: language-tagged multilingual titles and aliases, including non-Japanese primary titles and explicit regional/language editions; directory naming uses only verified original titles and genuinely necessary subtitles.
- `anime_staff`, `anime_cast`, `anime_studio`, `anime_studio_cluster`: normalized staff, cast, and studio data.
- `anime_tag`, `anime_theme`, `anime_theme_evidence`, `anime_country`: filter fields and their rule evidence.
- `anime_relation`: raw Archive relationships; `anime_relation_edge` and `anime_series_component` store normalized relationships and strict series connected components respectively.
- `anime_image`: validated cover MIME, bytes, source, and cache state; data is written atomically only after complete download and format validation.
- `external_library_source`, `external_media_file`: external read-only media-library sources, directories, and file-level evidence.
- `ani_rss_state`, `ani_rss_subscription`, `ani_rss_media`, `ani_rss_resource`, `ani_rss_search_state`, `ani_rss_action`: Ani-RSS synchronization state, playable-media snapshots, background-search throttling state, and idempotent operation records.
- `metadata_snapshot`, `metadata_evidence`, `metadata_repair_queue`: base-package provenance, supplementary metadata, and deferred repair tasks.

### Runtime database and query projections

- `torrent_source`, `torrent`, `torrent_manifest_file`: Torrent-Pool file fingerprints, infohashes, titles, sources, release groups, manifests, and parse errors; a source is reread only when its fingerprint changes. Source-path identity follows host-filesystem normalization: case is equivalent on Windows, while case-sensitive filesystems retain case distinctions so missing sources can be reconciled accurately. If several `.torrent` copies share one info-hash and the current primary source disappears, a complete scan reselects `torrent_path` from a remaining present copy so usable metadata does not keep pointing at a vanished file.
- `anime_work`, `anime_work_member`, `torrent_work`: physical targets, logical members, and verified many-to-many Torrent-to-work mappings; `torrent_work` is authoritative evidence for identity and final path.
- `file_map`: canonical targets and selection evidence for each file index in a collection.
- `submission`, `submission_revision`, `submission_file_revision`: AnimeMachine-managed qBittorrent tasks and append-selection history; one infohash maps to one task.
- `asset_provenance`, `release_baseline`, `upgrade_candidate`: local-file provenance, comparison baselines, and verifiable upgrade candidates.
- `torrent_resolution`, `torrent_target_path`, `title_review`, `scope_exclusion`: scope, title, target, and handling reasons that cannot be resolved automatically.
- `runtime_work`, `runtime_torrent`, `runtime_torrent_work`, `runtime_torrent_file`, `runtime_file_map`, `runtime_submission`: front-end query projections in the Anime Catalog; they do not replace authoritative records in the runtime database.
- `download_plan`, `runtime_watch`, `runtime_watch_match`, `runtime_asset`, `runtime_completeness`, `runtime_review`: immutable plans, tracking, local completeness, and front-end review state stored in the Anime Catalog.

### State principles

AnimeMachine state handling can be reduced to six rules: (1) a logical work is not the same as a physical directory; split broadcasts, attached shorts, and originally unsplit collections may share one physical target; (2) unverified mappings, temporary proposals, and ambiguous matches cannot authorize directory changes or download submission; (3) local differential comparison is limited to the same canonical target, with fast mode skipping on canonical target plus exact byte size and exact mode hashing only when a comparison baseline exists; (4) replacement requires revision evidence, complete staging, and validation, and any failure preserves the old file; (5) magnet tasks are only registered until a complete manifest is available and do not automatically map files or submit downloads; and (6) configuration changes invalidate derived ranking and unexecuted plans only, not verified work identities or source evidence.

The common purpose of these rules is to keep state changes explainable. New evidence may change a conclusion, but a configuration edit or one ambiguous match must not erase facts that were already verified.

### Concurrency

Long imports and scans use short batch commits and avoid long-held transactions. Web reads use independent connections with WAL enabled. Cover network access runs entirely in a separate process and uses neither Web request threads nor the main process HTTP connection pool. Front-end progress comes from atomic state files or background-task tables. Time-consuming work remains isolated so its latency does not spread into ordinary browsing and queries.
