# AnimeMachine 架构说明

AnimeMachine 的架构以证据边界和写权限边界为基础：Torrent Collector 可以发现并写入新的 `.torrent` 元数据，AnimeMachine 只读扫描 Torrent Pool；AnimeMachine 负责生成下载计划，实际媒体下载交给 qBittorrent 或 Ani-RSS；外部媒体库可以参与识别和播放，并默认保持只读。明确的分层状态能够阻止模糊匹配沿自动化链路继续放大，降低错误目录和错误下载的风险。

Collector 的完整性过滤位于 `src/animemachine/torrents/collector_filter.py`，网络抓取与服务循环位于 `collector.py`，迁移、重试、原子保存和 Pool 审计位于 `collector_state.py`。Collector 只读访问本地 Catalog。SEARCH、FILTER 与 metainfo 分类版本分别管理：FILTER 变化优先重评已经发现的结果，只有 SEARCH 变化才建立新的历史发现任务。Torrent v1、v2 与 hybrid 的 identity 统一由 `metainfo.py` 计算和保存，避免不同入口各自推导一套 hash 规则。

## 0.2.1 架构

0.2.1 沿用既有“证据边界 + 写权限边界”，没有改变 Catalog、Torrent Pool、qBittorrent、Ani-RSS 之间的职责划分；本次变化主要把原先分散的网络容错和后台维护提升为共享基础设施。新增 `network/connectivity.py` 统一维护疑似断网、确认离线、环境切换和恢复许可，`network/diagnostics.py` 将实际端点探测与健康学习连接起来，`application_update.py` 复用同一网络源、下载和完整性校验机制完成 Release 检查与更新。Docker 镜像中的稳定入口 `packaging/docker/entrypoint.py` 负责选择已验证的应用层、监督重启并在健康检查失败时回滚。Docker 应用层只覆盖 AnimeMachine Python 包，不替换基础镜像、supervisor、Python/系统组件或运行依赖；这些边界发生变化时必须发布并拉取完整镜像。应用层激活时先持久化 `pending.json` 中的目标/回滚信息，再原子切换 `current` 指针，确保即使两次写入之间发生异常，也不会让未经过首次健康检查的新层成为唯一活动指针。便携版更新 worker 与 Docker supervisor 的首次健康探针由实际 Web 监听地址派生：显式 LAN/IPv6 绑定直接探测该地址，只有 IPv4/IPv6 通配监听才转换为本机回环地址，避免把正常的新实例误判为升级失败。

图片侧把后台预取、失败重试和周期刷新划成独立优先阶段，并把前台提升、自适应资源预算和持久化进度纳入同一调度边界。服务生命周期同时显式拆为 `Starting → Ready → Warming → Warm`，使“Catalog 已可用”和“后台仍在准备图片/历史数据”不再混为一个状态。远程 Ani-RSS 播放则通过 AnimeMachine HTTP 中继把未挂载媒体目录的部署也纳入统一播放链路，并记录有限的 Range、续传和吞吐诊断信息。

Ani-RSS 资源发现与图片预热共用同一作品优先序，但保持独立网络队列：健康的优先/备选模式先处理当前首页分页和最近 6 个月，再按第 7～24 个月逐月回溯；运行期由资源池扫描间隔触发滚动复查。启动预热与周期复查共享非阻塞扫描租约，若到期时上一轮仍在执行，本轮直接跳过而不排队、不并发，也不推进完成时间。运行期 Ani-RSS 监控也独立调度同一资源复查，避免首次部署时图片预热线程先于 API 首次健康同步启动而漏掉整轮后台检索；一旦连接在当前进程变为 `ready`，后续监控轮次即可补启。`ani_rss_search_state` 记录每部作品的最近尝试、成功时间、结果数与失败证据，避免重复请求；连接/传输失败不会被记作成功扫描，调度器改为不超过 5 分钟的短退避后重试；若系统时钟回拨使作品级最近尝试时间明显落在未来，则立即视为到期重新检查，避免被未来时间戳长期抑制。24 个月边界只限制后台自动发现，显式用户选择仍可按需查询更早作品。地区策略在 Torrent 与 Ani-RSS 资格判定前统一应用，联合制作只要至少一个地区获准即可保留。 资源检索在当前标题候选无结果时会继续尝试后续可用的中/日/英标题候选，直到找到结果或候选耗尽。资源缓存还绑定到当前 Ani-RSS 的“端点 + 凭据指纹”代次：同步检测到端点或 API Key 变化时会在同一事务内清空旧 `ani_rss_resource` / `ani_rss_search_state`，并把资源扫描重新置为到期；旧代次已经在飞的搜索在写入前再次核对当前代次，失配时直接丢弃，因此旧实例结果不能在切换后回灌。远程资源搜索还固定开始时的有效代理路由代次，并在落库前复核；若代理或 `NO_PROXY` 在一次慢搜索中途换代，本轮结果同样直接丢弃，避免跨网络代次回灌。


Ani-RSS 运行期同步现在由 `ani_rss_state`、`ani_rss_subscription` 与 `ani_rss_media` 组成一个一致快照，并把自动订阅/媒体刷新收敛到 Web 服务的单一监控入口；CLI 显式同步仍可独立触发，但不会再与第二条自动周期线程竞争。一次成功的 `listAni` 先完成作品映射，再以有界并发获取所有已映射且仍有 URL 的订阅 `playList`，包括远端已禁用但仍可能保有下载文件的订阅，把可播放媒体物化到本地 SQLite。只有媒体阶段完整完成才推进 `last_success_at`；单个 `playList` 失败或媒体阶段因用户操作让路时只保留对应订阅上一次成功快照，并在不超过 5 分钟的短周期内再次具备同步资格，而不是等待完整同步间隔；如果系统时钟回拨使持久化的尝试/成功时间明显落在当前时间的未来，同步会立即重新判定为到期，避免被未来时间戳长期抑制。同步任务有严格请求超时和总媒体阶段预算，后台只在没有用户 Ani-RSS 操作排队时非阻塞取得操作锁，因此失效或半失效的 Ani-RSS 不会长期占住用户搜索、Torrent、图片回退或 Web 请求。作品详情的可播放数量来自 `ani_rss_media` 实际快照而不是订阅进度字段。配置 Ani-RSS 媒体目录时，只读目录扫描使用相同间隔设置但与 HTTP API 健康状态解耦，在独立后台线程中运行；API 未配置/不可用时仍可扫描挂载目录，并通过按来源的非阻塞扫描锁保证同一来源上一轮未完成时新一轮直接跳过，且不影响其它外部库。封面只在作品没有正常本地缓存、或用户显式重新加载时通过已同步订阅的 `cover` 路径和 Ani-RSS `/api/file` 获取，并且只有当前 API Key 与最近一次同步验证的凭据代际一致、端点和同步状态均已确认正常时才启用这条捷径；请求快速失败，返回内容必须通过图片校验，而且只有校验通过后才把 `/api/file` 端点记为健康，否则立即交回 ImageFetcher 的原图片源链路；传输或服务端故障会让当前“`/api/file` 端点 + 凭据代际”进入 30 秒快速回退冷却，使后续图片不再逐张重复等待；冷却绑定该 Ani-RSS 端点实际使用的路由代际，只有远程端点的有效路由确实变化才提前失效，localhost/LAN 直连端点不受无关代理开关影响；API Key 更换并完成成功重同步后也不会继承旧凭据的冷却。远程 Ani-RSS 的统一同步在每轮开始时固定记录本轮真正使用的有效路由代际；若代理恰好在同步过程中切换，完成时仍保存旧代际，因此新旧代际差会立即触发补偿同步，不会把尚未实际验证的新路由误记为健康。环境代理、Windows 系统代理或 `NO_PROXY` 规则改变并形成新路由时，即使原同步间隔未到也立即重新具备同步资格；在新路由完成同步验证之前，旧远程 `ready` 快照在逻辑状态上降为 `unknown/manual`，不会继续作为当前资源、外部只读媒体或远程播放来源，但底层快照仍保留用于成功重同步后的快速恢复。localhost、回环和私有网段保持直连并免受这类代理代际触发，因此环境代理变化不会把本地 Ani-RSS 错送到代理或制造无意义的重复同步。 对同一远端 ID，某轮 `listAni` 若暂时缺少 URL、启用状态、当前/总集数、下载路径或其它可选证据，会继承上一轮已验证字段，不因一次不完整响应切断媒体刷新或把已知状态误清零；下载路径同时识别当前 Ani-RSS 的 `customDownloadPathTemplate` 与旧响应中的 `downloadPath`，避免不同版本间路径证据丢失；只有明确从完整远端列表消失并满足删除宽限条件的订阅才按删除处理；若 `listAni` 申报总数大于本轮实际返回的唯一远端 ID 数，该轮标记为不完整订阅快照，未出现订阅不累计删除宽限、完整成功时间也不推进，并进入短周期补偿重试。兼容旧版 Ani-RSS 时，无 `total` 的 `listAni` 仍可同步已有行，但“本轮缺席”不作为删除证据；只有有效 `total` 与返回的唯一远端 ID 数一致时才推进缺失订阅的删除宽限。远程媒体 token 在真正访问上游前还会复核当前凭据与 `ani_rss_state`，状态不再健康时在本地快速失效，避免旧播放器请求卡在不可用 Ani-RSS。成功的 `listAni` 若为已映射作品提供明确 `cover` 路径，会同时解除该作品此前由自有图片链路留下、且没有有效图片字节的 `no_cover` 负缓存；因此 Ani-RSS 从故障恢复并重新验证后，下一次正常图片请求即可使用其封面，不受 24/72 小时维护周期或窗口外停刷策略阻塞。 协议边界按 0.2.1 完整 Compose 固定的 Ani-RSS `v3.2.28` 核验：`listAni` / `playList` / `mikan` / `mikanGroup` 不只校验顶层类型，还严格校验 `weekList` / `weeks` / `items` 等嵌套对象数组；畸形子结构按协议错误失败关闭，不能被解释成完整空快照而老化订阅、清空媒体或替换资源缓存。

“可用来源”是与“收藏库状态”正交的证据维度：Torrent 与 Ani-RSS 可以同时为真，只有两者都为假才属于“无可用来源”；其中 Ani-RSS 只有在当前凭据已配置且连接状态已确认 `ready` 时才提供当前“可用来源”证据，删除/更换凭据或更换端点不会继续沿用旧的 ready 状态。对外的“收藏库状态”由内部证据归一为互斥四类，并按本地入库 > 外部只读 > 提交下载 > 暂未入库确定：`runtime_work` 的 `existing`/已完成 qBittorrent 结果归入本地入库；已验证外部媒体归入外部只读；`ani_rss_media` 中仍对应有效订阅的 HTTP 可播放媒体只有在当前凭据存在且连接状态确认为 `ready` 时才归入外部只读，并同时设置卡片级 `has_external_media` 证据。API 断连、凭据删除/更换或端点变更待重新验证时，SQLite 中的历史媒体快照继续保留以便恢复，但不再通过卡片、详情或播放入口作为当前可播放外部媒体暴露；独立挂载的只读外部媒体不受该 API 健康门控影响。仅 qBittorrent 的 `queued`/`downloading` 等未完成任务归入提交下载；其余归入暂未入库。`occupied_review`、`placeholder`、`absent` 等内部状态继续服务目录核验、完整度和写入安全，但不暴露为收藏库分类；Ani-RSS 订阅也不会被误算为提交下载。地区策略首先进入 Catalog SQL 可见性过滤，因此被关闭地区的作品不会被重新归类成“无可用来源”后继续显示；同一规则也用于卡片富化和 Torrent/Ani-RSS 资格判断，避免已存在的 Ani-RSS 订阅绕过用户关闭的地区。非日本作品继续以 Archive 的国家/地区证据与文字系统推断 `original_language`，标题语言、原作名称和制作公司聚合保持独立，不因同步来源变化而互相覆盖。详情页的关联作品、系列关系图、后续发布监视列表与图片预加载诊断的当前作品名使用同一套当前界面语言标题选择：优先采用 `anime_work` / `anime_title` 中已有且可验证的中、英、日标题。0.2.1 的特性迁移会重新遍历现有 `anime_title` 英文别名，拒绝包含任何非拉丁字母文字（包括中/日/韩、西里尔、希腊、阿拉伯等文字）却被误标为英文的候选，补齐或清理旧 Catalog 的 `anime_work.title_en`，并写入新的标题策略代际；如果上游确实没有英文标题，英语界面的显示层会临时回退到作品原标题，但不会把该原标题写入 `title_en` 或标记为英文；后续取得可靠英文名时会自然恢复英文优先。升级无需重建 Catalog。简体中文界面即使面对原语言粗粒度标记为 `zh` 的港台作品，也优先使用明确的 `zh-Hans` 标题。 卡片上的 Ani-RSS 受管标记和资源计数与筛选、详情、播放使用同一健康门控；凭据删除/更换、端点变更待验证或连接失效后会立即归零，不会让历史 SQLite 快照继续制造“当前可用”的视觉证据。

## 运行边界

AnimeMachine 的主要实现位于 `src/animemachine`。Web、Catalog、Torrent 索引、收藏库核验、qBittorrent、Ani-RSS、播放和字幕模块共享 SQLite 证据，但不共享“所有事情都可以写”的权限。一个模块产生的结果，只有达到下一个模块要求的证据强度，才会继续进入目录修改、下载提交或替换流程。

程序直接处理两类输入：(1)用户或可选 Torrent Collector 放进共享目录的本地 Torrent 元数据；(2)用户连接的外部组件返回的记录。Archive、封面和补充元数据统一经过网络层，由网络层处理代理/直连选择、镜像切换、失败退避、响应大小限制和完整性校验。对于已知大小与摘要的 Archive/应用升级资产，下载层优先使用可续传 Range 分段；若分段源在实际传输中失效而已有探测确认的非 Range 备用源，则降级为整文件传输，仍在原子发布前验证大小和 SHA-256，完整但摘要错误的临时文件不会进入下一轮重试。代理设置按每次请求动态读取，并将实际路由标记为直连、环境代理或 Windows 系统代理；代理 URL 无效、端口异常或当前运行时无法建立相应代理传输时，该候选路由会在客户端建立阶段被隔离并继续尝试后续路由，诊断中的代理标识也只保留脱敏后的 scheme/host/port；实际代理设置变化仍会产生新的连接代际，但网络健康学习固定按这三类网络环境分别累计，因此切换代理后可以立即使用对应环境此前学到的最优源，切回直连也不会丢失原有直连经验。localhost、回环和私有网段保持直连。部署凭据优先从环境变量或密钥文件取得；管理员在 Web 设置页填写的 qBittorrent、Ani-RSS 与字幕服务凭据则保存在状态目录的受限凭据文件中，并在重启后继续生效。它们不会写入公开配置、文档、浏览器存储或 Web API 响应；POSIX 使用仅服务账户可读写的权限，Windows 尽量收紧为当前服务账户和 SYSTEM 可访问。该文件是权限隔离的本地密钥存储而非加密保险库，因此拥有服务账户或宿主机管理员权限者仍可读取；部署环境变量/Secret 始终优先于 Web 保存值。连接测试可以把当前输入框中的 qBittorrent/Ani-RSS Key 作为仅本次请求使用的临时凭据传给服务端探测器，不写入进程环境或状态文件；持久化只发生在设置保存流程。设置保存由服务端把完整配置与本次新凭据作为一个事务处理：先执行持久配置和运行时覆盖后的完整校验，再原子写配置并以可回滚批次写入凭据；任一持久化步骤失败都会恢复本次提交前状态；配置与凭据写入共用同一写入门闩，并发管理员请求不会穿插到事务与回滚之间。显式连接测试进入 `recovery_probe` 上下文，因此即使完全离线已确认也不会被本地模式阻断，同时 localhost、回环和私有网段仍按本地目标直连。网络健康层分别持久保存每个端点在各网络环境下的近期成功率、EWMA 延迟、吞吐、冷却状态和最近失败原因，并以时间桶保留图片源短期健康趋势。近期样本会按时间衰减形成有效样本量，低样本结果通过置信度收缩避免被偶发成功或失败放大；端点选择在综合质量之外增加当前源保持窗口和最小切换收益阈值，只有明显更优或当前源进入冷却时才切换。诊断探测与正式请求共用同一份健康证据，并显示当前选择、样本置信度和保持/切换原因。完全离线只在 AnimeMachine 常用服务与独立互联网探针持续失败至少 30 分钟、且失败探测没有长时间空档时才确认；第一次整体失败起即暂停失败样本学习，但仍继续允许正常请求尝试，确认离线后才暂停远程后台任务。恢复探测始终可以绕过本地模式，普通远程请求或手动网络复检一旦证明联网即退出离线状态并恢复后台工作，因此代理切换、短时断网、单一上游故障或休眠唤醒都不会把程序锁死在本地模式。图片预加载由独立进程执行，后台并发和带宽限制只作用于后台任务；前台可见作品始终优先，已进入后台队列的同一作品也可以被前台请求即时提升。后台预算会根据前台交互压力、前台图片响应时间、CPU 压力以及近期图片 I/O 时长和网络失败信号保守缩放；浏览器侧还会按滚动方向在严格有限的窗口内预取下一屏附近作品。服务启动后的后台预加载先按当前随机种子逐页完成有界的首页预取窗口，再补齐最近 6 个月全部作品，随后从第 7 个月开始严格逐月向更早作品回溯；定期图片更新使用独立的最低优先级队列。已有正常缓存只在开播前 6 至 2 个月、开播前 2 个月至开播后 1 个月、开播后 1 至 2 个月三个窗口内自动检测，间隔分别为 72、24、72 小时，维护扫描每 12 小时挑选到期作品，窗口外不自动刷新，手动“重新加载”始终可强制刷新。

可选 Torrent Collector 作为独立 Compose 服务运行，对共享 Torrent Pool 有写权限；AnimeMachine 对同一 Pool 仍保持只读。这个边界很重要：Collector 负责“能否把元数据纳入候选池”，AnimeMachine 负责“这份候选到底对应哪部作品、能否覆盖目标、是否值得下载”。前者不能替代后者。

首次部署边界也属于安全模型的一部分。CLI、本地启动器和四套 Compose 默认统一监听 `0.0.0.0:8787`，因此同一局域网可直接使用主机 `IP:8787`；非回环监听在没有显式覆盖时自动启用 Web 认证。首次创建账户库时，无论管理员密码来自自动生成、部署变量还是密钥文件，控制台都会明确显示初始管理员账号和密码；对于零配置自动生成并保存到受限凭据文件的初始管理员，只要该账户仍处于启用的管理员状态，后续启动也会再次显示同一组账号密码，避免首次日志被错过。显式部署凭据不会为了重复显示而额外落盘。托管 qBittorrent/Ani-RSS 未提供服务密钥时，由各自 bootstrap 在组件配置目录的 `.animemachine/` 下生成一次并持久复用，AnimeMachine 只读挂载这些密钥文件；显式环境变量或 Secret 仍优先。第 3/4 套托管 Compose 还把应用启动依赖明确绑定到一次性 bootstrap 的成功完成和对应服务容器的启动，因此首次创建空配置目录时，AnimeMachine 不会先于 API 密钥文件生成而启动。Compose 不依赖必须存在的 `.env`，并为本地目录提供相对路径默认值，所以模板本身可以直接启动，而 `.env` 只承担覆盖默认值的职责；`04-full-stack/compose.yaml` 还内联了 Torrent Collector 服务和命名卷定义，不依赖父目录中的其它 Compose 文件，因此单独复制到空目录也保持完整。完整栈的下载路径也采用单一语义：Ani-RSS 生成的最终下载模板使用共享 `/Media`，qBittorrent 把 `/downloads/incomplete` 作为未完成临时目录，AnimeMachine 再以只读 `/Media` 消费完成媒体，从而让“订阅 → 下载 → 扫描/播放”在零配置下保持同一路径闭环。Docker supervisor 以 root 身份仅完成必要可写挂载点的非递归所有权准备，随后在启动任何 AnimeMachine 命令前永久降权到 `PUID/PGID`；因此 Docker 首次创建的空 bind 目录不会阻塞零配置启动，同时主程序仍以非 root 身份运行。

## Web 认证与权限边界

Web 层使用本地 SQLite 账户库和短期会话 Cookie。启用认证时账户只有 `admin` 与 `user` 两类：服务端的 `requires_admin()` 对配置写入、Archive/元数据维护、Library Audit、历史恢复、用户管理、网络复检、图片预加载控制、日志/历史/诊断读取和应用更新等管理接口统一执行管理员检查；普通用户保留 Catalog 查询、单作品操作、下载计划和允许的播放/订阅能力。状态改变请求同时要求有效 CSRF token。配置/API 输出会对凭据等敏感值脱敏。

前端只把权限显隐作为可用性提示，安全边界始终由服务端再次验证。例如全局“重新随机”会改变实例随机种子，因此仅管理员显示并可调用；普通用户不会看到该按钮，即使自行构造请求也会被服务端拒绝。认证关闭时本地单用户会话映射为管理员角色，但 Web 服务仍执行 Host/Origin 与写请求约束，不能把“无登录”理解为“无请求边界”。

## 数据流

```text
Bangumi Archive ──> 动画 Catalog ──> 标题、关系、目录规划
Torrent Collector ─> 共享 Torrent 池（合集元数据）
Torrent 池 ───────> 增量索引 ─────> 候选策略与文件清单
本地收藏库 ───────> 核验/历史 ───> 差分补完与状态
Ani-RSS ──────────> 订阅与只读媒体映射
候选计划 ─────────> qBittorrent / Ani-RSS ──> 下载状态回写
```

Archive 在后台分阶段构建，只有完整性检查通过后才原子发布。大型 Torrent Pool 与外部媒体库采用增量、分批处理，避免一次全量扫描长期占用数据库事务。Web 查询使用独立连接和短事务，因此后台建库、扫描和前台浏览可以并行进行。启动状态 API 将生命周期明确为 `Starting → Ready → Warming → Warm`：`Ready` 表示 Catalog 与 Web 已可正常使用，`Warming` 只表示后台 Catalog/图片准备仍在继续，不能被前端解释成服务不可用。首页第二行采用“后台图片准备中 · 由后向前已获取至 YYYY-MM 的图片；使用 Bangumi Archive YYYYMMDD · 共 N 部作品。”的紧凑结构，不再显示剩余量、ETA 或当前处理对象。完整进度、剩余量、基于近期实际处理吞吐估算的 ETA、当前对象及自适应后台并发预算继续保留在诊断页。年/季筛选本质上仍投影为显式 `start_from` / `start_to` 月份边界：冬季以 1 月所属年份为锚点并跨到上一年 12 月，春、夏、秋分别映射为 3–5、6–8、9–11 月，因此服务端无需增加第二套“季”查询语义。浏览器恢复旧筛选状态时会先按当前季节定义归一化，再进行年/季反向同步；仅保存跨年冬季月份的旧状态以 1 月所在年份作为锚点，避免恢复时产生一年的偏移。预加载阶段与控制状态另外持久化，重启后会以图片缓存为事实基线继续处理。

非日本动画的 Archive 主标题仍写入兼容字段 `anime_work.title_ja`，但该物理列名现在只是历史兼容名称，语义是“Archive 主标题/原标题”；真实语言由 `original_language` 决定。`anime_title` 保存带语言标签的多语标题与别名，因此韩文主标题可以与中文译名、日文版名、英文版名同时存在。国家证据会综合标签、Infobox、标题文字和制作公司；非日本作品的制作公司聚合只使用 Archive 中可验证的“品牌〖法人列表〗”“法人名（品牌）”结构，日本作品继续使用既有改名族规则。原作关系标题与动画标题分表保存，避免把同名原作或某一地区版标题反写成动画原标题。标题归一化路径同时保留韩文和西里尔字母，供原作匹配、字幕搜索和媒体完整性比较使用。

封面是另一个容易拖慢整个系统的典型外部依赖，所以网络读取被移到独立 `ImageFetcher` 进程。程序优先尝试 Bangumi 约 400 px 的服务端缩放图，并对官方源与可用镜像执行短延迟并行后备，原图留作最后兜底。瞬时失败只做短期负缓存；服务重启后会清除这类瞬时失败状态。缓存未命中时，Web API 先返回占位图，后台成功后由前端自动替换；同作品正在下载时再次点击“重新加载”，也会保留一次强制刷新，而不是被正在进行的请求直接吞掉。已有有效缓存的刷新失败时继续返回旧图，并保留最后一次成功获取时间和失败证据，使该作品在后续 12 小时维护轮次仍可按原 24/72 小时刷新规则重试，而不会把失败检查误当作一次成功刷新后延后整个刷新周期。批量图片维护以终止状态统计进度；完全离线或图片工作进程不可用而未能入队的项目会计入失败，不会仅因队列为空而误报为成功。 Web 持久化凭据会在独立图片进程创建前装入父进程环境，同时每个任务都携带当前有效 Ani-RSS 凭据快照；因此 `spawn` 子进程不会把启动时的旧 API Key 固化到后续请求，运行中更换或删除 Key 无需重启即可让 Ani-RSS 封面捷径启用、切换或停用。

## 身份与目录

目录处理遵循一个固定顺序：**先确认作品，再确认已有路径，最后才考虑新建。** 作品身份由标题、别名、首播年月、系列关系和现有文件共同提供证据；如果已有目录中存在唯一、可信的相近目标，优先复用。发现错误目录时也先在原位置纠正，而不是先新建一个“看起来更标准”的目录。官方英语副标题只有在与原名语义不同、且证据充分时才追加到目录名称。

这套设计的原因是，Bangumi 的逻辑条目并不天然等于物理目录。分割放送、附属短篇、原生没有拆分的电影/OVA 合集、超长连续作品，都可能需要把多个逻辑成员归到同一物理目标；反过来，物理目录合并以后，Catalog 中的逻辑成员仍要分别保留。所有下载计划因此先解析到规范目标路径，再与本地文件做差分，不能跳过身份层直接按 Torrent 标题拼目录。

## 资源策略

用户提供的 Torrent 与 Collector 收集的 Torrent 最终进入同一增量索引。Collector 的预筛选只负责挡掉明确不符合自动收集边界的元数据，不能替代 AnimeMachine 的作品识别、资格判断和排序。资源类别只有在用户明确关闭时才被排除，无法识别的值进入“其它”；这比把未知值当成错误更适合长期收藏库，因为旧资源的命名并不总是规范。

“允许的资源类别”同时包含地区策略。中国映射中国大陆/港澳台，欧洲映射全部欧洲国家（含英国、俄罗斯），地区为空或证据不足映射“其它”。该策略只约束新候选的资格，不破坏已经存在的媒体、订阅或历史证据。

排序以一部作品或一个系列的完整方案为单位。系统先判断方案是否覆盖应有集数/卷数，再比较合集形式、资源组、片源、分辨率、字幕和修订日期等条件。资源质量在覆盖关系成立后参与比较，高分辨率不能抵消缺集。

同一 infohash 在 AnimeMachine 中只能存在一个受管任务。一个合集可以把不同文件索引映射给多个子作品；以后需要补充文件时继续复用原任务，只追加此前没有选择的索引。任何正式提交前都会先生成不可变计划。如果计划发现目标目录冲突或待替换文件，就转入暂存、核验或人工审核，不直接覆盖现有内容。

## 作品关系图算法

作品关系图先从多对多关系中恢复关系结构，再确定绘制方式。第一阶段处理图本身：(1)把 Bangumi 原始关系规范化为方向边；(2)补齐能够确定的反向关系；(3)删除可以确认的重复边，以及能够证明的传递冗余；(4)使用严格关系建立系列连通分量。只有证据足够强时，系统才修正明显误连、给孤立子系列补入口，或把关系重新锚定到子系列首部；原始证据始终保留，修正结果不会覆盖来源事实。

第二阶段才处理布局。节点按年月、媒介和标题序列安排；同媒介或具有明确数字顺序的作品优先同排。主线续作尽量走中轴直线，番外、衍生、总集篇、不同演绎和跨系列关系使用独立轨道与端口。路由器同时考虑节点边界、已占轨道、标签矩形和转折成本，可选择直线、正交折线或必要的纵向绕行；同一起点的长跨距关系再按时间和目标位置分层，尽量减少无法辨认的交叉。复杂关系图支持隐藏指定关系类型、全屏浏览和导出 SVG/PNG。

## 仓库结构

```text
src/                 运行源码与内置静态资源
config/              公开配置示例与 JSON Schema
deploy/              本地、四种 Compose 模板及共享 Torrent Collector 定义
packaging/            镜像构建定义
scripts/              Windows、Linux、macOS 构建/启动/清理入口
tests/                可重复的单元与集成测试
docs/                 用户与开发文档
```

运行数据库、Archive、封面缓存、日志、凭据、私有路径和构建产物都属于运行时数据或本地产物，不属于源码仓库。这个区分也意味着：源码可以重新取得，状态目录却应该备份；反过来，清理构建缓存不应触碰用户 Catalog 和收藏历史。

## 数据库约定

AnimeMachine 使用两个 SQLite 文件，分别承载“大规模扫描写入”和“前台稳定查询”。(1)动画 Catalog 默认位于 `$ANM_STATE_DIR/catalog/anime-catalog.sqlite3`，保存 Bangumi Archive 派生的动画元数据、作品关系、封面、外部媒体映射，以及 Web 查询和计划生成需要的运行状态投影；(2)运行库默认位于 `$ANM_STATE_DIR/catalog/runtime.sqlite3`，保存 Torrent Pool 原始增量索引、已核验身份、文件分区、提交证据和本地核验结果。运行库完成短批次后，只把已经核验的结果同步到 Catalog 的 `runtime_*` 表，因此前台不需要直接争用扫描库。

两个数据库路径都可以由环境变量覆盖，但两个 AnimeMachine 实例不能同时写入同一状态目录。动画 Catalog 的基础结构由 `src/animemachine/catalog/service.py` 构建，运行库迁移由 `src/animemachine/catalog/migrations.py` 管理，查询投影由 `src/animemachine/torrents/runtime.py` 管理。迁移必须向前兼容并可重复执行；凭据、私有路径清单和人工导出结果不得写入公开文档或测试夹具。

### 动画 Catalog

- `anime_work`：动画逻辑作品，保存 Bangumi ID、Archive 主标题（物理列 `title_ja` 为兼容名称）、`original_language`、首播年月、媒介、话数、简介和物理归并角色。
- `anime_title`：保存带语言标签的多语标题和别名，包括非日本作品的原语主标题与明确的地区/语言版本名；目录命名只使用已经核验的原名，以及确有必要的副标题。
- `anime_staff`、`anime_cast`、`anime_studio`、`anime_studio_cluster`：保存制作人员、声优和制作公司的归一化结果。
- `anime_tag`、`anime_theme`、`anime_theme_evidence`、`anime_country`：保存筛选字段及其规则证据。
- `anime_relation`：保存 Archive 原始关系；`anime_relation_edge` 和 `anime_series_component` 分别保存规范化关系与严格系列连通分量。
- `anime_image`：保存经过验证的封面 MIME、字节、来源和缓存状态；只有完整下载并通过格式验证后才原子写入。
- `external_library_source`、`external_media_file`：保存外部只读媒体库的来源、目录和文件级证据。
- `ani_rss_state`、`ani_rss_subscription`、`ani_rss_media`、`ani_rss_resource`、`ani_rss_search_state`、`ani_rss_action`：保存 Ani-RSS 同步状态、可播放媒体快照、后台资源检索节流状态与幂等操作记录。
- `metadata_snapshot`、`metadata_evidence`、`metadata_repair_queue`：保存底包来源、补充元数据和延后修补任务。

### 运行库与查询投影

- `torrent_source`、`torrent`、`torrent_manifest_file`：保存 Torrent Pool 文件指纹、infohash、标题、片源、资源组、manifest 和解析错误；只有来源指纹变化时才重新读取。来源路径身份遵循宿主文件系统的路径归一化规则：Windows 上大小写等价，区分大小写的文件系统则保留大小写差异，以便缺失来源能被准确核对。同一 info-hash 存在多份 `.torrent` 副本时，如果当前主来源消失，完整扫描会把 `torrent_path` 自动回选到仍存在的副本，避免可用元数据继续指向失效路径。
- `anime_work`、`anime_work_member`、`torrent_work`：保存物理目标、逻辑成员，以及 Torrent 到作品的已核验多对多映射；`torrent_work` 是身份与最终路径的权威证据。
- `file_map`：保存合集内每个文件索引的规范目标和选择证据。
- `submission`、`submission_revision`、`submission_file_revision`：保存 AnimeMachine 管理的 qBittorrent 任务和追加选择历史；一个 infohash 只对应一个任务。
- `asset_provenance`、`release_baseline`、`upgrade_candidate`：保存本地文件来源、比较基线和可核验的升级候选。
- `torrent_resolution`、`torrent_target_path`、`title_review`、`scope_exclusion`：保存不能自动确认的范围、标题、目标与处理理由。
- `runtime_work`、`runtime_torrent`、`runtime_torrent_work`、`runtime_torrent_file`、`runtime_file_map`、`runtime_submission`：位于动画 Catalog 中，是已核验运行数据的前台查询投影，不替代运行库中的权威记录。
- `download_plan`、`runtime_watch`、`runtime_watch_match`、`runtime_asset`、`runtime_completeness`、`runtime_review`：位于动画 Catalog 中，保存不可变计划、追更、本地完整度和前台审核状态。

### 状态原则

AnimeMachine 的状态处理可以归纳为六条：(1)逻辑作品不等于物理目录，分割放送、附属短篇和原生未拆分合集可以共享一个物理目标；(2)未核验映射、临时提案和模糊匹配不能授权目录修改或下载提交；(3)本地文件差分只在同一规范目标内比较，快速模式以规范目标和精确字节数判断跳过，精确模式只在存在比较基准时计算哈希；(4)替换必须同时具备修订证据、完整暂存和验证，任何一步失败都保留旧文件；(5)磁力任务在取得完整 manifest 前只登记，不自动映射文件，也不提交下载；(6)配置变化只使派生排序和尚未执行的计划失效，不删除已经核验的作品身份和来源证据。

这六条的共同目标是让“状态变化”可解释。系统可以因为新证据改变结论，但不能因为一次配置改动或一次模糊匹配，把以前已经验证过的事实一起抹掉。

### 并发

长时间导入和扫描使用短批次提交，避免持有长事务；Web 读取使用独立连接并启用 WAL。封面网络访问完全运行在独立进程中，不占用 Web 请求线程或主进程 HTTP 连接池。前端进度来自原子状态文件或后台任务表。耗时任务保持独立运行，其延迟不会扩散到普通浏览和查询。
