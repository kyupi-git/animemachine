# AnimeMachine 部署指南

部署 AnimeMachine 时，首先确定两项内容：(1)AnimeMachine 管理的媒体存放位置；(2)现有 qBittorrent、Ani-RSS、Torrent 池和旧媒体库采用外置方式，或统一交给 Compose 管理。其它设置基本由这两项选择派生。

首次运行前，至少准备一个动画收藏库即可。Torrent 池和外部只读媒体库可以先为空，qBittorrent 与 Ani-RSS 也都不是启动 AnimeMachine 的前置条件；以后补接组件，不需要重新建库。

## 路径的含义

| 名称 | 权限 | 用途 | 推荐设置 |
|---|---|---|---|
| 动画收藏库 | 读写 | 保存 AnimeMachine 管理的媒体、占位、字幕和目录结构 | 本机磁盘、NAS 共享目录或容器 `/Library` |
| Torrent 池 | AnimeMachine 只读 | 用户或可选 Torrent Collector 放入 `.torrent` 的目录；允许包含子目录和无关文件 | 独立目录或容器 `/Torrents` |
| 外部只读媒体库 | 只读 | 映射已经存在的媒体，不移动、不改名、不删除 | ani-rss 或其它媒体目录；容器 `/External` |
| Ani-RSS 媒体目录 | 只读 | 将 Ani-RSS 已下载内容映射到作品页和播放列表 | 容器 `/Media` |
| 状态目录 | 读写 | 保存 SQLite、Archive、封面、字幕、计划和操作历史 | 本地 SSD；容器 `/Data` |
| 配置目录 | 读写 | 保存 `config.json`、证书和组件配置 | 容器 `/Config` |

这几类路径最容易混淆的是“宿主机路径”“AnimeMachine 看到的路径”和“qBittorrent 看到的路径”。本地运行时三者往往相同；Docker 或跨主机部署时则可能完全不同。AnimeMachine 只要求最终的路径映射关系真实可访问，并不要求不同进程使用同一串路径文字。

Windows 本地部署可以直接填写盘符或 UNC，例如 `D:\Anime`、`\\nas\anime`。访问 UNC 的是运行 AnimeMachine 的 Windows 账号，因此该账号必须能够直接读写共享目录；映射盘符属于当前登录会话，不适合作为长期后台服务的唯一依赖。建议使用同一账号实际新建、改名并删除一个测试文件，以确认权限完整。

Docker 中的 `/Library`、`/Torrents` 等是容器内部固定路径，用户只需要把宿主机真实目录挂载到这些位置。外部 qBittorrent 还要另外填写“qBittorrent 自己看到的收藏库路径”，它可能是 `/Anime`、`/downloads/anime` 或 UNC，不要求与 AnimeMachine 的 `/Library` 相同。Windows Docker Desktop 通常不适合直接把 UNC 当作 bind source；更稳妥的做法是先由宿主系统挂载 SMB/NFS，再把本地挂载点交给 Docker。Linux、macOS 和 fnOS 也建议采用同一思路。

![连接与路径设置](images/settings-connections.png)

*“设置 → 连接”：集中确认收藏库、Torrent Pool、外部媒体库、qBittorrent 与 Ani-RSS 的连接和路径状态。*

配置与 Ani-RSS 的连接时，可以在 Ani-RSS 设置界面的“登录设置”找到所需的 API key。0.2.0 起，在“设置 → 连接”中保存 qBittorrent、Ani-RSS、ASSRT 或 OpenSubtitles 的 API 凭据后，凭据会写入状态目录下权限受限的 `credentials/` 文件并在重启后继续生效；正文不会进入 `config.json`、浏览器本地存储、日志或 API 响应。若部署侧已经通过环境变量或 Docker Secret 提供同一凭据，则部署值优先，Web 保存值不会覆盖运行中的部署凭据。“测试连接”会临时使用当前输入框中的 qBittorrent/Ani-RSS API Key，但不会保存或清空它；只有提交“保存设置”才会把新凭据写入受限凭据文件。保存时，完整配置与本次新输入的多项凭据由服务端作为一个事务处理：先完成全部配置校验，再提交配置和凭据；任一步持久化失败都会回滚本次提交。即使系统已经确认完全离线，管理员主动执行“测试连接”仍会作为显式恢复探测尝试目标地址；已识别的本地/LAN 目标继续保持直连。

## 本地部署

### Windows 10/11

Windows 本地运行建议按以下顺序完成：(1)源码模式先安装 Python 3.11 或更高版本；官方 Windows Release 固定随包提供 Python 3.14 运行时，因此不要求额外安装 Python，根目录 `BUILD-INFO.json` 可核对版本、提交和构建环境；(2)源码模式运行 `scripts\windows\AnimeMachine.cmd`，Release 解压后运行根目录的 `AnimeMachine.cmd`；(3)不创建 `.env.local` 也可以直接启动，默认监听 `0.0.0.0:8787`，因此本机可用 `http://127.0.0.1:8787`，局域网其它设备可用 `http://<AnimeMachine主机IP>:8787`；远程可访问绑定会自动启用认证，首次启动若未提供管理员密码会生成随机密码并保存到受限凭据文件，控制台会明确显示账号、密码及保存位置；只要这个自动生成的初始管理员仍有效，后续启动也会再次显示同一组登录信息；(4)登录后进入“设置 → 连接”，再按需填写收藏库、Torrent 池和外部组件；(5)源码模式的状态默认位于 `.local/state`，Release 默认位于 `data/state`，重复启动会继续使用原来的 Catalog、缓存和历史。

如果希望第一次启动前就准备好路径，可以把 `deploy/local/.env.local.example` 复制为 `.local/.env.local`，再取消需要项目的注释。Release 则使用根目录的 `.env.local`。不建议为了“省一步”把 NAS 用户名和密码长期写进 AnimeMachine 配置；Windows 本地运行应优先让运行账号本身取得共享目录权限。

### Linux/macOS

Linux 源码模式运行 `scripts/unix/AnimeMachine-Linux.sh`，macOS 运行 `scripts/unix/AnimeMachine-macOS.command`；首次启动会在 `.local/venv` 建立隔离环境，同样要求 Python 3.11 或更高版本。Release 解压后使用根目录中的对应启动脚本。每个 Release 都保留 Windows、Linux 和 macOS 入口，但跨构建平台运行时需要系统自己提供 Python 3.11+，首次启动也可能联网安装当前平台可用的依赖。

若解压工具丢失了 Unix 可执行位，可以先执行 `chmod +x AnimeMachine.sh AnimeMachine-Linux.sh AnimeMachine-macOS.command`。macOS 访问 NAS 时，建议先在 Finder 挂载 SMB，再使用 `/Volumes/共享名/...`；Linux 则更适合由系统在 `/mnt` 或 `/srv` 挂载 SMB/NFS。这样做的好处是 AnimeMachine 只处理普通文件路径，认证、断线重连和网络文件系统行为仍由操作系统负责。

## Docker Compose

Docker 部署要求 Docker Engine 24+ 和 Docker Compose 2.20.3+；如果 AnimeMachine 直接管理 qBittorrent，目标 qBittorrent 需要 5.2.0 或更新版本。0.2.1 的完整 Compose 默认固定 Ani-RSS `v3.2.28` 与 qBittorrent `5.2.3`，当前适配层按这两版接口核验。四套 Compose 均可不创建 `.env` 直接执行 `docker compose up -d`：默认发布 `0.0.0.0:8787`，使用相对目录，并自动生成 AnimeMachine 管理员密码；`04-full-stack/compose.yaml` 是自包含单文件定义，即使只复制这一个 YAML 到空目录也不依赖父目录文件；第 3/4 套内置 qBittorrent、Ani-RSS 还会在各自配置目录中自动生成并持久复用随机 API 密钥；AnimeMachine 会等待对应 bootstrap 成功并确认托管服务容器已经启动后再进入首次应用启动，避免空配置目录下的密钥生成与应用启动发生竞态。第 4 套首次生成 Ani-RSS 配置时把最终下载目录模板指向共享 `/Media`（宿主机默认 `./external/ani-rss`），qBittorrent 的 `/downloads/incomplete` 只承担未完成数据，因此 Ani-RSS 下载完成后 AnimeMachine 可直接扫描、生成播放列表并播放，无需用户再对齐两套容器路径。为兼容 Docker 首次自动创建的 `root:root` 空目录，AnimeMachine 容器入口只在启动早期准备必要的可写挂载点，随后立即降权到 `PUID/PGID` 再启动应用；不会递归修改已有媒体文件。需要自定义宿主机路径、固定凭据、PUID/PGID、代理或端口时，再把 `.env.example` 复制为 `.env` 修改即可；原有显式配置仍优先于自动生成值。

配置完成后运行：

```bash
docker compose up -d
docker compose logs -f animemachine
```

若需要自定义部署，通常把 `.env` 与 `compose.yaml` 放在同一目录即可；Compose 会按标准规则自动读取它。自动化平台也可以直接使用 `docker compose --env-file /path/to/custom.env up -d`，不需要再设置额外的服务级环境文件路径。Compose 中的 `ANM_BIND_ADDRESS` 只控制宿主机发布地址，容器内 AnimeMachine 固定监听 `0.0.0.0:8787`；默认值让局域网设备可通过 `http://<Docker主机IP>:8787` 访问，并自动要求认证。若明确设置 `ANM_BIND_ADDRESS=127.0.0.1`，则只发布到宿主机回环地址。`ANM_WEB_PORT` 表示宿主机发布端口，容器内端口保持 8787。

以 fnOS 为例，通过 Docker Compose 首次启动时需要下载并解析 Bangumi Archive 底包。以集中出现的 `========== AnimeMachine access ==========` 为就绪标志：此时核心初始化和 Catalog 已完成，Web 服务已可访问，后台图片预加载已经开始；同一区块会简洁显示当前实际网络路由、Ani-RSS、qBittorrent、存储路径和主要图片源状态。实例随机种子在首次建立有效 Catalog 时生成并持久保存，普通重启或底库重建不会改变；只有用户点击“重新随机”或重新部署实例才会产生新种子。图片先按当前随机种子逐页完成有界的首页预取窗口，再完整处理最近 6 个月，并从第 7 个月开始逐月持续回溯更早作品；单张图片的临时失败不会阻塞后续批次，会在后台继续重试。已有正常缓存只在开播前 6 至 2 个月、开播前 2 个月至开播后 1 个月、开播后 1 至 2 个月三个区间自动检测更新，间隔分别为 72、24、72 小时；系统每 12 小时以最低优先级挑选到期作品，区间外停止自动刷新，手动“重新加载”不受限制。`[images] preload complete` 表示整段历史遍历和有限重试轮次已经完成，仍可能保留确实无封面或持续不可达的个别项目。

### 四种方案

| 目录 | 组件 | Torrent Pool 来源 | 推荐使用场景 |
|---|---|---|---|
| `01-animemachine-standalone` | AnimeMachine；可选外部 Ani-RSS | 用户维护目录或留空 | 独立维护动画底库、目录、外部媒体与 Torrent Pool；不配置 Ani-RSS 也可直接使用 |
| `02-animemachine-external-qbt` | AnimeMachine + 外部 qBittorrent；可选外部 Ani-RSS | 用户维护目录 | 手动收藏库；匹配 Torrent Pool 资源并提交到外部 qBittorrent |
| `03-animemachine-managed-qbt` | AnimeMachine + Torrent Collector + 内置 qBittorrent；可选外部 Ani-RSS | Collector 自动收集资源 | 自动收藏库；Collector 收集资源，内置 qBittorrent 维护收藏库 |
| `04-full-stack` | AnimeMachine + Torrent Collector + 内置 qBittorrent + 内置 Ani-RSS | Collector 自动收集合集 | 全自动收藏和订阅；所有组件由同一 Compose 项目管理 |

四种方案没有“低配到高配”的继承关系，都可以独立使用。前三种方案的 Ani-RSS 连接均为可选；已经有稳定 qBittorrent 的机器通常更适合 02，希望 AnimeMachine 连同下载链路一起迁移到 NAS，再考虑 03 或 04。`04-full-stack` 首次创建 Ani-RSS 配置时会补齐下载目录与自动启动等默认项；之后重建容器只更新由 Compose 管理的 API Key 与 qBittorrent 连接，不会覆盖用户已在 Ani-RSS 中修改的自动启动、下载目录模板等行为设置。

03 会引用 `deploy/compose/torrent-collector.yaml` 中的共享服务定义；04 为满足单文件零配置部署，已经把同一 Torrent Collector 服务和命名卷直接内联到 `04-full-stack/compose.yaml`，因此单独复制该 YAML 也可部署。发布包仍保留共享 Collector 文件供 03 与高级自定义复用。Torrent Collector 以 AnimeMachine 镜像中的 `torrent-collector` 命令运行，对宿主机 Torrent Pool 有写权限；AnimeMachine 对容器内 `/Torrents` 仍保持只读。Collector 使用标题、Torrent manifest 与本地 Catalog 证据执行 `accept / reject / defer` 三态裁决，只有 `accept` 才进入 Torrent Pool。证据不足的资源维持待判断状态，不用固定集数跨度“猜成全集”。现有 Pool 审计默认只报告；若要隔离明确拒绝的文件，需要显式启用隔离，并把隔离目录放在 Torrent Pool 之外。单集、单卷的持续追更仍交给 Ani-RSS 更合适。

普通 `.env` 只保留日常需要修改的变量。代理、轮询间隔、历史回溯批量、最大重试次数、审计模式和 Collector 独立状态目录等参数放在 `deploy/compose/torrent-collector.advanced.env.example`；确有调优需求时再复制对应项目到 `.env`，默认不启用代理。

### fnOS / NAS

fnOS 或类似 NAS 环境建议在 Docker 项目目录准备 `config`、`data`、`imports`、`torrents`、`library`、`external` 六类目录，再按读写特性分配存储：(1)`config`、`data` 放 SSD；(2)`library` 放大容量媒体存储池；(3)`torrents` 映射现有 Torrent Pool，AnimeMachine 一侧保持只读；(4)`external` 映射 ani-rss 或旧媒体目录，同样只读；(5)`.env` 填写 NAS 上真实绝对路径，例如 `/vol1/1000/docker/animemachine/data`；(6)容器使用的 `PUID/PGID` 必须对 `config`、`data`、`library` 具备写权限；使用 `04-full-stack` 时，还必须对 Ani-RSS 的媒体目录具备写权限。

如果部署后出现“页面能打开，但扫描不到文件”或“能读取却不能建立目录”，首先检查宿主机挂载和 `PUID/PGID`，而不是先改 AnimeMachine 的内部路径。容器内部路径是固定映射结果，宿主权限才是更常见的根因。

### 部署与存储分离

AnimeMachine 可以运行在小型主机或虚拟机中，而媒体实际放在另一台 NAS。推荐的完整路径是：NAS 提供 SMB/NFS → AnimeMachine 宿主系统负责挂载 → Compose 只接收本地挂载点。这样 AnimeMachine 不需要长期保存 NAS 账号密码，网络文件系统的重连也交给成熟的系统组件处理。

数据库、Archive 和封面缓存最好留在运行主机的 SSD，只把大容量媒体与 Torrent Pool 放到网络存储。原因很简单：建库、筛选和关系图会频繁读取大量小记录，而视频文件本身才真正需要容量。把两类 I/O 分开，通常比把整个状态目录放 NAS 更稳定。

## 网络与底包

AnimeMachine 的网络层会在官方源、用户配置的镜像和直连之间选择可用路径，并对 Archive 执行大小与 SHA-256 校验。对于 Archive 和应用升级这类已知大小与摘要的大文件，优先使用可续传的 Range 分段；如果首选 Range 路径在实际传输中失效，而另一路径已确认只能整文件传输，会自动降级到整文件下载并继续执行完整性校验。完整但 SHA-256 不匹配的临时文件会丢弃，避免后续重试复用损坏内容。每次外部请求都会重新判断实际路由，并区分直连、环境代理和 Windows 系统代理；代理配置发生变化时会自动进入新的连接代际，同时隔离旧网络环境留下的端点失败状态，因此从首次无代理切换到代理、在不同代理之间切换或恢复直连都不要求重启。若环境代理或 Windows 系统代理的 URL 损坏、端口无效或当前运行环境无法建立对应代理传输，该代理路由会被跳过并继续尝试后续路由（包括直连），而不是使整个远程请求链提前失败；诊断中的代理地址会脱敏，异常代理字符串也不会原样回显凭据。回环和私有网段始终保持直连，避免访问本地 qBittorrent、Ani-RSS 或 NAS 时绕远路。

“设置 → 常规”顶部的“系统健康”只把网络、Ani-RSS、qBittorrent、存储、图片预加载和播放链路压缩为少量“正常/警告”状态，详细信息仍集中在“设置 → 诊断”。诊断页会只读显示当前实际网络路由，以及 Bangumi Archive、Subject Cache、Bangumi API 和各图片源的近期成功率、延迟、吞吐与最近失败原因；图片源另外按直连、环境代理和 Windows 系统代理分别绘制近 12 小时健康趋势。“重新检测”使用与正式请求相同的网络层，因此检测结果也会更新镜像健康状态。镜像排序按三类网络环境分别学习，近期样本随时间衰减，并根据有效样本量计算置信度；低样本源不会因一次偶发结果立即跃迁。当前源还具有短时保持和最小切换收益阈值，诊断页会直接说明当前选择、置信度以及“继续保持/候选明显更优/当前源冷却”等选择原因。相同页面还显示最近 6 个月、历史库和失败重试三段图片预加载进度、预计剩余量、基于近期真实吞吐估算的 ETA、近期处理速率、当前处理对象和自适应后台并发。后台预加载可以暂停、恢复并限制并发或带宽，控制值与进度保存在状态目录；实际后台强度还会在此前台交互、图片响应变慢、CPU 压力升高或近期图片 I/O/网络状态恶化时自动降低，条件恢复后再逐步提高。预加载始终先满足前台可见作品，浏览器还会按滚动方向只预取下一屏附近的有限窗口；服务端后台则先按当前随机种子依次完成首页、第二页及后续有界预取页，再补齐最近 6 个月，随后从第 7 个月起逐月向历史回溯。定期图片更新排在全库预加载与失败重试之后，并限制为单个最低优先级后台任务；即使某作品已进入后台队列，前台滚动到该作品时也会立即提升其优先级。

Web 顶部第二行按“后台图片准备中 · 由后向前已获取至 YYYY-MM 的图片；使用 Bangumi Archive YYYYMMDD · 共 N 部作品。”的结构显示图片进度、底包版本和 Catalog 作品总数；首页不再显示剩余作品数、ETA 或当前处理对象，详细的剩余量、ETA、吞吐和当前对象仍可在“设置 → 诊断”查看。

如果希望完全手动准备底包，可以把官方 `dump-*.zip` 放入 `/Imports`，本地 Release 对应 `imports` 目录，再启动程序导入。公司 HTTPS 网关使用自签名证书时，应把 PEM CA 放入配置目录并设置 `ANM_CA_BUNDLE`。证书验证失败说明信任链没有建立，正确处理方式是补充 CA，而不是关闭 TLS 校验。

## 0.2.1 升级提示

从更早版本升级到 0.2.1 不需要重建 Catalog 或迁移媒体目录，0.2.0 用户也不需要额外迁移。原有本地/Compose 配置仍作为基础，应用更新定时检查默认关闭；未显式开启时不会自动安装新版。0.2.1 Docker 镜像继续包含稳定监督入口和可写状态目录中的应用层更新区域；如果当前仍是早于 0.2.0、尚不具备该监督入口的旧 Docker 镜像，应先按常规方式拉取 0.2.1 镜像并重建容器，之后才可使用 Web 内的 Docker 在线更新与失败回滚。便携版更新 worker 与 Docker supervisor 在重启后都会按实际监听地址执行健康检查；显式绑定 LAN/IPv6 地址时不会固定探测 `127.0.0.1`，只有 `0.0.0.0`/`::` 等通配监听才转换到相应回环地址。

网络行为也无需额外迁移。运行中启用、关闭或更换环境/Windows 系统代理后，后续请求会重新识别网络环境；诊断和健康学习按路由环境分离。若所有上游暂时失败，程序不会立即进入完全离线，而是在连续观测至少 30 分钟后才暂停远程后台工作，并保留恢复探测和受控的机会性恢复请求。升级后如需确认环境，可先在“设置 → 诊断”执行一次重新检测，再检查系统健康摘要、应用更新源和图片源状态。

## 更新与备份

更新和备份可以记成四条：(1)官方便携版和新版 Docker 镜像都可在“设置 → 检查更新”查看当前/最新版本、下载源、SHA-256 校验与升级结果，并手动检测或在线升级；更新线路会测试 GitHub、API、Release 与内置代理的健康度并持久学习最快可用线路，不可用线路进入退避冷却。定时检查默认关闭，启用后可选择仅通知或自动安装，默认每天 04:35 按运行设备本地时间检查。Docker 的应用层更新保存到状态目录，由容器内监督进程完成重启和失败回退，不需要挂载 Docker Socket；它只替换 AnimeMachine 自身 Python 应用层，若基础镜像、supervisor、Python/系统组件或运行依赖变化则不能用应用层更新代替完整镜像；(2)源码部署仍按源码更新后重新运行启动脚本，Docker 在上述镜像级内容发生变化或旧镜像尚不支持在线升级时使用 `docker compose pull && docker compose up -d` 完整更新镜像；(3)备份状态目录与配置目录即可保存数据库、封面、字幕、计划、设置及 Docker 在线升级层，媒体文件仍按用户自己的存储策略备份；(4)任何时候都不要让两个 AnimeMachine 实例同时写入同一个状态目录。

如果需要迁移机器，优先完整复制状态目录和配置目录，再恢复原来的媒体路径或等价映射。只复制 SQLite 而遗漏其它状态文件虽然可能可以启动，但会失去部分缓存、计划或历史上下文，不是推荐的迁移方式。

## 使用指南

### 设置与账户权限

“设置”窗口由管理员维护，包含常规、资源优先级、资源组、连接、诊断、订阅、用户、日志、历史记录、检查更新和关于 AnimeMachine。常规页用于 Archive/元数据维护与界面策略；资源优先级与资源组用于调整候选资源排序和发布组规则；连接页集中配置收藏库、Torrent Pool、qBittorrent、Ani-RSS、外部只读媒体、字幕服务、外部播放器交接以及元数据网络端点，其中播放器交接负责服务器路径到客户端路径或 HTTP 播放地址的映射；诊断页集中显示网络、存储、图片预加载、播放链路和系统健康状态，并可执行网络重新检测；订阅、用户、日志和历史记录分别用于后续发布/Ani-RSS 订阅、账户管理、排障和回看可恢复的目录变更；检查更新页用于检查和安装应用更新，关于页显示版本与项目链接。

“设置 → 常规 → 允许的资源类别”还提供资源地区多选：中国、日本、韩国、美国、欧洲、其它，默认全部勾选。中国包含中国大陆、香港、澳门和台湾；欧洲包含所有欧洲国家，包括英国和俄罗斯；地区为空或没有足够证据判断时归入“其它”。资源来自多国联合制作时，只要其中至少一个地区处于允许状态即可参与候选。中文界面按中、日、韩、美、欧、其它排列；英文按美、欧、中、日、韩、其它；日文按日、韩、中、美、欧、其它。该策略先作用于 Catalog 可见性，并同时约束 Torrent 与 Ani-RSS 的来源可用性：取消某地区后，该地区作品会从 Catalog 卡片结果中排除，也不会再以对应 Torrent/Ani-RSS 来源参与筛选，但不会删除已经存在的本地媒体或远端订阅记录。

日常设置优先通过 Web 修改。需要自动化部署或使用未在界面直接暴露的高级项时，`config/config.example.json` 是完整持久配置模板，`config/config.schema.json` 给出对应字段、类型、枚举与边界；实际配置默认是源码/便携版根目录的 `config.json`，Docker 为 `/Config/config.json`，也可用 `ANM_CONFIG_PATH` 改写。直接编辑 `config.json` 时应先停止 AnimeMachine，避免与 Web 保存并发覆盖；重新启动时内置配置校验会拒绝非法值。部署级环境变量仍以 `deploy/local/.env.local.example` 和各 Compose 目录的 `.env.example` 为准，不应把密码、Token 或代理凭据写回公开模板。

启用认证时只有两种角色。管理员可以修改设置、维护 Archive/元数据、运行 Library Audit 与网络复检、控制图片预加载、管理用户和执行应用更新，也可以在随机排序时点击“重新随机”生成新的实例随机种子。普通用户可以浏览 Catalog、查看作品与资源、刷新单部作品图片、生成并提交下载计划，以及使用允许的播放/订阅操作，但不能进入管理员设置或调用上述全局维护接口。建议首次登录后先创建一个新的管理员账户，再停用初始 `admin`；当前登录账户不能停用自己。关闭认证的单用户本地模式按管理员能力运行，但仍保留 Host/同源与写请求保护。

### 首次建库

第一次使用时，不建议同时打开所有自动化功能。更稳妥的顺序是：(1)登录后进入“设置 → 连接”，先确认动画收藏库、Torrent Pool 和可选外部媒体库的访问状态；(2)进入“常规”检查并更新动画底库，Archive 在后台分阶段导入，顶部状态行显示 Catalog 状态、后台图片回溯进度与底包信息，完整 Catalog 校验通过后再一次性发布；(3)Torrent Pool 按设定周期增量扫描，已完成批次可以立即查询，如果某部作品暂时没有出现候选资源，可以在作品详情页单独搜索；(4)已经存在大量旧媒体时，先执行本地资源核验，再考虑自动下载。

本地核验分为两个层级。快速模式主要比较规范目标、文件分布和精确字节数，适合日常扫描；存在可比较基准且用户明确启用精确核验时，再进行哈希验证。该机制只在必要位置提高判定强度，避免对全部视频重复计算 SHA-256。

### 选择与下载

首页第一次使用时，作品月份默认覆盖当前月份及之前五个月，例如 2026 年 8 月为 2026-03 至 2026-08；之后用户修改的筛选条件保存在浏览器本地状态。若起始月份与截止月份处于同一年，“年”会仅作为显示同步为该年并启用“季”；服务端在已有明确月份范围时会忽略重复的年份条件，因此查询结果不变。跨年冬季同样会被识别：例如“2026 年 + 冬（1月前后）”对应 2025-12 至 2026-02，其中“年”按 1 月所属的 2026 年计算。五个“季”选项为全部、冬（1月前后）、春（4月前后）、夏（7月前后）、秋（10月前后），四季分别对应 12–2、3–5、6–8、9–11 月；切换已选季节的年份会重新计算正确的月份范围，而自定义同年范围只修改“年”时仍保留原月份号。旧版浏览器中已保存的季节筛选会在恢复时按新定义自动归一化；对于只保存了“上一年 12 月至当年 2 月”而没有明确年份的旧冬季状态，也始终按 1 月所属年份恢复，不会整体偏移一年。默认每页显示 12 部作品。界面主题跟随操作系统，也可以在语言切换左侧手动选择暗色或浅色模式。

“未来/日期未知”是没有固定起止月份的独立筛选状态，因此恢复浏览器状态时不会用空月份反推并清除该选项。非日本动画的标题也不再套用“主标题一定是日语”的假设：Catalog 会结合 Archive 主标题文字、国家/地区、标签和制作公司证据保存原始语言；明确标注的日文、英文等别名仍独立保留并用于对应语言界面。原作关系中的标题单独作为“原作名称”显示，不会为了某个作品把原作标题或日文版标题硬编码成动画原标题。

资源选择可以自动和手动混合使用：(1)勾选作品后，系统按当前规则寻找完整度和优先级更合适的方案；(2)需要人工干预时，可以在作品详情页指定某个合集、合卷、多集或单集方案。自动选择并不意味着直接下载，它只是在当前证据下生成候选。

点击“开始下载”后，程序先生成不可变下载计划。计划会列出目标目录、预计空间、准备新增/跳过/暂存替换的文件，以及任务将交给 qBittorrent 还是 Ani-RSS。AnimeMachine 提交给 qBittorrent 的任务始终保持停止状态，避免“确认计划”等同于立即下载；核对计划后，再由用户在 qBittorrent 中启动任务。

资源策略优先完整合集，再考虑单集或单卷拼接。拼接方案必须根据实际覆盖范围判断，已经长期中断更新的发布组会降低优先级。本地已有文件则走差分计划：规范目标相同且字节数完全一致时默认跳过；缺失项只补缺失部分；具备可靠修订证据的旧文件先进入暂存；不是重复内容的原文件继续保留。

### 浏览、筛选与作品关系图

首页支持卡片/表格视图、月份与状态筛选、搜索、排序、每页数量以及随机排序；筛选与显示偏好保存在浏览器本地。“可用来源”分为“Torrent 来源”“Ani-RSS 来源”“无可用来源”：前两项可同时命中同一作品，只有两者都不存在时才属于“无可用来源”。“收藏库状态”独立且互斥地分为“本地入库”“外部只读”“提交下载”“暂未入库”：本地或 qBittorrent 已完成并已纳入受管目录的媒体属于“本地入库”；映射的只读媒体属于“外部只读”；通过 Ani-RSS HTTP API 可播放的媒体只有在当前凭据存在且连接已确认正常时才属于“外部只读”，断连、删除/更换凭据或端点变更待重新验证时，历史 API 媒体快照会保留用于恢复，但不会继续显示为当前可播放外部媒体，独立挂载的只读目录不受 API 健康状态影响；qBittorrent 已提交但尚未完成的排队、下载中、停止/暂停等任务属于“提交下载”；其余属于“暂未入库”。Ani-RSS 订阅本身不会进入“提交下载”。“目录待核验”等细粒度状态仍用于目录核验、完整度和下载安全判断，但不再作为收藏库筛选分类。设置中取消某个地区后，该地区作品会直接从 Catalog 卡片结果中排除，而不是转入“无可用来源”；联合制作只要至少一个地区仍被允许就继续显示。随机排序使用实例级持久种子，因此刷新页面或重启服务不会打乱同一随机序列；管理员点击“重新随机”才会生成新种子。作品详情页的“作品关系图”可以查看前作、续作、总集篇、番外、衍生、不同演绎和跨系列关联，点击节点可进入关联作品；复杂关系图支持全屏、隐藏部分关系类型，并可导出 SVG/PNG。卡片、详情、关系图、资源追更列表以及图片预加载诊断中的当前作品统一按当前界面语言选择标题；升级到 0.2.1 时会自动重新核对现有 Catalog 已保存的英文别名，剔除任何含非拉丁字母、却被错误标记为英文的标题（包括中/日/韩、西里尔、希腊、阿拉伯等文字），并补齐或改进可验证的英文显示标题；英语标题确实不存在时，英语界面会临时回退显示作品原标题以保持可读性，但不会把该原标题写回或标记为英文标题；后续取得可靠英文名后会自动优先使用，无需重建 Catalog。关系图中的勾选仍受当前资源资格和内部收藏核验状态约束，不能绕过正常下载计划。

### 后续发布监视

AnimeMachine 完成由单集或单卷构成的受管任务后，会按该任务的精确发布指纹建立后续发布监视；扫描到序号更高且指纹一致的新资源时，只在“设置 → 订阅”生成待确认匹配，不会自动下载。该监视与 Ani-RSS 的远端订阅是两套机制：删除这里的监视只停止 AnimeMachine 的后续匹配，不删除已经下载的媒体，也不会删除 Ani-RSS 远端订阅。

### Ani-RSS

Ani-RSS 连接后有三种资源调用模式：(1)优先调用：本地没有完整合集时优先交给 Ani-RSS；(2)备选调用：只有本地完全没有可用方案时才调用 Ani-RSS；(3)手动调用：不在后台自动查询或规划 Ani-RSS 资源，只有用户点击“Ani-RSS 查询资源”等显式操作时才执行资源查询。三种模式只控制资源发现与规划；订阅和 API 可播放媒体状态仍按“同步间隔（分钟）”周期更新。远端暂时不可用时不会改变用户选定的长期模式，连接恢复后仍按原设置工作。

当 Ani-RSS API Key 可正常连接且处于“优先调用”或“备选调用”时，AnimeMachine 会在后台预热 Ani-RSS 资源缓存。顺序跟随图片预加载：先按当前随机种子从首页开始逐页处理最近 6 个月作品，随后处理最近 6 个月的其余作品，再从第 7 个月起逐月回溯，最远到最近 24 个已开播自然月；图片批次先提交，Ani-RSS 用小规模受控并发随后检索，因此图片通常略早完成。运行中的周期复查使用“资源池扫描间隔（分钟）”，超过 24 个月的作品退出后台自动检索。启动预热与周期复查共用一个非阻塞扫描租约：若下一次扫描到期时上一轮仍未结束，本轮会直接跳过，不排队、不并发，也不提前更新完成时间；上一轮结束后由后续调度重新判断到期作品。若一轮资源检索因 Ani-RSS 连接或传输故障失败，失败证据会被记录，调度器改用不超过 5 分钟的短退避，而不是把失败当成完整扫描后等待整个资源池扫描间隔；若作品级最近尝试时间因系统时钟回拨而明显位于未来，则该作品会立即重新判定为到期，不会被异常时间戳长期跳过。运行期监控还会独立触发同一资源复查，因此首次部署时即便图片预热启动瞬间 Ani-RSS 尚未完成首次健康同步，连接在数秒后变为 `ready` 也会在当前进程自动补上资源复查，无需重启。该两年限制只约束无人值守预热/复查，不限制用户主动选择：只配置 Ani-RSS 且连接正常时，作品卡片和关系图节点仍可勾选，生成多作品计划时可按当前资源优先级将一部分作品提交 Ani-RSS、另一部分使用 Torrent。 单次作品查询会在前一标题没有结果时继续尝试后续可用的中/日/英标题候选，避免只有英文标题能命中时被前两个候选提前截断。若用户更换 Ani-RSS 地址或 API Key，上一来源的资源搜索缓存会立即清除；旧来源仍在执行的搜索结果不会在切换后写回，新来源验证成功后会立即重新进入资源扫描，而不是继续等待上一来源留下的扫描间隔。对远程 Ani-RSS，单次资源搜索还会记录开始时的有效代理路由代次；搜索途中代理或 `NO_PROXY` 换代时，本轮迟到结果会在落库前被丢弃，随后由当前网络代次继续正常复查。

由 Ani-RSS HTTP API 提供的媒体在当前 API 凭据存在且连接已确认正常时按外部只读来源处理，不直接移动或改名；独立挂载的 Ani-RSS 媒体目录始终按外部只读目录处理。同步间隔由“同步间隔（分钟）”统一控制，默认 30 分钟；自动订阅/API 媒体刷新只有一个后台监控入口。每轮先同步订阅与作品映射，再通过 API `playList` 刷新所有仍有远端 URL 的已映射订阅，包括在 Ani-RSS 中已禁用但仍可能保有下载内容的订阅，因此 Ani-RSS 新下载一话后，无需挂载 Ani-RSS 媒体目录，正常情况下也会在该同步间隔内出现在作品详情和 M3U 播放列表中。作品详情显示的“可播放集数”来自本地 `ani_rss_media` 快照的实际文件数/集数，而不是订阅的 `currentEpisodeNumber`，两者不会再混用。只有媒体阶段完整完成才记为一次完整成功；单个订阅的播放列表暂时失败或后台主动给用户操作让路时保留上一次成功结果，并在不超过 5 分钟的短周期内重新具备补偿同步资格，不会清空其它作品；若系统时钟回拨使持久化同步时间明显落到未来，也会立即重新判定为到期，避免刷新被未来时间戳长期抑制。若配置了 Ani-RSS 媒体目录，其只读目录扫描使用同一个“同步间隔”设置，但与 HTTP API 健康状态解耦：即使 API 未配置或暂时不可用，已配置的本地/挂载目录仍继续只读扫描；目录扫描在独立后台线程执行，不阻塞 API 快照刷新，同一外部媒体来源同一时刻只允许一轮扫描；同一来源上一轮未完成时新到期扫描直接跳过而不排队，其它来源不受影响。若 Ani-RSS 同时提供本地封面缓存，AnimeMachine 仅在当前 API Key 与最近一次同步所验证的凭据代际一致、端点与同步状态均已确认正常，且自身没有正常封面时通过 `/api/file` 快速尝试并验证图片；传输或服务端故障会使当前“端点 + 凭据代际”进入 30 秒快速回退冷却，让后续图片直接走原图片源；仅当该 Ani-RSS 端点实际使用的远程路由代际变化时才提前解除冷却，localhost/LAN 直连端点不会因无关代理开关反复重试；API Key 更换并完成重新同步后也不会继承旧冷却。HTTP 成功也只有在返回内容通过图片校验后才会把 `/api/file` 记为健康；无效图片会拒绝并立即回落；已有正常缓存不被后台替换，手动“重新加载”才会再次尝试 Ani-RSS。同一作品存在多个 Ani-RSS 订阅时按远端 ID 独立保留。Ani-RSS 未配置、凭据不存在、端点变化尚未重新验证或连接失败时，HTTP 自动同步、当前 Ani-RSS“可用来源”资格、API 外部只读状态、API 订阅/资源展示、远程播放入口与封面捷径都会跳过；SQLite 中最近一次成功 API 媒体快照只作为恢复缓存保留。Torrent、Bangumi 图片、本地收藏及已配置的 Ani-RSS 媒体目录只读扫描继续独立运行；localhost、回环和私有网段保持直连，不会因用户切换环境代理而绕路；远程 Ani-RSS 则会跟踪实际代理/直连路由代际；同步开始时会固定记录本轮真正使用的路由代际，因此即使代理恰好在同步过程中切换，也不会把新路由误记为已验证，后续会立即补偿同步。环境代理、Windows 系统代理或 `NO_PROXY` 规则发生有效变化后，会立即使统一同步重新具备到期资格，不必等待原同步间隔。新路由完成同步验证前，旧远程 `ready` 快照会被视为待重新验证，不再作为当前 Ani-RSS 资源、API 外部只读媒体或远程播放来源暴露；数据库快照仅作为恢复缓存保留。本地/LAN 目标保持直连，不受该门控影响。 若某轮 `listAni` 对已有远端 ID 暂时漏掉 URL、启用状态、当前/总集数、下载路径等可选字段，AnimeMachine 会沿用上一轮已验证值，使后续 `playList` 仍能刷新新增集数且不会把已知订阅状态误清零；只有明确删除的远端订阅才进入删除流程。 如果 `listAni` 本轮申报的订阅总数大于实际返回的唯一远端 ID 数，系统会把整轮视为不完整快照：未返回订阅不累计删除宽限、完整成功时间不前移，并在短周期内重试，直至取得可验证的完整列表。兼容旧版 Ani-RSS 时，如果 `listAni` 不提供 `total`，现有行仍可同步，但“未出现”本身不会作为删除证据；只有带有效 `total` 且数量与返回的唯一远端 ID 数一致的完整列表才会推进缺失订阅的删除宽限。Web 保存的 Ani-RSS API Key 会在图片工作进程启动前装载，并把当前有效值随图片任务传入，因此运行中修改或删除凭据会立即让封面捷径切换到当前状态。已经签发的远程播放地址如果随后遇到凭据删除/更换或连接状态不再为 `ready`，会先在 AnimeMachine 本地快速失效，不再继续向不可用 Ani-RSS 发起媒体请求。若成功同步时发现已映射作品现在具有明确的 Ani-RSS 封面路径，AnimeMachine 会解除该作品此前由自身图片链路留下、且没有有效图片字节的 `no_cover` 负缓存；因此 Ani-RSS 恢复后不必等待 24/72 小时图片维护周期，下一次正常图片请求即可重新尝试 Ani-RSS。

作品详情页允许删除已有下载内容的 Ani-RSS 订阅，但这是明确的远端写操作：界面会再次确认，然后通过 Ani-RSS HTTP API 请求删除订阅及文件，再重新同步远端列表核对结果。这里的“外部只读”是指 AnimeMachine 不直接改写映射目录，不代表用户明确发出的 Ani-RSS API 删除操作也被禁止。

### 播放

收藏库列表需要先选中一个具体媒体，再使用“复制”“下载播放列表”“使用 VLC 打开”或“使用 PotPlayer 打开”。生成的 M3U 只包含正片，并按集数排序；同一集存在多个媒体副本时，默认播放列表按来源优先级和文件大小选择一份。不同集数始终独立选择，即使两个文件的字节数恰好相同也不会互相去重。特典和其它副本仍保留在收藏库记录中。如果从第 N 集开始播放，前面的项目仍保留在列表里，只把播放器起始位置放到用户选择的媒体。

本地运行时，播放器通常可以直接使用文件路径；Docker 或远程部署则未必。容器内部的 `/Library` 对用户电脑没有意义，因此需要在“设置 → 连接 → 外部播放器交接”提供客户端可以访问的 HTTP 地址，或者建立服务器路径到客户端路径的映射。例如服务器 `/Library` 可以映射到 Windows 的 `\\nas\anime`，也可以映射到 macOS 的 `/Volumes/anime`。如果 Ani-RSS 媒体目录没有挂载，AnimeMachine 仍可通过 Ani-RSS HTTP API 生成并代理完整 M3U；VLC/PotPlayer 访问的是 AnimeMachine 的临时 HTTP 媒体地址，支持字节 Range、拖动进度和列表连续播放，并会在上游发生短暂中断时从已传输位置尝试续传。因此远程 Ani-RSS 播放不以本地媒体路径为前提。

出现 PotPlayer/VLC 拖动失败、中途停止或远程播放速度异常时，可直接查看“设置 → 诊断 → 远程播放会话”。该区域只保留最近会话的简洁运行摘要，包括客户端 Range、自动续传次数、Ani-RSS 上游 HTTP 状态与当前传输速率，不保存媒体内容、完整本地路径或凭据。

### 字幕

连载类资源在候选选择阶段优先匹配用户语言字幕；归档类资源则按顺序检查：(1)媒体内嵌字幕；(2)同名外挂字幕；(3)本地字幕压缩包；(4)用户自行配置的字幕服务。选择新的字幕文件时，旧字幕先备份到状态目录；媒体如果来自外部只读库，新字幕也保存到 AnimeMachine 状态目录，不写回原媒体路径。

因此，字幕处理和媒体所有权是分开的：AnimeMachine 可以为一个只读视频建立播放时的字幕关联，但不会因为“找到了更好的字幕”就获得修改外部媒体库的权限。

### 目录与历史

单部作品目录默认使用 `『YYYY_MM』『作品原名』`；系列目录使用 `『开始－结束』『「系列根名」シリーズ』`，系列内的子作品仍按各自首播年月命名。分割放送如果属于同一官方季度，会归并到首个季度；迷你动画、Picture Drama 等内容如果具有明确本篇归属，则作为附件处理，不另外创建占位目录。

目录处理以确认作品身份和已有路径为前提。AnimeMachine 对用户原有文件执行移动、改名或替换前，会把变更写入“设置 → 历史记录”；程序自己新建的普通目录不重复记录。如果目录占用、合集边界或作品身份仍然存在无法自动证明的冲突，下载计划会停在审核状态，等待取得充分证据后继续。
